## 슬라이드 2: 프로그램 분석이란?

### 개념 설명
프로그램 분석(Program Analysis)은 **프로그램을 직접 실행하지 않고도 프로그램의 특성을 자동으로 결정하는 기법**입니다. 예를 들어, "변수 x가 항상 양수인가?"와 같은 질문에 yes 또는 no로 답할 수 있습니다.

### 배경 지식
2학년 학생들도 이미 여러 프로그램을 작성하면서 다음과 같은 경험을 했을 것입니다:
- IDE(통합 개발 환경)에서 타입 오류 감지
- 컴파일러의 경고 메시지
- 디버깅 과정에서 버그 찾기

프로그램 분석은 이러한 작업들을 **자동화하고 체계화**하는 것입니다.

### 수식/기호/코드 설명
분석의 기본 형태:
```
분석(프로그램) → {가능한 실행 결과들}
```

예: `분석(x = if(...) { 1 } else { 2 })` → `x ∈ {1, 2}`

### 전체적인 맥락
프로그램 분석은 다양한 분야와 연관되어 있습니다:
- **컴파일러**: 코드 최적화
- **소프트웨어 공학**: 품질 관리, 리팩토링
- **보안**: 취약점 탐지
- **AI/머신러닝**: 프로그램 이해

## 슬라이드 3: 응용 - 프로그램 변환 (루프 불변 코드 이동)

### 개념 설명
**루프 불변 코드 이동(Loop-Invariant Code Motion, LICM)**은 컴파일러가 수행하는 중요한 최적화입니다. 루프 내부에서 반복되지만 결과가 매번 같은 계산을 루프 바깥으로 옮기는 최적화 기법입니다.

**최적화 전:**
```c
for (int i = 0; i < n; i++) {
    int y = a * b;  // a, b는 루프에서 변하지 않음
    result[i] = y + i;
}
```

**최적화 후:**
```c
int t = a * b;      // 루프 바깥으로 이동
for (int i = 0; i < n; i++) {
    int y = t;
    result[i] = y + i;
}
```

### 배경 지식
- **루프의 비효율**: 루프가 n번 반복될 때, 루프 내 명령어도 n번 실행됩니다.
- **성능 향상**: `a * b`는 복잡한 계산이므로, 이를 n-1번 줄이면 성능이 크게 향상됩니다.
- **안전한 최적화**: 루프 내 a, b의 값이 변하지 않음을 **증명**해야 안전하게 최적화할 수 있습니다.

### 수식/기호/코드 설명
분석이 답해야 할 질문:
```
"a * b가 루프의 모든 반복에서 항상 같은 값인가?"
```

이 질문에 "YES"라는 답을 얻으려면:
1. a의 값이 루프에서 변하지 않음
2. b의 값이 루프에서 변하지 않음
3. a * b의 부작용(side effect)이 없음

### 전체적인 맥락
이것은 프로그램 분석이 **실제로 사용되는 사례**입니다. 컴파일러는:
1. 프로그램을 분석하여 "루프 불변"인 표현식을 찾아냅니다
2. 그 표현식을 루프 밖으로 이동시킵니다
3. 실행 시간을 단축합니다

이러한 자동 최적화가 없으면 프로그래머가 모든 루프를 수동으로 최적화해야 합니다.

## 슬라이드 4: 응용 - 버그 찾기

### 개념 설명
프로그램 분석은 **프로그램을 실행하지 않고도 잠재적인 버그를 찾을 수 있습니다**. 특히 0으로 나누기, 메모리 오류, null pointer dereference 등의 오류를 사전에 탐지할 수 있습니다.

### 배경 지식
학생들이 경험한 버그 사례:
```c
int result = 10 / x;  // x가 0이면 오류!
```

동적 분석(테스트)으로 이를 찾으려면:
- x = 0인 경우를 테스트 케이스에 포함시켜야 함
- 테스트 케이스에 포함되지 않으면 버그를 놓칠 수 있음

정적 분석으로는:
- 프로그램을 실행하지 않고도 "x가 0이 될 수 있다"는 것을 발견
- 경고를 발생시켜 버그를 미리 예방

### 수식/기호/코드 설명
예시 코드:
```c
void process(int divisor) {
    if (divisor > 0) {
        int result = 100 / divisor;  // 안전
    } else {
        int result = 100 / divisor;  // 위험! 0 가능
    }
}
```

분석이 수행하는 일:
```
divisor의 가능한 범위 = {..., -2, -1, 0, 1, 2, ...}
→ 0으로 나누기 가능! → 경고 발생
```

### 전체적인 맥락
버그 찾기는 프로그램 분석의 가장 중요한 응용입니다:
- **비용 절감**: 배포 후 버그는 매우 비쌈
- **안정성 향상**: 보안 취약점, 충돌 등을 사전에 방지
- **개발 효율성**: 개발자가 수동으로 모든 경우를 고려할 필요 없음

## 슬라이드 5: 응용 - 프로그램 이해

### 개념 설명
프로그램 분석을 통해 코드를 실행하지 않고도 코드의 동작을 이해할 수 있습니다. IDE에서 제공하는 기능들(자동완성, 타입 정보, 함수 이동 등)이 모두 프로그램 분석을 기반으로 합니다.

### 배경 지식
IDE 기능의 예:
```c
int x = 5;
x.  // ← 여기서 Ctrl+Space를 누르면?
```

IDE는:
1. x의 타입이 `int`임을 분석
2. `int` 타입의 메서드/속성들을 표시
3. 자동 완성 제공

다른 예:
```java
MyClass obj = new MyClass();
obj.getData()  // ← 이 메서드를 Ctrl+클릭하면 정의로 이동
```

IDE는 마찬가지로 분석을 통해 `getData()`가 어디서 정의되었는지 찾습니다.

### 수식/기호/코드 설명
IDE 기능의 종류:
- **타입 정보**: `x: int`
- **정의로 이동**: `MyClass` → 클래스 정의 위치
- **호출 그래프**: 함수 A는 B를 호출, B는 C를 호출, ...
- **의존성 추적**: 이 함수를 변경하면 어떤 함수들이 영향을 받는가?

### 전체적인 맥락
프로그래머가 대규모 프로젝트(수백만 줄의 코드)를 이해하는 데 있어 프로그램 분석은 필수입니다:
- 수동으로 모든 함수의 정의를 추적할 수 없음
- 프로그램 분석은 이를 자동화
- 개발 생산성 크게 향상

## 슬라이드 6: 정적 분석 vs 동적 분석

### 개념 설명
프로그램 분석은 크게 두 가지로 나뉩니다:

**정적 분석(Static Analysis)**
- 프로그램을 **실행하지 않고** 분석
- 소스 코드나 바이트코드를 분석
- 모든 가능한 실행을 고려

**동적 분석(Dynamic Analysis)**
- 프로그램을 **실행하면서** 분석
- 실제 실행 중에 일어나는 일을 관찰
- 특정 입력에 대한 실행만 분석

### 배경 지식
학생들이 이미 경험한 예:
- **정적 분석**: 컴파일러의 타입 체킹, 경고
- **동적 분석**: 테스트, 프로파일링, 디버거

```c
// 컴파일 시점 (정적): 타입 오류 감지
int x = "hello";  // ← 컴파일 오류!

// 실행 시점 (동적): 실제 동작 관찰
for (int i = 0; i < 1000000; i++) {
    result[i] = expensive_function();
}
// 실행하면서 어느 함수가 시간을 많이 쓰는지 측정
```

### 수식/기호/코드 설명
분석 방식의 차이:

**정적 분석의 관점:**
```
소스 코드 → [분석 엔진] → 가능한 모든 동작들
(실행 X)
```

**동적 분석의 관점:**
```
입력 1 → [프로그램 실행] → 동작 관찰
입력 2 → [프로그램 실행] → 동작 관찰
입력 3 → [프로그램 실행] → 동작 관찰
```

### 전체적인 맥락
정적 분석과 동적 분석은 **상호 보완적**입니다:
- 정적: 모든 가능성을 고려하지만 부정확할 수 있음
- 동적: 정확하지만 테스트된 경우만 고려
- 실무에서: 둘을 함께 사용하여 품질 향상

## 슬라이드 7: 정적 분석의 장점

### 개념 설명
정적 분석은 프로그램을 실행하지 않기 때문에 여러 장점을 가집니다.

**장점 1: 종료 보장 (Termination Guaranteed)**
- 분석 자체는 항상 종료됨
- 프로그램의 무한 루프는 분석에 영향을 주지 않음

**장점 2: 입력 불필요 (No Inputs Needed)**
- 프로그램을 실행하지 않으므로 입력 데이터가 필요 없음
- 동적 분석은 항상 입력을 제공해야 함

**장점 3: 부분/미완성 프로그램 분석 가능 (Partial Programs)**
- 아직 완성되지 않은 코드도 분석 가능
- 컴파일되지 않는 코드도 분석 가능

### 배경 지식
학생들의 경험:
```c
// 이 코드는 컴파일되지 않음 (f() 미정의)
int x = f() + 1;

// 그런데도 IDE는:
// - f()의 반환 타입이 int임을 알 수 있음
// - 다른 부분의 타입을 분석할 수 있음
```

동적 분석으로는 불가능합니다. 실행을 시도하려면 f()가 정의되어야 합니다.

### 수식/기호/코드 설명
정적 분석의 특징:

```
분석(프로그램) {
    if (프로그램이 무한 루프를 가짐)
        // 정적 분석은 여전히 종료됨!
    // 분석 엔진은 항상 답을 내놈
}
```

### 전체적인 맥락
정적 분석이 실무에서 광범위하게 사용되는 이유:
- **CI/CD 파이프라인 통합**: 빌드 과정에서 자동으로 실행 가능
- **개발 초기 단계**: 아직 완성되지 않은 코드도 분석 가능
- **안정성**: 분석이 항상 종료되므로 예측 가능

## 슬라이드 8: 건전성 (Soundness)

### 개념 설명
**건전한 분석(Sound Analysis)**은 다음과 같은 성질을 가집니다:

> 분석이 "불가능하다"고 결론 내리면, **실제로 진짜 불가능**합니다.

다시 말해, 건전한 분석은 **과다 근사(Overapproximation)**를 수행합니다. 실제 가능한 모든 경우를 포함합니다.

### 배경 지식
현실의 예:
```c
int x = if (...) { 1 } else { 2 };
// 실제로 x는 1 또는 2 만 가능

// 건전한 분석:
// "x는 {1, 2, 3, 4, 5}"라고 할 수 있음 (과다 근사)
// 실제 값을 포함하므로 건전함

// 비건전한 분석:
// "x는 {1}"이라고 하면 (2를 놓침)
// 비건전함 → 위험함
```

### 수식/기호/코드 설명
건전성의 정의:

```
Sound(분석) ⟺
    분석이 제시하는 범위 ⊇ 실제 가능한 범위

// 기호 설명:
// ⊇ : "포함한다" (superset)
// 즉, 분석의 결과가 실제 결과보다 크거나 같아야 함
```

### 전체적인 맥락
건전성이 중요한 이유:

**예: 루프 불변 코드 이동**
```c
for (...) {
    y = a * b;  // 이를 루프 밖으로 꺼낼까?
}
```

- 건전한 분석: "a * b가 불변인가?" → YES만 꺼냄 (안전)
- 비건전한 분석: "아마도 불변인 것 같다" → 꺼냄 (위험!)

비건전한 분석으로 최적화하면 프로그램의 의미가 바뀔 수 있습니다.

## 슬라이드 9: 완전성 (Completeness)

### 개념 설명
**완전한 분석(Complete Analysis)**은 다음과 같은 성질을 가집니다:

> 분석이 "가능하다"고 결론 내리면, **실제로 진짜 가능**합니다.

다시 말해, 완전한 분석은 **부분 근사(Underapproximation)**를 수행합니다. 실제 가능한 것 중 일부만 보고합니다.

### 배경 지식
```c
int x = if (...) { 1 } else { 2 };

// 완전한 분석:
// "x는 {1}"이라고 할 수 있음
// x가 1이 될 수 있다는 것은 진짜 가능함

// 비완전한 분석:
// "x는 {1, 2, 3}"이라고 하면 (3은 불가능)
// 비완전함
```

### 수식/기호/코드 설명
완전성의 정의:

```
Complete(분석) ⟺
    분석이 제시하는 범위 ⊆ 실제 가능한 범위

// 기호 설명:
// ⊆ : "부분집합" (subset)
// 즉, 분석이 말하는 모든 것은 실제로 가능해야 함
```

### 전체적인 맥락
완전성이 중요한 이유:

**예: 테스팅과 동적 분석**
- 테스트를 실행하면 "x = 1인 경우"를 찾을 수 있음
- 이는 완전함: 실제로 x = 1이 되는 입력이 존재
- 그러나 x = 2인 경우를 놓쳤을 수 있음 → 비건전함 (거짓 음성)

## 슬라이드 10-11: 건전성 예제

### 개념 설명
건전성의 구체적인 예를 통해 이해해봅시다.

```c
let x = if (...) { 1 } else { 2 };
let y = x + 1;
```

### 배경 지식
이 코드에서:
- x는 정확히 {1, 2} 중 하나
- y는 정확히 {2, 3} 중 하나

### 수식/기호/코드 설명
**분석 1: 건전하고 정확**
```
분석 결과: x ∈ {1, 2}
근사: {1, 2} ⊇ {1, 2} ✓ 건전
```

**분석 2: 건전하지만 덜 정확**
```
분석 결과: x는 정수
근사: ℤ (모든 정수) ⊇ {1, 2} ✓ 건전
```

**분석 3: 비건전 (위험)**
```
분석 결과: x = 1
근사: {1} ⊄ {1, 2} ✗ 비건전 (2를 놓침)
```

### 전체적인 맥락
건전한 분석은 **거짓 음성(False Negative)이 없습니다**. 즉:
- 분석이 "불가능"이라 하면, 정말 불가능
- 분석이 "가능"이라 하면, 가능하거나 불가능할 수 있음 (거짓 양성 가능)

이것이 **최적화 기법**에 필수적인 이유입니다.

---

## 슬라이드 12-13: 완전성 예제

### 개념 설명
완전성의 구체적인 예를 살펴봅시다. 같은 코드로 분석해봅시다.

```c
let x = if (...) { 1 } else { 2 };
let y = x + 1;
```

### 배경 지식
**테스팅 (동적 분석의 예)**

테스트 케이스 1: if 조건이 참인 경우 실행
```
결과: x = 1 → 완전함 (x = 1이 정말 가능)
```

테스트 케이스 2를 놓친 경우:
```
분석 결과: x = {1}
근사: {1} ⊆ {1, 2} ✓ 완전 (1은 정말 가능)
그러나 2를 놓침 → 비건전 (거짓 음성)
```

### 수식/기호/코드 설명
완전한 분석의 특징:

```
Complete(분석) ⟹
    분석이 보고한 모든 케이스는 실제로 가능
    하지만 가능한 모든 케이스를 보고하지 않을 수 있음

거짓 양성(False Positive): 없음
거짓 음성(False Negative): 있을 수 있음
```

### 전체적인 맥락
**테스팅은 완전하지만 건전하지 않습니다:**
- 완전: 테스트를 통과한 경우는 정말 가능
- 비건전: 테스트되지 않은 경우도 실제로 있을 수 있음

이것이 테스팅만으로는 부족한 이유입니다.

---

## 슬라이드 14: 건전성 vs 완전성 비교표

### 개념 설명
두 성질을 비교하는 표입니다.

| 성질 | 정의 | 거짓 양성 | 거짓 음성 | 사용처 |
|------|------|---------|---------|--------|
| **건전 (Sound)** | "불가능" → 진짜 불가능 | 있을 수 있음 | 없음 | 최적화 |
| **완전 (Complete)** | "가능" → 진짜 가능 | 없음 | 있을 수 있음 | 테스팅 |

### 배경 지식
거짓 양성(False Positive)의 예:
```c
if (x > 0) {
    int result = 100 / x;  // 안전
} else {
    // 경고: "0으로 나누기 가능"
}
```

거짓 양성은 있지만, **거짓 음성(놓친 버그)은 없습니다**.

거짓 음성(False Negative)의 예:
```c
// 테스트에서는 x = 5인 경우만 테스트
int result = 100 / x;

// x = 0인 경우를 놓칠 수 있음
```

### 수식/기호/코드 설명
```
건전성: P(분석이 불가능 | 실제로 불가능) = 1
        즉, 실제 불가능한 것을 가능하다고 절대 하지 않음

완전성: P(분석이 가능 | 실제로 가능) = 1
        즉, 실제 가능한 것을 불가능하다고 절대 하지 않음
```

### 전체적인 맥락
이 비교를 통해 왜 정적 분석과 동적 분석이 모두 필요한지 이해할 수 있습니다.

## 슬라이드 15-17: 역사적 버그 사례

### 개념 설명
프로그램 분석이 얼마나 중요한지 실제 사례를 통해 알아봅시다.

### 사례 1: 아리안 5 로켓 (1996년)

**상황:**
- 유럽우주국(ESA)의 아리안 5 로켓 첫 발사
- 발사 73초 후 폭발

// 아리안 4에서 사용한 코드
int64_t horizontal_velocity = ...;  // 64비트
int16_t velocity_16bit = horizontal_velocity;  // 16비트로 변환

**배경 지식:**

- 6명 사망/부상

**원인:**

// 레이스 컨디션 (Race Condition)

shared int dose_setting;

// 스레드 1: dose_setting 읽음 → dose_setting 쓰기
// 스레드 2: dose_setting 읽음 → dose_setting 쓰기
// 순서가 뒤바뀌면서 예상 밖의 값 발생
```

### 사례 3: 하트블리드 (2014년)

**상황:**

- 개인 정보 노출

// 버퍼 오버리드 (Buffer Over-read)
void heartbeat(char *payload, int length) {
    char response[64];

}
```

### 수식/기호/코드 설명
이 모든 사례에서 **정적 분석이 미리 감지할 수 있었습니다**:

```
아리안 5: 정수 오버플로우 분석

테랙-25: 데이터 레이스 분석
         여러 스레드의 동시 접근 추적

하트블리드: 버퍼 오버플로우 분석
           배열 인덱스 범위 검증
```

### 전체적인 맥락
이 사례들이 중요한 이유:
- **비용**: 버그 수정 비용은 시간이 지날수록 지수적으로 증가
- **안전**: 일부 버그는 인명 피해를 초래
- **신뢰성**: 소프트웨어의 신뢰성은 경제와 안전 모두 중요

정적 분석은 이런 재앙을 예방하는 강력한 도구입니다.

## 슬라이드 18-20: 루프 불변 코드 이동 상세 예제

### 개념 설명
슬라이드 3의 루프 불변 코드 이동을 더 자세히 살펴봅시다.

```c
void compute(int a, int b, int n, int *result) {
    for (int i = 0; i < n; i++) {
        int y = a * b;
        result[i] = y + i;
    }
}
```

이 코드에서:
- `a * b`는 매 반복마다 같은 값
- 분석이 이를 확인하면 최적화 가능

### 배경 지식
**루프 불변식(Loop Invariant)의 조건:**

변수 또는 표현식 E가 루프 불변이려면:
1. E의 모든 피연산자가 루프 내에서 수정되지 않음
2. E가 사이드 이펙트(부작용)를 가지지 않음
3. E의 동작이 반복 횟수에 무관함

### 수식/기호/코드 설명
분석 과정:

```
단계 1: a, b가 루프에서 변하지 않는가? → YES
단계 2: a * b가 부작용을 가지는가? → NO
단계 3: 따라서 a * b는 루프 불변 → 꺼낼 수 있음

최적화:
int t = a * b;  // 루프 전에 계산
for (int i = 0; i < n; i++) {
    result[i] = t + i;
}
```

### 전체적인 맥락
이 분석이 중요한 이유:
- **성능**: n이 100만이면 100만 번의 곱셈 → 1번으로 줄임
- **자동화**: 프로그래머가 수동으로 최적화할 필요 없음
- **정확성**: 분석이 안전을 보장하므로 최적화 가능

## 슬라이드 21: 이상적인 경우 - 건전성과 완전성 동시 달성

### 개념 설명
**이상적인 분석은 건전하면서 완전합니다.**

즉:
- "불가능" → 진짜 불가능 (건전성)
- "가능" → 진짜 가능 (완전성)
- 거짓 양성도 없고 거짓 음성도 없음

```c
let x = if (...) { 1 } else { 2 };
// 이상적인 분석: x ∈ {1, 2} (정확함)
```

### 배경 지식
학생들이 처음 배우는 타입 시스템:
```java
int x = 5;      // x: int (정확함)
int y = x + 3;  // y: int (정확함)
```

단순한 타입 시스템은 건전하고 완전합니다!

그러나 더 복잡한 경우는 어떨까요?

### 수식/기호/코드 설명
건전하면서 완전한 분석:

```
분석(프로그램) = 실제 가능한 경우들

이 경우:
- 거짓 양성: 0개
- 거짓 음성: 0개
- 분석 결과가 정확함
```

### 전체적인 맥락
여기서 중요한 질문:
**모든 분석을 건전하면서 완전하게 만들 수 있을까?**

다음 슬라이드에서 놀라운 답을 얻게 됩니다.

## 슬라이드 22: 라이스 정리 (Rice's Theorem)

### 개념 설명
**라이스 정리(Rice's Theorem)**는 컴퓨터 과학의 기초 정리입니다:

> **Turing 완전한 언어에서 프로그램의 비자명한 성질(non-trivial property)은 모두 결정 불가능하다.**

결정 불가능(Undecidable)이란:
- 그 성질을 판정하는 알고리즘이 존재하지 않음
- 모든 입력에 대해 yes/no를 답하는 알고리즘을 만들 수 없음

### 배경 지식
학생들이 알아야 할 배경:
- **Turing 완전**: while, if 등 제어 구조가 있는 모든 현대 프로그래밍 언어
- **비자명한 성질**: "프로그램이 존재한다" 같은 자명한 성질이 아닌 모든 의미 있는 성질
- **정지 문제(Halting Problem)**: 프로그램이 무한 루프 없이 종료하는가?

### 수식/기호/코드 설명
라이스 정리의 형식:

```
P = {프로그램들의 집합}
R = P의 부분집합 (어떤 성질을 만족하는 프로그램들)

R이 비자명하면 (즉, ∅ ≠ R ≠ P):
    "주어진 프로그램이 R에 속하는가?"를 판정하는
    알고리즘이 존재하지 않는다.
```

### 전체적인 맥락
라이스 정리의 의미:
- **이론적 한계**: 프로그램 분석의 한계를 설명
- **실무적 영향**: 모든 성질을 완벽하게 분석할 수 없음
- **해결책**: 근사, 휴리스틱, 또는 건전성/완전성 중 택일

---

## 슬라이드 23: 라이스 정리 예제

### 개념 설명
라이스 정리를 구체적으로 이해해봅시다.

분석해야 할 질문:
```c
if (...) {
    f();        // f()가 종료하는가?
    x = 1;
} else {
    x = 2;
}
return x;
```

**질문**: "x = 1이 가능한가?"

### 배경 지식
이 질문을 답하려면:
1. f()가 종료하는지 판단해야 함
2. f()가 종료하면 x = 1 가능
3. f()가 무한 루프면 x = 2만 가능

그런데 f()가 종료하는가는 **정지 문제**입니다!

### 수식/기호/코드 설명
이를 정지 문제로 축소(Reduction):

```
정지 문제 해결 ⟸ "x = 1이 가능한가?" 판정

따라서 "x = 1이 가능한가?"도 결정 불가능!

더 일반적으로, 모든 비자명한 성질은
마찬가지로 결정 불가능
```

### 전체적인 맥락
이것이 의미하는 바:

**건전하고 완전한 분석은 불가능합니다!**

왜냐하면:
- 건전성: 비자명한 모든 성질 판정 필요
- 라이스 정리: 이는 불가능
- 따라서 선택해야 함: 건전성 또는 완전성

---

## 슬라이드 24: 건전성 vs 완전성: 어떤 것을 선택할 것인가?

### 개념 설명
라이스 정리로부터 우리는 다음을 알았습니다:
- 건전하면서 완전한 분석은 불가능 (일반적으로)
- 따라서 하나를 선택해야 함

**선택은 응용에 따라 다릅니다!**

### 배경 지식
두 가지 응용:
1. **의미 보존 변환 (Semantics-Preserving Transformation)**
   - 프로그램의 의미를 바꾸지 않는 최적화
   - 최적화 후에도 같은 결과

2. **버그 찾기 (Bug Finding)**
   - 잠재적 오류 탐지
   - 일부 버그를 놓쳐도 괜찮음

### 수식/기호/코드 설명
응용별 분석 특성:

```
의미 보존 변환: 건전성이 필수
    - 비건전한 최적화 → 프로그램 의미 변경
    - 이는 절대 허용 불가

버그 찾기: 완전성이 원함
    - 모든 버그를 찾고 싶음
    - 그러나 건전성도 필요 (거짓 양성 줄이기)
```

### 전체적인 맥락
실무에서:
- **컴파일러**: 건전한 분석만 사용 (의미 보존)
- **버그 탐지 도구**: 건전 + 최대한 정확 (거짓 양성 최소화)
- **테스팅**: 완전한 분석 (놓친 버그도 수용)

---

## 슬라이드 25: 의미 보존 변환을 위한 건전성

### 개념 설명
**의미 보존 변환(Semantics-Preserving Transformation)**을 위해서는 반드시 건전한 분석이 필요합니다.

코드 예제:
```c
int x;
if (some_condition) {
    x = 1;
} else {
    x = 2;
}
// 여기서 x를 사용
```

최적화 기회: if 문을 제거할 수 있을까?

### 배경 지식
**완전한 분석으로 최적화하면:**
```
분석: "x는 항상 1"
결론: else 분기 제거
최적화 코드:
    x = 1;
```

문제: 만약 some_condition이 거짓인 경우가 있으면?
→ 프로그램 의미 변경 (오류)

**건전한 분석으로 최적화하면:**
```
분석: "x는 1 또는 2"
결론: 안전하게 제거 불가
→ 원래 코드 유지
```

### 수식/기호/코드 설명
의미 보존의 조건:

```
최적화(P) =_sim P (의미 동일)

∀ 입력 i: 실행(P, i) = 실행(최적화(P), i)

이를 보장하려면:
- 분석이 건전해야 함
- 분석이 놓친 경우가 있으면 안 됨
```

### 전체적인 맥락
컴파일러에서:
- GCC, LLVM, Clang 모두 건전한 분석 사용
- 버그가 있으면 (비건전한 최적화) → 컴파일러 버그
- 매우 심각한 문제

따라서 **컴파일러는 반드시 건전한 분석만 사용합니다**.

---

## 슬라이드 26: 버그 찾기를 위한 건전성

### 개념 설명
버그 찾기에서는 건전성과 완전성 중 어떤 것이 더 중요할까요?

**정적 분석 vs 동적 분석:**
- 정적: 건전함 → 정지 문제 없음, 모든 경로 분석
- 동적: 완전함 → 테스트 케이스만 분석

### 배경 지식
**Dijkstra의 명언:**
> "Testing shows the presence, not the absence of bugs."
> (테스팅은 버그의 유무를 보여줄 뿐, 부재를 증명하지 못한다)

이것은 동적 분석(테스팅)이 완전하지만 건전하지 않다는 뜻입니다.

### 수식/기호/코드 설명
버그 찾기의 특성:

```
정적 분석:
    - 건전: 모든 가능한 오류 경로 포함
    - 장점: 모든 오류 경로를 고려
    - 단점: 거짓 양성 (불가능한 경로도 포함)

동적 분석:
    - 완전: 테스트 케이스가 정말 오류를 일으킴
    - 장점: 거짓 양성 없음
    - 단점: 거짓 음성 (테스트 안 된 경로 놓침)
```

### 전체적인 맥락
실무에서:
- **정적 분석 도구** (SpotBugs, Clang Static Analyzer): 건전 + 정확
- **동적 분석/테스팅**: 완전하지만 불완전
- **조합 사용**: 정적과 동적을 함께 사용하여 상호 보완

학과 철학: **정적 분석은 건전해야 한다**

## 슬라이드 27: 건전한 분석 설계의 과제

### 개념 설명
**건전한 분석을 설계하는 것은 매우 어렵습니다.**

왜냐하면:
1. **자명하게 건전한 분석**: 모든 가능성을 포함 → 쓸모 없음
2. **정확하고 건전한 분석**: 달성하기 어려움

### 배경 지식
예제:
```c
int x = if (...) { 1 } else { 2 };
```

**자명하게 건전하지만 쓸모 없는 분석:**
```
"x는 모든 정수이다"
// 기술적으로는 건전함 (1과 2는 정수)
// 하지만 아무 정보도 주지 않음
```

**정확하고 건전한 분석:**
```
"x는 {1, 2}"
// 건전함 + 정확함
// 실제 사용 가능
```

### 수식/기호/코드 설명
분석의 정확성(Precision):

```
정확한 분석: 분석 결과 = 실제 범위
             거짓 양성 = 0

덜 정확한 분석: 분석 결과 ⊃ 실제 범위
              거짓 양성 > 0

쓸모없는 분석: 분석 결과 = 매우 큼
             거짓 양성 = 많음
             → 사용 불가
```

### 전체적인 맥락
이 과제가 이 강의의 중심입니다:
- **쉬운 부분**: 건전한 분석 만들기
- **어려운 부분**: 정확하면서 건전한 분석 만들기
- **강의의 목표**: 이 균형을 달성하는 기법 배우기

## 슬라이드 28: 정확성 (Precision)

### 개념 설명
**정확성(Precision)**은 분석이 실제 범위에 얼마나 가까운지를 나타냅니다.

```
높은 정확성: 분석 결과가 실제 범위와 가까움
낮은 정확성: 분석 결과가 매우 큼
```

### 배경 지식
예제:
```c
int x = if (random()) { 1 } else { 2 };
int y = x + 10;
```

**정확성이 높은 분석:**
```
x ∈ {1, 2}
y ∈ {11, 12}
```

**정확성이 낮은 분석:**
```
x ∈ {1, 2, 3, 4, 5}
y ∈ {11, 12, 13, 14, 15}
```

**정확성이 매우 낮은 분석:**
```
x는 정수
y는 정수
```

### 수식/기호/코드 설명
정확성의 정의:

```
정확성(Precision) = |실제 범위| / |분석 범위|

더 정확함: 비율이 높음 (분석 범위가 작음)
덜 정확함: 비율이 낮음 (분석 범위가 큼)

극단적 예:
- 완벽: 1.0 (분석 범위 = 실제 범위)
- 나쁜: 0.01 (분석 범위가 100배 큼)
```

### 전체적인 맥락
정확성이 중요한 이유:
- **거짓 양성 감소**: 정확할수록 거짓 경고가 적음
- **쓸모성**: 너무 부정확한 분석은 무의미
- **효율성**: 너무 정확하려는 분석은 느림

---

## 슬라이드 29: 정적 분석 설계의 목표들

### 개념 설명
정적 분석을 설계할 때 고려해야 할 목표들:

**필수 목표:**
1. **종료(Termination)**: 분석이 항상 종료되어야 함
2. **건전성(Soundness)**: 분석이 건전해야 함

**추가 목표:**
3. **효율성(Efficiency)**: 분석이 빨리 끝나야 함
4. **정확성(Precision)**: 분석이 정확해야 함

### 배경 지식
목표들의 우선순위:

```
필수: 종료 + 건전성
   (이 없으면 쓸모 없음)

원하는: 효율성 + 정확성
   (이것이 있으면 실용적)
```

### 수식/기호/코드 설명
효율성과 정확성의 트레이드오프:

```
효율성과 정확성은 보통 상충:
- 더 정확한 분석 = 더 많은 계산 필요
- 더 빠른 분석 = 덜 정확

목표: 최적 지점 찾기
      효율성과 정확성의 균형
```

### 전체적인 맥락
실무에서:
- **연구**: 매우 정확한 분석 추구
- **프로덕션**: 효율성과 정확성의 균형
- **대규모 코드 분석**: 효율성 우선

## 슬라이드 30: 강의의 목표

### 개념 설명
이 강의를 통해 학생들이 배울 목표:

**목표 1: 기존 정적 분석 기법 이해**
- 타입 분석(Type Analysis)
- 구간 분석(Interval Analysis)
- Andersen 스타일 포인터 분석(Pointer Analysis)

**목표 2: 새로운 분석 설계를 위한 프레임워크 학습**
- 단일화(Unification) 기반 분석
- 단조 격자(Monotone Framework)
- 3차 솔버(Cubic Solver)

**목표 3: 건전성에 대한 이해**
- 추상 해석(Abstract Interpretation)
- 분석의 정확성과 건전성 증명

### 배경 지식
각 기법의 역할:

**타입 분석**: 변수의 타입 추론
```java
int x = 5;
String s = "hello";
// 분석: x는 int, s는 String
```

**구간 분석**: 변수의 범위 추론
```c
int x = 5;
if (x > 0) {
    // 여기서 x ∈ (0, ∞)
}
```

**포인터 분석**: 포인터가 가리키는 메모리 추론
```c
int *p = &x;
int *q = p;
// 분석: q도 x를 가리킴
```

### 수식/기호/코드 설명
추상 해석의 개념:

```
추상 도메인: 실제 값들의 집합을 대표하는 추상값
- {1, 2} → {양수}
- [0, 10] → [정수 범위]

구체적 의미론: 실제 실행
추상 의미론: 분석을 통한 근사 실행
```

### 전체적인 맥락
강의 구조:
1. **이론**: 라이스 정리, 건전성, 추상 해석
2. **기법**: 다양한 분석 알고리즘
3. **설계**: 새로운 분석을 만드는 방법
4. **실제**: 과제를 통한 구현

## 슬라이드 31: LLM 시대의 학습

### 개념 설명
Chris Lattner(Swift, LLVM 개발자)의 인용:

> "The details of correct abstractions are not something that can be Googled. You need someone who has deep understanding and experience to guide you."

올바른 추상화를 선택하는 것은 인터넷 검색으로 해결 불가능합니다. 깊은 이해가 필요합니다.

### 배경 지식
LLM(Large Language Model)의 능력과 한계:

**LLM이 잘하는 것:**
- 코드 작성/구현
- 아이디어 설명
- 문제 해결

**LLM이 못하는 것:**
- 올바른 추상화 선택
- 근본적인 설계 결정
- 복잡한 문제의 원인 파악

### 수식/기호/코드 설명
엔지니어의 책임:

```
엔지니어:
1. 의도 명확화 (Intent)
2. 결과 검증 (Validation)
3. 설계 개선 (Improvement)

LLM은 도구일 뿐 의사 결정은 엔지니어가 함
```

### 전체적인 맥락
이 강의의 철학:
- LLM 사용 권장
- 하지만 개념 이해가 먼저
- 도구를 효과적으로 사용하되, 비판적 사고 필수

## 슬라이드 32: LLM과 이 강의

### 개념 설명
이 강의에서 LLM(특히 ChatGPT, Claude 등)의 역할:

**LLM의 활용:**
- 자료 검색
- 개념 설명
- 코드 구현
- 디버깅

**LLM 사용 권장:**
- 학생들은 LLM 사용 장려
- 시간 절약 가능
- 반복 작업 자동화

**강조사항:**
1. **아이디어 이해가 우선**: 개념을 먼저 이해
2. **설계 구조 관리**: LLM이 생성한 코드를 학생이 관리
3. **결과 검증**: LLM의 출력이 맞는지 확인

### 배경 지식
학생들의 우려:
- "LLM을 쓰면 뭔가 부정행위 같은데?"
- "실제로 배울 수 있을까?"

답변:
- LLM은 도구 (계산기, IDE와 같음)
- 중요한 것은 문제를 푸는 방법을 이해하는 것
- LLM 사용 능력도 현대 엔지니어에게 필수

### 수식/기호/코드 설명
LLM을 효과적으로 사용하는 방법:

```
1. 개념 이해 (강의 듣기, 텍스트 읽기)
2. 문제 분석 (직접 생각)
3. LLM 활용 (구현, 디버깅)
4. 결과 검증 (직접 테스트)
5. 이해 확인 (왜 작동하는가?)
```

### 전체적인 맥락
미래의 엔지니어:
- 단순 구현 능력보다 문제 해결 능력 중시
- LLM 시대에는 **협력** 능력이 중요
- 이 강의는 이러한 능력 배양을 목표

## 슬라이드 33: 요약

### 개념 설명
강의의 핵심 내용을 정리합니다:

**프로그램 분석이란:**
- 프로그램을 직접 실행하지 않고 특성을 자동으로 결정하는 기법
- 컴파일러, 보안, 소프트웨어 공학 등 다양한 분야에 응용

**정적 vs 동적 분석:**
- 정적: 프로그램 코드 분석 (건전, 한계 있음)
- 동적: 프로그램 실행 분석 (완전, 테스트에만 적용)

### 배경 지식
정적 분석의 장점:
1. 종료 보장 (프로그램의 무한 루프와 무관)
2. 입력 불필요
3. 부분 프로그램 분석 가능

정적 분석의 한계:
- 라이스 정리: 비자명한 성질은 모두 결정 불가능
- 건전하면서 완전한 분석은 일반적으로 불가능
- 따라서 선택 필요: 건전성 또는 완전성

### 수식/기호/코드 설명
핵심 정의들:

```
건전성 (Sound): "불가능" → 진짜 불가능
               (거짓 음성 없음)

완전성 (Complete): "가능" → 진짜 가능
                  (거짓 양성 없음)

라이스 정리: 둘 다 달성 불가능 (일반적으로)

정해야 할 선택:
- 최적화: 건전성 (의미 보존 필수)
- 버그 찾기: 건전성 + 정확성 (거짓 경고 최소화)
```

### 전체적인 맥락
강의를 통해 배울 것:

**이론:**
- 정적 분석의 기초와 한계
- 추상 해석
- 건전성 증명

**실제:**
- 타입, 구간, 포인터 분석
- 새로운 분석 설계 방법
- 도구 구현

**목표:**
- 기존 분석 기법 이해
- 새로운 분석 설계 능력
- 정확하고 효율적인 분석 개발

## 강의 전체 요약

이 강의 1에서는 프로그램 분석의 개념적 기초를 다루었습니다:

1. **프로그램 분석의 정의와 응용**
   - 자동으로 프로그램 특성 결정
   - 최적화, 버그 찾기, 코드 이해에 사용

2. **정적 분석의 특성**
   - 장점: 종료 보장, 입력 불필요, 부분 프로그램 분석
   - 한계: 라이스 정리로 인한 결정 불가능성

3. **건전성과 완전성**
   - 건전성: 거짓 음성 없음 (최적화에 필수)
   - 완전성: 거짓 양성 없음 (완벽한 버그 찾기)
   - 일반적으로 둘을 동시에 달성 불가능

4. **응용별 선택**
   - 의미 보존 변환: 반드시 건전성
   - 버그 찾기: 건전성 + 정확성

5. **향후 강의에서**
   - 구체적인 분석 기법 학습
   - 새로운 분석 설계 방법
   - 추상 해석을 통한 건전성 증명

이 기초 위에서 나머지 강의들은 실제 분석 기법과 설계 방법론을 다룰 것입니다.
