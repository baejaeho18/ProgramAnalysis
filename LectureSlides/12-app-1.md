## 강의 12 전체 조감도 (먼저 큰 그림)

강의 1~11은 정적 분석의 **이론과 도구**를 쌓았습니다(추상화·격자·데이터플로우·위드닝·절차간·제어흐름). 강의 12부터는 그 도구들이 **실제로 어디에 쓰이는가** — 즉 **응용(application)** — 을 봅니다. 이번 강의의 무대는 강사 본인의 연구 주제인 **C-to-Rust 자동 변환**입니다.

핵심 줄거리: **C 코드를 Rust로 안전하게 바꾸려면, C에는 암묵적(implicit)으로만 존재하는 정보를 정적 분석으로 복원(infer)해야 한다.** 이번 강의는 그중 **락(lock, 뮤텍스)**의 변환에 집중합니다. C의 `pthread_mutex_lock/unlock`은 "어떤 락이 어떤 데이터를 보호하는지", "어느 지점에서 어떤 락이 잡혀 있는지"가 코드에 드러나지 않습니다. Rust의 `Mutex`/`MutexGuard`는 이 관계를 **타입으로 명시**하므로, 변환하려면 그 숨은 관계를 분석으로 알아내야 합니다.

이를 위해 **두 개의 데이터플로우 분석**을 설계합니다 — 둘 다 강의 7~8에서 배운 고전 분석의 변형입니다:
1. **Live Guard Analysis** = Live Variable Analysis의 변형 (후방·may): 함수 진입 시 잡혀 있을 수 있는 락
2. **Available Guard Analysis** = Available Expression Analysis의 변형 (전방·must): 함수 반환 시 반드시 잡혀 있는 락

그리고 **함수 요약(function summary)**과 **상향식(bottom-up) 모듈러 분석**(강의 10의 functional 접근), **재귀의 고정점 반복**으로 절차간으로 확장합니다.

이 강의는 "지금까지 배운 모든 것(데이터플로우+격자+절차간+요약)이 실전 한 문제에서 어떻게 합쳐지는가"를 보여 주는 **종합 응용편**입니다.

## 슬라이드 2: C-to-Rust Translation

### 원문 내용

> - Legacy system programs developed in C suffer from various security vulnerabilities because C does not ensure safety at language level
> - Rust ensures memory/thread safety by detecting critical bugs at compile time through type checking
> - C-to-Rust translation can improve the reliability of legacy systems by discovering previously unknown bugs and preventing new bugs in advance

### 번역

> - C로 개발된 레거시 시스템 프로그램들은 다양한 보안 취약점에 시달린다. C는 언어 차원에서 안전성을 보장하지 않기 때문이다
> - Rust는 타입 검사를 통해 치명적 버그를 **컴파일 타임에** 탐지함으로써 메모리/스레드 안전성을 보장한다
> - C-to-Rust 변환은 이전에 알려지지 않은 버그를 발견하고 새 버그를 미리 방지함으로써 레거시 시스템의 신뢰성을 높일 수 있다

### 해설

**개념 설명 — 왜 C를 Rust로?**

C는 빠르고 어디서나 돌지만, **메모리 안전성(memory safety)**과 **스레드 안전성(thread safety)**을 언어가 보장하지 않습니다. 버퍼 오버플로, use-after-free, 데이터 레이스 같은 버그가 컴파일러를 통과해 런타임에 보안 취약점이 됩니다. 운영체제·네트워크 스택 등 오래된(legacy) C 코드가 보안 사고의 단골인 이유죠.

**Rust**는 같은 수준의 성능을 내면서, **소유권(ownership)·빌림(borrowing)** 타입 시스템(강의 2 복습)으로 이런 버그를 **컴파일 타임에 거부**합니다. 그래서 "기존 C를 Rust로 자동 변환하면, 변환 과정에서 숨은 버그도 드러나고 앞으로의 버그도 막을 수 있다"는 것이 연구 동기입니다.

**슬라이드 연결**

그런데 자동 변환은 쉽지 않습니다 — 그 이유가 슬라이드 3입니다.

## 슬라이드 3: Challenges in C-to-Rust Translation

### 원문 내용

> - Rust requires more information to be explicitly stated in source code, compared to C, so that the compiler can utilize the information
> - To translate C to Rust, such information should be inferred
> - Static analysis can identify necessary information

### 번역

> - Rust는 C에 비해 더 많은 정보를 소스 코드에 **명시적으로** 적도록 요구한다. 컴파일러가 그 정보를 활용할 수 있도록 하기 위해서다
> - C를 Rust로 변환하려면, 그런 정보를 **추론(infer)**해야 한다
> - 정적 분석이 그 필요한 정보를 알아낼 수 있다

### 해설

**개념 설명 — 이번 강의의 핵심 논리**

Rust가 안전한 비결은 "프로그래머가 의도를 **타입으로 명시**하고, 컴파일러가 그것을 검사"하기 때문입니다. 반대로 C는 그 의도가 **코드에 적히지 않고 프로그래머 머릿속에만** 있습니다. 따라서 C→Rust 변환의 본질은:

> **C에 암묵적인 정보를 정적 분석으로 복원해, Rust의 명시적 형태로 채워 넣는 것.**

이 한 문장이 강의 12~13 전체를 관통하는 아이디어입니다. "정적 분석은 무엇에 쓰는가?"라는 질문에 대한 구체적 답이기도 합니다.

**슬라이드 연결**

그러면 구체적으로 어떤 정보들을 복원해야 할까요? 슬라이드 4가 목록입니다.

## 슬라이드 4: Static Analysis for C-to-Rust Translation

### 원문 내용

> - Each language feature of Rust requires distinct kinds of information
> - Static analysis specialized for each language feature is required
>   - Locks¹
>   - Output parameters²
>   - Unions³
>   - I/O⁴
>
> ---
> ¹ Concrat: An automatic C-to-Rust lock API translator for concurrent programs (Hong and Ryu, 2023)
> ² Don't write, but return: Replacing output parameters with algebraic data types in C-to-Rust translation (Hong and Ryu, 2024)
> ³ To tag, or not to tag: Translating C's unions to Rust's tagged unions (Hong and Ryu, 2024)
> ⁴ Forcat: Automatic I/O API translation from C to Rust via origin and capability analysis (Hong and Ryu, 2025)

### 번역

> - Rust의 각 언어 기능은 서로 다른 종류의 정보를 요구한다
> - 각 언어 기능에 특화된 정적 분석이 필요하다
>   - 락(Locks)¹
>   - 출력 매개변수(Output parameters)²
>   - 공용체(Unions)³
>   - 입출력(I/O)⁴
>
> (각주는 각 주제를 다룬 실제 논문들 — 강사 본인의 연구)

### 해설

**개념 설명**

복원해야 할 정보가 Rust 기능마다 다르므로, 기능별로 **특화된 분석**을 만듭니다. 슬라이드의 네 항목은 각각 별도 논문이 된 연구 주제입니다:
- **Locks** (이번 강의): C의 뮤텍스를 Rust `Mutex`/`MutexGuard`로. 어떤 락이 어떤 데이터를 보호하고, 어디서 잡혀 있는지를 복원.
- **Output parameters** (다음 강의 13에서 다룸): C에서 포인터 인자로 결과를 "써서 돌려주는" 패턴을, Rust의 반환값/대수적 자료형으로.
- **Unions**: C의 태그 없는 공용체를 Rust의 태그 있는 enum으로.
- **I/O**: C의 파일/스트림 API를 Rust API로.

각주의 논문 제목들은 시험에 나올 내용은 아니지만, "정적 분석이 실제 연구·도구로 어떻게 이어지는가"를 보여 줍니다. **이번 강의는 첫 항목 Locks에 집중**합니다.

**슬라이드 연결**

슬라이드 5부터 본격적으로 "C의 락"이 무엇이고 왜 문제인지 봅니다.

## 슬라이드 5: Locks in C

### 원문 내용

> ```c
> pthread_mutex_t m = ...;
> int n = 0;
>
> pthread_mutex_lock(&m);
> n = n + 1;
> pthread_mutex_unlock(&m);
> ```
> - Each shared data is protected by a lock
> - A thread acquires and releases the lock before and after accessing the data

### 번역

> 코드: 뮤텍스 `m`과 공유 정수 `n`이 있고, `lock(&m)`으로 락을 잡은 뒤 `n`을 수정하고 `unlock(&m)`으로 락을 푼다.
> - 각 공유 데이터는 하나의 락으로 보호된다
> - 스레드는 데이터에 접근하기 **전후로** 락을 획득(acquire)하고 해제(release)한다

### 해설

**배경 지식 — 락과 데이터 레이스**

여러 스레드가 동시에 같은 데이터를 건드리면 **데이터 레이스(data race)**가 나서 결과가 깨집니다. 이를 막으려고 **뮤텍스(mutual exclusion lock)**를 씁니다: 한 번에 한 스레드만 `lock`을 잡을 수 있고, 그 동안만 데이터를 만지고, 끝나면 `unlock`. C에서는 이 약속(`m`이 `n`을 보호한다)이 **코드 어디에도 적혀 있지 않습니다** — 프로그래머가 지켜야 할 관례일 뿐입니다.

**슬라이드 연결**

이 "적혀 있지 않음"이 어떤 문제를 낳는지 슬라이드 6~8이 보여 줍니다.

## 슬라이드 6: Problem with Locks in C

### 원문 내용

> - Implicit data-lock relation (which lock protects which data)
> - Implicit flow-lock relation (which locks is held at which program point)
> - The compiler does not detect programmers' mistake

### 번역

> - **암묵적 데이터-락 관계**: 어떤 락이 어떤 데이터를 보호하는가
> - **암묵적 흐름-락 관계**: 어떤 락이 어느 프로그램 지점에서 잡혀 있는가
> - 컴파일러가 프로그래머의 실수를 탐지하지 못한다

### 해설

**개념 설명 — 두 가지 숨은 관계 (이번 강의의 키워드)**

C 락의 문제는 두 관계가 **암묵적**이라는 것입니다. 이 두 용어는 강의 끝까지 계속 나옵니다:

1. **데이터-락 관계(data-lock relation)**: "락 `m`은 데이터 `n`을 보호한다"는 짝짓기. 코드에 안 적혀 있음.
2. **흐름-락 관계(flow-lock relation)**: "프로그램의 이 지점에서는 락 `m`이 잡혀 있다"는, 제어 흐름을 따라가며 추적해야 하는 상태. 역시 코드에 안 적혀 있음.

C 컴파일러는 이 둘을 모르므로, 프로그래머가 **엉뚱한 락을 잡거나(슬라이드 7) 타이밍을 틀려도(슬라이드 8)** 잡아 주지 못합니다.

**슬라이드 연결**

이 두 종류의 실수를 슬라이드 7과 8이 각각 예시합니다. 그리고 이 두 관계를 복원하는 것이 강의 후반의 두 분석(흐름-락 → guard 분석들, 데이터-락 → 슬라이드 34)의 목표입니다.

## 슬라이드 7: Potential Data Race (1)

### 원문 내용

> ```c
> pthread_mutex_t m1 = ..., m2 = ...;
> int n1 = 0, n2 = 0;
>
> pthread_mutex_lock(&m1);
> n2 = n2 + 1;
> pthread_mutex_unlock(&m1);
> ```
> - Programmers may acquire the wrong lock

### 번역

> 코드: 두 락 `m1`, `m2`와 두 데이터 `n1`, `n2`가 있는데, `n2`를 수정하면서 `m1`을 잡았다(원래 `n2`를 보호하는 락은 `m2`여야 할 텐데).
> - 프로그래머가 **엉뚱한 락**을 잡을 수 있다

### 해설

**개념 설명 — 데이터-락 관계 위반**

`n2`는 `m2`로 보호되어야 하는데 실수로 `m1`을 잡았습니다. 그러면 다른 스레드가 `m2`를 잡고 `n2`를 건드릴 때 **동시에** 이 코드도 `n2`를 건드려 데이터 레이스가 납니다. C 컴파일러는 "이 락이 이 데이터를 보호한다"는 관계를 모르니 경고도 없습니다. 이것이 **데이터-락 관계의 실수**입니다.

## 슬라이드 8: Potential Data Race (2)

### 원문 내용

> ```c
> pthread_mutex_t m = ...;
> int n = 0;
>
> pthread_mutex_lock(&m);
> ...
> pthread_mutex_unlock(&m);
> n = n + 1;
> ```
> - Programmers may acquire or release the lock at the wrong timing

### 번역

> 코드: 락을 풀고 **난 뒤에** `n`을 수정한다(보호 구간 밖에서 접근).
> - 프로그래머가 락을 **잘못된 타이밍에** 획득/해제할 수 있다

### 해설

**개념 설명 — 흐름-락 관계 위반**

`unlock` 이후에 `n = n + 1`을 합니다 — 즉 **락이 풀린 상태**에서 공유 데이터를 만집니다. 보호 구간을 벗어난 접근이므로 역시 데이터 레이스 위험. 여기서 문제는 "어느 지점에서 어떤 락이 잡혀 있는가"라는 **흐름-락 관계**입니다. 이걸 추적하려면 제어 흐름을 따라가는 데이터플로우 분석이 필요합니다(슬라이드 15·17의 두 guard 분석이 정확히 이 일을 합니다).

**슬라이드 연결**

슬라이드 7(데이터-락 실수)과 8(흐름-락 실수)은 슬라이드 6의 두 암묵적 관계에 정확히 대응합니다. 이제 Rust가 이를 어떻게 명시적으로 만드는지(슬라이드 9~11) 봅니다.

## 슬라이드 9: Locks in Rust

### 원문 내용

> ```rust
> let mut m = Mutex::new(0);
>
> let mut guard = m.lock().unwrap();
> *guard = *guard + 1;
> drop(guard);
> ```
> - A lock is a protected container for shared data
>   - Rust lock = C lock + data
> - A guard is a special pointer to the shared data
>   - A guard is constructed only by acquiring the lock
>   - When a guard is destructed, the lock is released

### 번역

> 코드: `Mutex::new(0)`으로 **0이라는 데이터를 품은** 뮤텍스 `m`을 만든다. `m.lock()`으로 잠그면 `guard`(가드)를 얻고, `*guard`로 안의 데이터에 접근한다. `drop(guard)`로 가드를 버리면 락이 풀린다.
> - 락은 **공유 데이터를 담는 보호된 컨테이너**다 — 즉 **Rust 락 = C 락 + 데이터**
> - 가드(guard)는 공유 데이터를 가리키는 **특수한 포인터**다
>   - 가드는 **락을 획득해야만** 만들어진다
>   - 가드가 소멸되면 **락이 해제**된다

### 해설

**개념 설명 — Rust가 두 관계를 타입으로 강제하는 법**

Rust의 `Mutex<T>`는 **락과 데이터를 하나로 묶습니다**(`Mutex::new(0)`은 정수 0을 *품은* 락). 그래서 **데이터-락 관계가 타입에 박혀** 있습니다 — `n`에 접근하려면 반드시 그 `n`을 품은 락을 거쳐야 합니다(엉뚱한 락을 잡을 수가 없음, 슬라이드 7 문제 해결).

데이터에 접근하려면 `m.lock()`으로 **가드(guard)**를 얻어야 합니다. 가드는:
- **락을 잡아야만 생긴다** (가드 존재 = 락 보유 중).
- **소멸되면 락이 풀린다** (가드를 `drop`하거나 스코프를 벗어나면 자동 unlock — RAII⁵).

따라서 "지금 락이 잡혀 있는가" = "가드가 살아 있는가"가 되어, **흐름-락 관계가 가드의 수명(lifetime)으로** 표현됩니다(슬라이드 8 문제 해결).

**각주**

⁵ **RAII (Resource Acquisition Is Initialization)**: 자원(락)의 획득을 객체(가드)의 생성과, 해제를 소멸과 묶는 패턴. 강의 2의 Rust 소유권/`Drop`과 직접 연결됩니다. 가드는 소유권 규칙을 따르므로, 컴파일러가 "가드가 살아 있는 동안만 데이터 접근 가능"을 정적으로 보장합니다.

**슬라이드 연결**

이 설계 덕분에 슬라이드 6의 두 암묵적 관계가 슬라이드 10에서 "명시적"으로 바뀝니다.

## 슬라이드 10: Advantages of Rust Locks

### 원문 내용

> - Explicit data-lock relation
> - Explicit flow-lock relation
> - The compiler can detect programmers' mistake

### 번역

> - **명시적** 데이터-락 관계
> - **명시적** 흐름-락 관계
> - 컴파일러가 프로그래머의 실수를 탐지할 수 있다

### 해설

**개념 설명**

슬라이드 6의 정확한 반대입니다. Rust에서는 두 관계가 모두 **타입으로 명시**되므로:
- 데이터-락: 락이 데이터를 품으니 짝이 고정 → 엉뚱한 락 불가.

그래서 컴파일러가 실수를 잡아 줍니다(슬라이드 11에서 실제 거부 예).

**슬라이드 연결**

이 "명시성" 덕분에 C→Rust 변환이 가치 있지만(버그를 드러냄), 동시에 변환기가 그 명시 정보를 **C로부터 복원**해야 한다는 숙제가 생깁니다(슬라이드 12~).

## 슬라이드 11: Data Race Prevented

### 원문 내용

> ```rust
> let mut m = Mutex::new(0);
>
> let mut guard = m.lock().unwrap();
> ...
> drop(guard);
> *guard = *guard + 1;
> ```
> - The compiler rejects the program because guard is not owned in the last line

### 번역

> 코드: 가드를 `drop`한 **뒤에** `*guard`로 데이터에 접근하려 한다.
> - 컴파일러는 이 프로그램을 **거부**한다. 마지막 줄에서 `guard`가 (이미 버려져) 소유되고 있지 않기 때문이다

### 해설

**개념 설명**

슬라이드 8의 C 버그(unlock 후 접근)를 Rust로 옮기면 **컴파일 에러**가 납니다. `drop(guard)` 후 `guard`는 무효(moved/dropped)이므로 `*guard` 접근은 소유권 규칙 위반. 즉 "락 풀린 뒤 데이터 접근"이 **타입 시스템 차원에서 불가능**합니다. C에서는 조용히 통과하던 버그가 Rust에서는 드러나는 것 — 슬라이드 2의 "previously unknown bugs를 발견"이 이렇게 실현됩니다.

**슬라이드 연결**

여기까지가 "왜 Rust 락이 좋은가". 슬라이드 12부터는 "그럼 C를 Rust로 바꾸려면 무엇을 분석해야 하는가"(=변환의 도전 과제)로 넘어갑니다.

## 슬라이드 12: Challenges in Translating Locks — Data-Lock Relations

### 원문 내용

> ```c
> pthread_mutex_t a = ..., b = ...;
> int x = 0;
> float y = 0.0f;
> double z = 0.0;
> ```
> - The data-lock relations must be decided

### 번역

> 코드: 두 락 `a`, `b`와 세 데이터 `x`, `y`, `z`가 따로따로 선언되어 있다.
> - (변환하려면) **데이터-락 관계를 결정해야 한다**

### 해설

**개념 설명**

Rust로 바꾸려면 "각 데이터를 어느 락의 컨테이너 안에 넣을지" 정해야 합니다. 예컨대 `a`가 `x`를, `b`가 `y`,`z`를 보호한다면 `Mutex<i32>`(=a+x), `Mutex<(f32,f64)>`(=b+y,z) 식으로 묶어야죠. 하지만 C 코드에는 이 짝이 안 적혀 있으니 **분석으로 추론**해야 합니다. 그 방법이 슬라이드 34("어떤 락이 잡혀 있을 때만 데이터에 접근하면, 그 락이 그 데이터를 보호한다")입니다.

## 슬라이드 13: Challenges in Translating Locks — Flow-Lock Relations

### 원문 내용

> 왼쪽 (C):
> ```c
> void inc() {
>   n = n + 1;
> }
>
> pthread_mutex_lock(&m);
> inc();
> pthread_mutex_unlock(&m);
> ```
> 오른쪽 (Rust):
> ```rust
> fn inc(mut g: MutexGuard<i32>) -> MutexGuard<i32> {
>   *g = *g + 1;
>   g
> }
>
> let mut guard = m.lock().unwrap();
> guard = inc(guard);
> drop(guard);
> ```
> - The flow-lock relations must be decided
>   - Which functions should take guards
>   - Which functions should return guards

### 번역

> C에서는 `inc()`가 전역 `n`을 수정하고, 호출 전후로 `m`을 잠그고 푼다. Rust에서는 `inc`가 **가드 `g`를 인자로 받아** 데이터를 수정하고 **가드를 다시 반환**해야 한다(`guard = inc(guard)`).
> - **흐름-락 관계를 결정해야 한다**
>   - 어떤 함수가 가드를 **인자로 받아야** 하는가
>   - 어떤 함수가 가드를 **반환해야** 하는가

### 해설

**개념 설명 — 절차간으로 번지는 흐름-락 관계**

C에서 `inc()`는 "호출자가 락을 잡은 상태"라는 걸 암묵적으로 전제합니다. Rust에서는 데이터(`n`) 접근이 가드를 거쳐야 하므로, `inc`는 **가드를 인자로 받아야** 합니다. 그리고 호출 후에도 호출자가 계속 락을 써야 하면(여기선 `drop`하므로) 가드를 **반환**해 돌려줘야 합니다(가드는 소유권 이동 대상이라 그냥 넘기면 호출자가 잃어버림).

즉 "함수 진입 시 어떤 락이 잡혀 있나 → 그 가드를 인자로", "함수 반환 시 어떤 락이 잡혀 있나 → 그 가드를 반환"을 결정해야 합니다. 이것이 **흐름-락 관계의 절차간 버전**이고, 정확히 슬라이드 15(진입 시 락 = live guard)·17(반환 시 락 = available guard)의 두 분석이 푸는 문제입니다.

**슬라이드 연결**

이제 이 두 가지(진입 시·반환 시 잡힌 락)를 어떻게 분석하는지가 슬라이드 14~의 본론입니다.

## 슬라이드 14: Static Analysis for Lock Translation

### 원문 내용

> - Unsound analysis
>   - Do not consider pointer aliasing
>   - When locks are aliased, the results can be unsound
> - Bottom-up modular analysis
>   - Each function is analyzed once to create a function summary
>   - A callee is analyzed before its caller is analyzed
>   - Analyzing a caller requires the callees' function summaries
> - Two analyses per function
>   - First, live guard analysis
>   - Then, available guard analysis

### 번역

> - **불건전한(unsound) 분석**
>   - 포인터 앨리어싱(aliasing)을 고려하지 않는다
>   - 락이 앨리어스되면 결과가 불건전할 수 있다
> - **상향식(bottom-up) 모듈러 분석**
>   - 각 함수를 한 번 분석해 **함수 요약(function summary)**을 만든다
>   - 호출되는 함수(callee)를 호출하는 함수(caller)보다 **먼저** 분석한다
>   - caller를 분석하려면 callee들의 함수 요약이 필요하다
> - **함수당 두 개의 분석**
>   - 먼저 live guard analysis
>   - 그 다음 available guard analysis

### 해설

**개념 설명 — 분석의 세 가지 설계 결정**

1. **불건전(unsound)을 의도적으로 허용**: 보통 정적 분석은 건전성(soundness, 과근사)을 목표로 하지만(강의 5~9), 이 변환 도구는 **포인터 앨리어싱을 무시**합니다. 두 포인터가 같은 락을 가리킬 수 있는 경우(앨리어스)를 추적하지 않아, 그런 코드에선 틀릴 수 있습니다.⁶ 실용적 도구에서 "완벽한 건전성 대신 단순함·실용성"을 택한 사례 — 정밀도/비용/건전성의 트레이드오프(강의 10의 주제)를 보여 줍니다.
2. **상향식 모듈러 분석**: 절차간 분석(강의 10)의 **함수 요약(functional/summary)** 접근. 각 함수를 딱 한 번 분석해 "요약"을 만들고, **callee를 먼저** 분석해 그 요약을 caller가 가져다 씁니다(호출 그래프의 역순, 잎→뿌리).
3. **함수당 두 분석을 순서대로**: 먼저 live guard(진입 시 락), 그 다음 available guard(반환 시 락). available 분석이 live 분석 결과를 진입 상태로 쓰기 때문에 순서가 정해집니다(슬라이드 17).

**각주**

⁶ **앨리어싱(aliasing)**: 서로 다른 이름(포인터)이 같은 메모리를 가리키는 현상. 정확히 추적하려면 포인터 분석(강의 14~15)이 필요한데, 비싸고 복잡합니다. 이 도구는 그걸 생략해 단순·빠르게 가는 대신 건전성을 일부 포기했습니다. "왜 unsound를 감수하나?"는 시험에서 트레이드오프를 묻기 좋은 지점.

**슬라이드 연결**

두 분석의 정의가 각각 슬라이드 15(live)·17(available)입니다. 둘 다 강의 7~8의 고전 데이터플로우 분석의 변형이라는 점에 주목하세요.

## 슬라이드 15: Live Guard Analysis — Definition

### 원문 내용

> - Goal: to decide locks that may be held at the function entry
> - Similar to live variable analysis (backward, may)
> - State = (𝒫(LockVar), ⊆)
>   - Locks to be released in the future
> - JOIN(v) = ⋃_{u∈succ(v)} ⟦u⟧
> - `return`: ⟦v⟧ = ∅
> - `pthread_mutex_unlock(x)`: ⟦v⟧ = JOIN(v) ∪ {x}
> - `pthread_mutex_lock(x)`: ⟦v⟧ = JOIN(v) \ {x}

### 번역

> - 목표: 함수 **진입 시점에 잡혀 있을 수 있는(may be held)** 락들을 결정
> - **Live variable analysis와 유사**하다 (후방·may)
> - 상태 = (락 변수들의 멱집합 𝒫(LockVar), 부분집합 순서 ⊆)
>   - 의미: "**앞으로(미래에) 해제될** 락들"
> - JOIN(v) = v의 모든 **후속(successor)** 노드 u의 분석값 ⟦u⟧의 **합집합(∪)**
> - 전이 함수:
>   - `return`: ⟦v⟧ = ∅ (반환 지점에선 미래에 풀 락이 없음)
>   - `unlock(x)`: ⟦v⟧ = JOIN(v) ∪ {x} (이 지점 이후 x가 풀리므로, 이 지점에선 x가 잡혀 있던 것)
>   - `lock(x)`: ⟦v⟧ = JOIN(v) \ {x} (이 지점에서 x를 잡으므로, 진입 쪽에선 x가 아직 안 잡혀 있음)

### 해설

**개념 설명 — Live Variable Analysis의 데자뷔**

이 분석은 강의 7~8의 **Live Variable Analysis(살아있는 변수 분석)**를 락에 맞춰 베낀 것입니다. 대응을 보면 한눈에 들어옵니다:
- 후방(backward): 정보가 **출구에서 입구로** 흐름 → JOIN이 **후속자(successor)**들의 합집합.
- may(가능성): "잡혀 있을 **수 있는**" → 격자 순서가 ⊆(합집합 join), 작을수록 정밀.
- 상태의 의미: "**미래에 unlock될 락**" = "지금 잡혀 있는 락"(잡혔으니 미래에 풀릴 것). 그래서 진입 노드의 값이 곧 "진입 시 잡힌 락".

전이 함수를 **거꾸로(뒤에서 앞으로)** 읽어야 합니다:
- `return`에서 시작: 더 이상 풀 락 없음 → ∅.
- `unlock(x)`를 **뒤에서** 만나면: 이 줄 다음(미래)엔 x가 풀린 상태지만, **이 줄 앞(=이 노드)**에서는 x가 아직 잡혀 있어야 풀 수 있음 → `∪ {x}` (x를 켠다).
- `lock(x)`를 **뒤에서** 만나면: 이 줄에서 x를 잡으므로, **이 줄 앞**에서는 x가 아직 안 잡힌 상태 → `\ {x}` (x를 끈다).

직관: 거꾸로 가면서 unlock은 "여기 위쪽엔 이 락이 켜져 있었네" 표시를 켜고, lock은 끕니다. 함수 맨 앞까지 거슬러 올라가 켜진 채로 남은 락이 = **진입 시 잡혀 있던 락**.

**각주**

⁷ 왜 "may"이고 ⊆/∪인가? 분기에서 한쪽 경로로만 락이 잡혀 와도 "잡혀 있을 수 있다"고 봐야 안전(보호 누락을 막음). 그래서 경로 합류 시 **합집합**으로 모읍니다. (대조: 슬라이드 17의 available은 "must"라 교집합.)

**슬라이드 연결**

추상적 정의를 슬라이드 16이 구체 예제로 확인합니다.

## 슬라이드 16: Live Guard Analysis — Examples

### 원문 내용

> **Example 1**
> ```c
> void foo() {
>   // { m }
>   pthread_mutex_unlock(&m);
>   // {}
> }
> ```
> **Example 2**
> ```c
> void foo() {
>   // {}
>   pthread_mutex_lock(&m);
>   // { m }
>   n = n + 1;
>   // { m }
>   pthread_mutex_unlock(&m);
>   // {}
> }
> ```

### 번역

> 주석 `// {...}`은 그 지점에서 live guard 분석값(앞으로 풀릴 = 지금 잡힌 락).
> - **예제 1**: `unlock(&m)`만 있는 함수. unlock 직전은 `{m}`(곧 m을 푸니 지금 잡혀 있던 것), 직후는 `{}`. → **진입 시 `{m}`**: 이 함수는 진입 때 m이 잡혀 있다고 가정.
> - **예제 2**: `lock` → 접근 → `unlock`. 거꾸로 보면 끝은 `{}`, unlock 위는 `{m}`, lock 위는 `{}`. → **진입 시 `{}`**: 이 함수는 스스로 락을 잡고 풀므로 진입 때 잡힌 락 없음.

### 해설

**개념 설명 — 거꾸로 읽기 연습**

각 줄의 주석을 **아래에서 위로** 채워 봅시다.

예제 1 (unlock만):
- 함수 끝(return): `{}`.
- `unlock(&m)` 적용: `JOIN(={}) ∪ {m} = {m}`. 그래서 unlock **위쪽=진입**은 `{m}`.
- **해석**: 이 함수는 진입 시 m이 이미 잡혀 있어야 정상 동작(자기가 잡지 않고 풀기만 하니까). → 변환 시 **m의 가드를 인자로 받아야** 함.

예제 2 (lock·접근·unlock):
- 끝: `{}` → `unlock` 위: `{m}` → `n=n+1` 위: `{m}`(대입은 락 안 건드림) → `lock` 위: `{m}\{m}={}`. 진입 `{}`.
- **해석**: 자기 완결적(self-contained). 진입 때 잡힌 락 없음 → 가드 인자 불필요.

**슬라이드 연결**

같은 두 예제를 슬라이드 17~18의 available 분석으로도 풀어 "반환 시 잡힌 락"을 구하고, 둘을 합쳐 함수 요약(슬라이드 21)을 만듭니다.

## 슬라이드 17: Available Guard Analysis — Definition

### 원문 내용

> - Goal: to decide locks that must be held at the function return
> - Similar to available expression analysis (forward, must)
> - State = (𝒫(LockVar), ⊇)
>   - Locks whose guards are already available
> - JOIN(v) = ⋂_{u∈pred(v)} ⟦u⟧
> - entry: ⟦v⟧ = the result of live guard analysis
> - `pthread_mutex_lock(x)`: ⟦v⟧ = JOIN(v) ∪ {x}
> - `pthread_mutex_unlock(x)`: ⟦v⟧ = JOIN(v) \ {x}

### 번역

> - 목표: 함수 **반환 시점에 반드시 잡혀 있는(must be held)** 락들을 결정
> - **Available expression analysis와 유사**하다 (전방·must)
> - 상태 = (𝒫(LockVar), 역포함 순서 ⊇)
>   - 의미: "이미 **사용 가능한(available)** 가드를 가진 락들" = 이미 잡혀 있는 락
> - JOIN(v) = v의 모든 **선행(predecessor)** 노드 u의 ⟦u⟧의 **교집합(∩)**
> - 진입(entry): ⟦v⟧ = **live guard 분석의 결과** (진입 시 잡힌 락)
> - 전이 함수:
>   - `lock(x)`: ⟦v⟧ = JOIN(v) ∪ {x} (여기서 x를 잡았으니 이후 x가 available)
>   - `unlock(x)`: ⟦v⟧ = JOIN(v) \ {x} (여기서 x를 풀었으니 이후 x는 더 이상 available 아님)

### 해설

**개념 설명 — Available Expression Analysis의 데자뷔**

이번엔 강의 7~8의 **Available Expression Analysis(사용 가능 식 분석)**의 변형입니다:
- 전방(forward): 정보가 **입구에서 출구로** 흐름 → JOIN이 **선행자(predecessor)**들의 교집합.
- must(필연): "반드시 잡혀 있는" → 격자 순서 ⊇(교집합 meet). 분기 합류 시 **양쪽 모두에서** 잡힌 락만 남김.
- 상태 의미: "이미 가드를 확보한(잡혀 있는) 락".

전이 함수는 **앞에서 뒤로** 자연스럽게 읽습니다:
- 진입값 = **live 분석 결과**(슬라이드 16에서 구한 "진입 시 잡힌 락"). ★두 분석을 잇는 다리★ — available은 live의 출력을 입력으로 받습니다(그래서 슬라이드 14의 "먼저 live, 그 다음 available" 순서).
- `lock(x)`: x를 잡았으니 이후 available에 추가 `∪{x}`.
- `unlock(x)`: x를 풀었으니 제거 `\{x}`.

함수의 **반환 노드 값**이 곧 "반환 시 반드시 잡힌 락" → 변환 시 **반환해야 할 가드**.

**왜 must·교집합인가**: "반환 시 반드시 잡혀 있다"고 하려면 **모든** 경로에서 잡혀 있어야 함 → 교집합. 한 경로에서라도 안 잡혀 있으면 "반드시"가 깨짐. (대조: live는 may·합집합.)

**배경 지식 — 4분면 정리 (강의 7~8 핵심 복습)**

| | may (∪, ⊆) | must (∩, ⊇) |
|---|---|---|
| **forward** | Reaching Definitions | **Available Expr ↔ Available Guard** |
| **backward** | **Live Variable ↔ Live Guard** | Very Busy Expr |

이 강의의 두 분석이 고전 4분면의 대각선 두 칸(backward-may, forward-must)을 정확히 차지합니다. **"새 분석을 만들 때 고전 분석의 틀을 빌린다"**는 것이 이 강의의 큰 교훈입니다.

**슬라이드 연결**

슬라이드 18은 예제 1·2의 available 값을, 슬라이드 19~20은 분기가 있는 예제 3을 다룹니다.

### 번역

예제 2는 잡고 풀어 균형이 맞으므로 반환 시 `{}`. live(진입 `{}`)와 available(반환 `{}`)을 합치면 "진입·반환 모두 빈" 자기완결 함수임을 알 수 있습니다.

## 슬라이드 20: Available Guard Analysis — Example 3 Analysis

### 원문 내용

> **Live guard analysis**
> ```c
> void foo() {
>   // { m }
>   if (...) {
>     // { m }
>     pthread_mutex_unlock(&m);
>     // {}
>     ...
>     // {}
>     pthread_mutex_lock(&m);
>     // {}
>   } else {
>     // {}
>     ...
>     // {}
>   }
>   // {}
> }
> ```
> **Available guard analysis**
> ```c
> void foo() {
>   // { m }
>   if (...) {
>     // { m }
>     pthread_mutex_unlock(&m);
>     // {}
>     ...
>     // {}
>     pthread_mutex_lock(&m);
>     // { m }
>   } else {
>     // { m }
>     ...
>     // { m }
>   }
>   // { m }
> }
> ```

### 번역

> 같은 코드에 두 분석을 적용한 결과.
> - **Live (후방·may)**: 진입 `{m}`(then 가지 첫 unlock 때문에 진입에 m이 잡혀 있어야). then 가지 끝의 `lock` 위로 거슬러 올라가면 `{}`가 되고, 합류·진입까지 `{m}`은 then 경로의 unlock에서만 켜짐.
> - **Available (전방·must)**: 진입 `{m}`(live 결과). then 가지: unlock 후 `{}`, 다시 lock 후 `{m}`. else 가지: 내내 `{m}`. 두 가지 합류 시 **교집합** `{m}∩{m}={m}` → 반환 `{m}`.

### 해설

**개념 설명 — 같은 코드, 다른 답 (may vs must의 정수)**

두 분석의 진입은 똑같이 `{m}`이지만(available이 live 결과를 받으므로), **반환에서 갈립니다**. 핵심은 then 가지에서 m을 "풀었다 다시 잡아" 결국 `{m}`로 끝나고, else는 `{m}` 그대로 → **두 경로 모두 반환 직전 `{m}`**. available은 교집합이라 `{m}`을 유지합니다.

**해석**: 이 함수는 진입 시 m이 잡혀 있고(→ 가드를 **인자로** 받음), 반환 시에도 m이 잡혀 있음(→ 가드를 **반환**함). then 가지에서 잠깐 풀었다 다시 잡는 것은 안에서만 일어나고 경계(진입·반환)에는 영향 없음. 변환된 Rust `foo`는 `fn foo(g: MutexGuard) -> MutexGuard` 시그니처가 됩니다.

만약 then 가지가 lock 없이 unlock만 했다면 반환이 `{}∩{m}=∅`이 되어 "반드시 잡혀 있다"가 깨졌을 것 — must·교집합의 보수성을 보여 줍니다.

**슬라이드 연결**

여기까지가 **한 함수 내부(intraprocedural)** 분석. 슬라이드 21부터는 **함수 호출을 넘는(interprocedural)** 처리 — 함수 요약과 상향식 분석입니다(강의 10 연결).

## 슬라이드 21: Analyzing Function Calls — Function Summary

### 원문 내용

> - Function summary: locks held at the entry and return
> ```c
> void lock() {
>   pthread_mutex_lock(&m);
> }
> ```
> Entry: {}, Return: {m}
> ```c
> void unlock() {
>   pthread_mutex_unlock(&m);
> }
> ```
> Entry: {m}, Return: {}

### 번역

> - **함수 요약(function summary)**: 함수의 **진입 시·반환 시 잡혀 있는 락들**
> - `lock()` 함수: 진입 `{}`, 반환 `{m}` (m을 잡고 끝남)
> - `unlock()` 함수: 진입 `{m}`, 반환 `{}` (m이 잡힌 채 들어와 풀고 끝남)

### 해설

**개념 설명 — 함수를 (진입, 반환) 한 쌍으로 압축**

절차간으로 확장하는 비결은 각 함수를 **두 집합의 요약** `(Entry, Return)`으로 압축하는 것입니다. Entry는 live 분석으로(진입 시 잡힌 락), Return은 available 분석으로(반환 시 잡힌 락) 구합니다. 이 요약만 있으면, 그 함수를 호출하는 쪽은 **내부를 다시 안 봐도** "이 함수는 진입에 이만큼 잡혀 있길 요구하고, 반환에 이만큼 남긴다"를 압니다.

이것이 강의 10의 **functional/summary 기반 절차간 분석**의 구체적 사례입니다. 함수 본문을 매 호출마다 재분석하지 않으니 효율적(모듈러).

**슬라이드 연결**

이 요약을 호출 지점에서 어떻게 쓰는가가 슬라이드 22의 제약 규칙입니다.

## 슬라이드 22: Analyzing Function Calls — Constraint Rules

### 원문 내용

> **Live guard analysis**
> - `f()`: ⟦v⟧ = (JOIN(v) \ {locks held at f's return}) ∪ {locks held at f's entry}
>
> **Available guard analysis**
> - `f()`: ⟦v⟧ = (JOIN(v) \ {locks held at f's entry}) ∪ {locks held at f's return}

### 번역

> 함수 호출 `f()`를 만났을 때의 전이 함수:
> - **Live (후방)**: ⟦v⟧ = (JOIN(v)에서 **f의 반환 시 잡힌 락**을 빼고) **f의 진입 시 잡힌 락**을 더함
> - **Available (전방)**: ⟦v⟧ = (JOIN(v)에서 **f의 진입 시 잡힌 락**을 빼고) **f의 반환 시 잡힌 락**을 더함

### 해설

**개념 설명 — 호출을 "lock/unlock의 일반화"로 보기**

함수 호출 `f()`는 사실 슬라이드 15·17의 `lock(x)`/`unlock(x)` 전이를 **일반화**한 것입니다. 단일 락 하나가 아니라 "f의 진입 요구 집합"과 "f의 반환 잔여 집합"을 한꺼번에 다룰 뿐입니다.

- **Available(전방, 앞→뒤로 읽기)**: 호출 직전 상태 JOIN(v)에서, f가 진입 때 **소비(잡혀 있길 요구)**하는 락을 빼고, f가 반환 때 **남기는** 락을 더함. 즉 "f를 통과하면 진입 요구 락 → 반환 잔여 락으로 바뀐다". (단일 `lock(x)`은 진입{}, 반환{x}인 함수로 보면 `\{} ∪ {x} = ∪{x}`로 슬라이드 17과 일치.)
- **Live(후방, 뒤→앞으로 읽기)**: 거꾸로. 호출 이후 상태에서 f의 반환 락을 빼고 진입 락을 더해, 호출 **이전**(진입 쪽) 상태를 만듦. (단일 `unlock(x)`은 진입{x}, 반환{}인 함수 → `\{} ∪ {x}`로 슬라이드 15의 unlock과 일치.)

이렇게 호출을 요약으로 치환하니, caller 분석이 callee 내부를 안 보고도 진행됩니다.

**슬라이드 연결**

슬라이드 23이 이 규칙으로 실제 호출 예제를 풉니다.

### 원문 내용

> ```c
> void foo() {
>   // {}
>   lock();
>   // { m }
>   n = n + 1;
>   // { m }
>   unlock();
>   // {}
> }
> ```

### 번역

> `foo`가 `lock()`(요약: 진입{}, 반환{m})과 `unlock()`(요약: 진입{m}, 반환{})을 호출.

### 해설

**개념 설명**

`lock()`/`unlock()` 호출이 마치 원시 `pthread_mutex_lock`/`unlock`처럼 동작합니다 — 슬라이드 22 규칙에 각 함수의 요약을 대입하면 슬라이드 16·18의 직접 lock/unlock 예제와 똑같은 결과(진입{}, 반환{})가 나옵니다. **요약이 함수의 락 동작을 정확히 대체**함을 보여 주는 확인용 예제입니다.

## 슬라이드 24: Analyzing Recursive Functions

### 원문 내용

> - When a function is recursive, its own summary is not available yet
> - Solution: initially analyze the function with a bottom summary (entry: {}, return: LockVar) and iterate until a fixed point is reached

### 번역

> - 함수가 재귀적이면, 그 함수 자신의 요약이 **아직 준비되지 않았다**
> - 해법: 처음엔 **바닥(bottom) 요약**(진입: `{}`, 반환: **LockVar** = 모든 락)으로 시작해, **고정점에 도달할 때까지 반복**한다

### 해설

**개념 설명 — 재귀와 고정점 반복**

상향식 분석은 "callee 먼저"가 원칙인데, 재귀(`foo`가 `foo`를 호출)에선 자기 요약이 필요한데 그게 지금 만들고 있는 것이라 순환에 빠집니다. 해법은 **고정점 반복**(강의 6·9의 핵심 아이디어):
1. 일단 **바닥 요약**으로 가정하고 시작. 여기서 바닥은 격자의 ⊥:
   - 진입 `{}` (live 격자 ⊆에서 가장 작은 = ∅),
   - 반환 `LockVar`(=모든 락) (available 격자 ⊇에서 가장 작은 원소는 전체집합 — 역포함 순서이므로 전체집합이 ⊥)⁸.
2. 이 가정으로 함수를 분석해 **새 요약**을 얻고, 가정을 갱신.
3. 요약이 더 안 바뀔 때까지(고정점) 반복.

**각주**

⁸ available의 격자 순서가 ⊇(역포함)임을 떠올리세요(슬라이드 17). 그 순서에서 "가장 작은 원소(⊥)"는 **전체집합 LockVar**입니다(모든 집합을 ⊇로 포함하는 가장 보수적 출발점). live는 ⊆라서 ⊥=∅. 양쪽 다 "격자의 바닥에서 시작해 위로 올라가며 고정점을 찾는다"는 강의 6의 Kleene 반복과 동일.

**슬라이드 연결**

슬라이드 25~30이 이 반복을 두 가지 재귀 예제로 손수 돌려 봅니다.

## 슬라이드 26: Recursive Example 1 — Iteration 1

### 원문 내용

> Initial summary: entry = {}, return = LockVar
>
> **Live guard analysis** (주석)
> ```c
> void foo(int n) {
>   // { m }
>   if (n <= 0) {
>     // { m }
>     pthread_mutex_unlock(&m);
>     // {}
>   } else {
>     // {}
>     foo(n - 1);
>     // {}
>   }
> }
> ```
> **Available guard analysis** (주석)
> ```c
> void foo(int n) {
>   // { m }
>   if (n <= 0) {
>     // { m }
>     pthread_mutex_unlock(&m);
>     // {}
>   } else {
>     // { m }
>     foo(n - 1);
>     // LockVar
>   }
> }
> ```
> Updated summary: entry = {m}, return = {}

### 번역

> 초기 요약 가정: 진입 `{}`, 반환 `LockVar`(모든 락).
> - **Live(후방)**: then 가지는 unlock 때문에 위가 `{m}`. else 가지의 `foo(n-1)` 호출은 (초기 요약 진입{}·반환 LockVar 사용) → 호출 위가 `{}`. 합류·진입 `{m}`.
> - **Available(전방)**: 진입 `{m}`(방금 live가 준 값). then: unlock 후 `{}`. else: `foo(n-1)` 호출 시 요약(진입{}, 반환 LockVar) 적용 → `({m}\{}) ∪ LockVar = LockVar`. 두 가지 합류 **교집합** `{} ∩ LockVar = {}`. 반환 `{}`.
> - **갱신된 요약: 진입 {m}, 반환 {}**.

### 해설

**개념 설명 — 1차 반복**

바닥 요약으로 시작했지만, 한 번 분석하니 벌써 **참값(진입{m}, 반환{})**이 나왔습니다. 핵심 장면:
- available의 else 가지에서 `foo(n-1)` 호출에 **아직 바닥인 반환 LockVar**가 흘러나오지만,
- then 가지(`{}`)와 **교집합**하면서 `{} ∩ LockVar = {}`로 정리되어, 바닥의 영향이 사라집니다.

이렇게 교집합(must)이 보수적 바닥값(LockVar)을 걸러 냅니다.

**슬라이드 연결**

갱신된 요약이 정말 고정점인지 슬라이드 27이 한 번 더 돌려 확인합니다.

## 슬라이드 27: Recursive Example 1 — Iteration 2

### 원문 내용

> **Live / Available** (둘 다 주석)

### 번역

2차 반복에서 `foo(n-1)` 호출이 이제 **참 요약(진입{m}, 반환{})**을 쓰는데, 결과 요약이 또 (진입{m}, 반환{})로 같습니다. **더 안 바뀌므로 고정점**입니다. 직관(슬라이드 25의 "결국 락을 푼다")과 일치하는 정답에 두 번 만에 도달했습니다.

## 슬라이드 29: Recursive Example 2 — Iteration 1

### 원문 내용

> Initial summary: entry = {}, return = LockVar

**개념 설명**

## 슬라이드 31: Mutual Recursion

### 원문 내용

> - Start with a bottom summary for each function in the cycle
> - Analyze each function with the same summaries and update their summaries
> - Finish when all summaries reach their fixed point

### 번역

> - 순환(cycle)에 속한 **각 함수**에 대해 바닥 요약으로 시작
> - **같은 요약 집합**으로 각 함수를 분석하고 요약들을 갱신
> - 모든 요약이 각자의 고정점에 도달하면 종료

### 해설

**개념 설명 — 상호 재귀의 동시 고정점**

`f`가 `g`를, `g`가 `f`를 호출하는 상호 재귀에서는 어느 하나를 먼저 끝낼 수 없습니다. 그래서 **순환에 속한 함수들을 한 묶음으로** 보고, 모두 바닥 요약에서 출발해 **동시에** 반복 갱신합니다(전체 요약 튜플의 고정점). 이는 슬라이드 11(강의 11)의 cubic 알고리즘에서 사이클을 한 노드로 합치던 발상, 그리고 강의 10의 상호재귀 호출 그래프 처리와 통하는 아이디어입니다.

**배경 지식**: 실제로는 호출 그래프의 **강한 연결 요소(SCC)** 단위로 묶어, SCC 안은 고정점 반복, SCC 사이는 위상 순서로 상향식 처리합니다.

**슬라이드 연결**

지금까지는 callee 요약이 caller로 올라가는 **상향식(bottom-up)** 흐름. 그런데 반대 방향 정보(호출 지점의 락 상태가 callee로 내려감)도 필요합니다 — 슬라이드 32.

## 슬라이드 32: Propagating Call-Site Information

### 원문 내용

> - Locks held at call sites should be considered in callees
> - A single top-down pass after the bottom-up analysis

### 번역

> - **호출 지점에서 잡혀 있는 락**들이 callee(피호출 함수) 안에서도 고려되어야 한다
> - 상향식 분석 **이후에** 단 한 번의 **하향식(top-down)** 패스를 수행

### 해설

**개념 설명 — 두 방향의 정보 흐름**

상향식(bottom-up) 분석은 "각 함수가 진입/반환에 무슨 락을 요구·잔여하는가"라는 **요약**을 잎→뿌리로 올렸습니다. 하지만 변환을 완성하려면 그 반대 정보도 필요합니다: **"이 함수가 실제 호출될 때 호출자 쪽에서 어떤 락이 이미 잡혀 있나"**. 예컨대 `inc()`가 항상 m이 잡힌 채 호출된다면, `inc` 본문 안에서도 m이 available하다고 봐야 변환이 맞습니다.

그래서 상향식이 끝난 뒤 **하향식(top-down) 패스 한 번**으로, 호출 지점의 락 상태를 callee로 내려보냅니다. (상향식으로 요약을 다 구해 놨으니 하향은 한 번이면 충분.)

**슬라이드 연결**

구체 예가 슬라이드 33입니다.

## 슬라이드 33: Propagating Call-Site Information — Example

### 원문 내용

> (왼쪽 → 오른쪽 변화)
> ```c
> void inc() {            void inc() {
>   // {}                   // { m }
>   n = n + 1;             n = n + 1;
>   // {}                   // { m }
> }                       }
>
> void foo() {           void foo() {
>   // {}                   // {}
>   pthread_mutex_lock(&m); pthread_mutex_lock(&m);
>   // { m }                // { m }
>   inc();                 inc();
>   // { m }                // { m }
>   pthread_mutex_unlock(&m); pthread_mutex_unlock(&m);
>   // {}                   // {}
> }                       }
> ```
> m is held at every call site of inc

### 번역

> 상향식만 했을 때 `inc`는 진입·반환 모두 `{}`로 보였지만(왼쪽), `inc`의 **모든 호출 지점에서 m이 잡혀 있으므로**(foo가 lock 후 inc 호출), 하향식 패스로 `inc` 내부도 `{m}`로 갱신(오른쪽).

### 해설

**개념 설명**

`inc` 자체는 락을 건드리지 않아 상향식 요약상 "진입{} 반환{}"입니다. 하지만 `inc`는 항상 m이 잡힌 채 불립니다(`foo`가 lock 후 호출). 하향식 패스가 이 호출 지점 정보를 `inc` 안으로 내려, `inc` 본문에서 `n` 접근 시 m이 available함을 채웁니다(오른쪽 `// {m}`). 이 정보가 있어야 변환기가 "`inc`는 m 가드를 인자로 받아야 한다"(슬라이드 13)고 결정할 수 있습니다.

**조건**: 모든 호출 지점에서 **공통으로(교집합)** 잡힌 락만 내려보낼 수 있습니다. 한 곳에서라도 안 잡혀 있으면, callee가 그 가드를 인자로 받는다고 단정할 수 없으니까요(must 성질).

**슬라이드 연결**

흐름-락 관계(진입·반환·내부 락 상태)는 이렇게 다 복원됐습니다. 남은 하나, **데이터-락 관계**가 슬라이드 34입니다.

## 슬라이드 34: Deciding Data-Lock Relations

### 원문 내용

> - If data is accessed only when a certain lock is held, it is considered to be protected by the lock

### 번역

> - 어떤 데이터가 **특정 락이 잡혀 있을 때만** 접근된다면, 그 데이터는 그 락에 의해 보호된다고 간주한다

### 해설

**개념 설명 — 데이터-락 관계 복원의 원리**

슬라이드 6의 두 암묵 관계 중 둘째(데이터-락)를 복원합니다. 원리는 단순·직관적: 프로그램 전체에서 데이터 `n`에 접근하는 모든 지점을 보고, **그때마다 항상 잡혀 있던 락**을 찾으면 그것이 `n`의 보호자입니다. (흐름-락 분석으로 이미 "각 지점에서 잡힌 락"을 알므로, 그것과 데이터 접근을 교차하면 됨.)

여러 락이 후보면 보통 모든 접근에서 공통으로 잡힌 것을, 없으면 보호자 미정(변환 곤란/unsound 가능). 이 추론으로 "락 m + 데이터 n"을 Rust `Mutex<...>`로 묶을 짝이 정해집니다.

**슬라이드 연결**

데이터-락(슬라이드 34)과 흐름-락(슬라이드 15~33)이 모두 복원됐으니, 이제 실제 **변환 규칙**(슬라이드 35)과 예제(36)로 마무리합니다.

## 슬라이드 35: Translation Rules

### 원문 내용

> - When m protects n:
>   - Merge m and n into a single Rust lock
>   - `pthread_mutex_lock`: call lock and assigns to m_guard
>   - `pthread_mutex_unlock`: drop m_guard
>   - n: *m_guard
> - When m is held at the entry:
>   - Take m_guard as a parameter
> - When m is held at the return:
>   - Return m_guard

### 번역

> - **m이 n을 보호할 때** (데이터-락):
>   - m과 n을 하나의 Rust 락 `Mutex`로 병합
>   - `pthread_mutex_lock` → `lock()` 호출 후 `m_guard`에 대입
>   - `pthread_mutex_unlock` → `m_guard`를 `drop`
>   - `n` 접근 → `*m_guard` (가드를 통한 접근)
> - **m이 진입 시 잡혀 있을 때** (흐름-락, live 결과):
>   - `m_guard`를 **매개변수로 받음**
> - **m이 반환 시 잡혀 있을 때** (흐름-락, available 결과):
>   - `m_guard`를 **반환**

### 해설

**개념 설명 — 분석 결과 → 코드 변환의 사전(dictionary)**

지금까지의 모든 분석이 이 변환 규칙표 하나로 수렴합니다. 각 규칙이 어느 분석에서 왔는지 보세요:
- **데이터-락 관계(슬라이드 34)** → m·n 병합, lock/unlock/접근의 가드화.
- **live guard(슬라이드 15·요약 진입)** → 진입 시 잡힌 락의 가드를 **매개변수**로(슬라이드 13의 첫째 질문 "어떤 함수가 가드를 받아야?"의 답).
- **available guard(슬라이드 17·요약 반환)** → 반환 시 잡힌 락의 가드를 **반환**(슬라이드 13의 둘째 질문 "어떤 함수가 가드를 반환?"의 답).

즉 **두 guard 분석의 출력이 함수 시그니처를, 데이터-락 분석이 락 구조를 결정**합니다.

## 슬라이드 36: Translation Example

### 원문 내용

> 왼쪽 (C):
> ```c
> pthread_mutex_t m = ...;
> int n = 0;
> void inc() {
>   n = n + 1;
> }
> pthread_mutex_lock(&m);
> inc();
> pthread_mutex_unlock(&m);
> ```
> 오른쪽 (Rust):
> ```rust
> let mut m: Mutex<i32> = Mutex::new(0);
> fn inc(mut g: MutexGuard<i32>) -> MutexGuard<i32> {
>   *g = *g + 1;
>   g
> }
> let mut guard = m.lock().unwrap();
> guard = inc(guard);
> drop(guard);
> ```

### 번역

> C 코드(왼쪽)를 분석 결과에 따라 Rust(오른쪽)로 변환한 전체 예.
> - `m`과 `n` 병합 → `Mutex<i32>::new(0)`
> - `inc`는 m이 진입·반환에 잡힌 채 호출되므로 → 가드 `g`를 받고 반환하는 시그니처, `n` 접근은 `*g`
> - `lock` → `m.lock().unwrap()`을 `guard`에, 호출은 `guard = inc(guard)`(가드 넘기고 돌려받기), `unlock` → `drop(guard)`

### 해설

**개념 설명 — 모든 조각이 맞춰지는 순간**

이 예제는 강의 전체의 결론입니다.
- 데이터-락(슬라이드 34): `inc`가 n에 접근할 때 항상 m이 잡혀 있음(슬라이드 33의 하향식으로 확인) → m이 n 보호 → `Mutex<i32>` 병합.
- `inc`의 흐름-락: 진입 `{m}`, 반환 `{m}`(하향식 정보 반영) → `fn inc(g: MutexGuard) -> MutexGuard`.
- 본문 lock/unlock/접근: 규칙대로 `m.lock()`/`drop`/`*g`로 치환.

결과는 슬라이드 13에서 미리 본 그 Rust 코드입니다 — 그때는 "이렇게 돼야 한다"였고, 이제 "분석으로 이렇게 만든다"가 완성됐습니다.

## 슬라이드 37: Summary

### 원문 내용

> - C-to-Rust translation can improve legacy systems' reliability, but Rust demands information to be inferred from C code
> - Lock translation must recover both data-lock and flow-lock relations that are implicit in C
> - Live guard analysis (backward, may) computes locks held at function entry; available guard analysis (forward, must) computes locks held at return
> - Function summaries enable bottom-up modular analysis; recursive functions are handled by fixed-point iteration from a bottom summary

### 번역

> - C-to-Rust 변환은 레거시 시스템의 신뢰성을 높일 수 있지만, Rust는 C 코드로부터 정보를 **추론**하길 요구한다
> - 락 변환은 C에 암묵적인 **데이터-락 관계와 흐름-락 관계를 모두 복원**해야 한다
> - **Live guard 분석(후방·may)**은 진입 시 잡힌 락을, **available guard 분석(전방·must)**은 반환 시 잡힌 락을 계산한다
> - **함수 요약**이 상향식 모듈러 분석을 가능케 하고, 재귀 함수는 **바닥 요약에서 시작하는 고정점 반복**으로 처리한다

### 해설

**전체 정리 — 강의 12의 한 장 요약**

1. **동기**: C는 락의 두 관계(데이터-락·흐름-락)가 암묵적 → Rust로 안전 변환하려면 정적 분석으로 복원해야(슬라이드 2~13).
2. **두 분석**: live guard(=live variable, 후방·may)로 진입 락, available guard(=available expr, 전방·must)로 반환 락(슬라이드 15~20). available은 live 결과를 진입값으로 받음.
3. **절차간 확장**: 함수 요약(진입,반환) + 상향식 모듈러, 재귀는 바닥 요약 고정점 반복, 상호재귀는 SCC 동시 반복, 마지막에 하향식 한 패스로 호출 지점 정보 전파(슬라이드 21~33).
4. **변환**: 데이터-락 추론(슬라이드 34) + 두 guard 결과 → Rust 시그니처·구조 결정(슬라이드 35~36).

**다른 강의와의 연결 (파일 간 연결성)**

- ← **강의 2 (Rust)**: `Mutex`/`MutexGuard`, 소유권·`Drop`(RAII)이 두 관계를 타입으로 강제하는 기반.
- ← **강의 5~6 (격자·고정점)**: 두 분석의 상태가 멱집합 격자(⊆ vs ⊇), 재귀는 ⊥에서 출발하는 Kleene 고정점 반복.
- ← **강의 7~8 (데이터플로우)**: live guard ↔ Live Variable, available guard ↔ Available Expression. 4분면(forward/backward × may/must)의 직접 응용.
- ← **강의 10 (절차간)**: 함수 요약 = functional/summary 접근, 상향식 모듈러, 재귀·상호재귀 처리.
- ← **강의 11 (제어 흐름/호출 그래프)**: 상향식은 호출 그래프의 역위상 순서, 상호재귀는 SCC 처리.
- → **강의 13 (응용 2)**: 같은 "암묵 정보를 분석으로 복원" 패러다임을 다른 Rust 기능(출력 매개변수 등)에 적용.

이 강의의 가장 큰 교훈: **새로운 분석은 무에서 만드는 게 아니라, 고전 분석(live/available)의 틀을 빌려 도메인(락)에 맞게 변형하고, 절차간 기법(요약·고정점)으로 확장하는 것**입니다.

## 마치며

강의 12는 이 과목에서 배운 거의 모든 도구 — 격자, 데이터플로우 4분면, 고정점 반복, 절차간 요약, 호출 그래프 — 가 **하나의 실전 문제(C 락의 Rust 변환)**에서 어떻게 합쳐지는지 보여 준 종합 응용편입니다. 핵심 한 줄: **"C의 암묵적 데이터-락·흐름-락 관계를, live/available guard 분석과 함수 요약으로 복원해 Rust의 명시적 타입으로 채워 넣는다."** 시험에서는 (1) 주어진 함수에 두 guard 분석을 손으로 돌려 요약 구하기, (2) 재귀 함수의 고정점 반복 추적, (3) live=may·available=must인 이유 서술이 단골입니다.
