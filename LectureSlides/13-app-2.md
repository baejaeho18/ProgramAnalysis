## 슬라이드 2: Output Parameters in C

### 원문 내용
> - An output parameter is a pointer-type parameter used for producing output, rather than for taking input
> - Widely used in C to implement
>   - Functions that return multiple values
>   - Partial functions (functions that may fail)

### 번역
> - **출력 매개변수(output parameter)**란, 입력을 받기 위해서가 아니라 **출력을 만들어 내기 위해** 쓰이는 포인터 타입 매개변수다
> - C에서 다음을 구현하는 데 널리 쓰인다:
>   - **여러 값을 반환**하는 함수
>   - **부분 함수(partial function)** — 실패할 수 있는 함수

### 해설

**개념 설명**

C 함수는 반환값(return)을 **하나**만 가질 수 있습니다. 그래서 결과를 여럿 돌려주거나, "성공/실패" 같은 추가 정보를 주고 싶을 때, **포인터 인자에 결과를 써넣는** 우회법을 씁니다. 이 포인터 인자가 **출력 매개변수**입니다. 입력처럼 생겼지만(인자 자리) 실제로는 출력 통로죠.

두 용도:
- **여러 값 반환**: 예) 나눗셈에서 몫과 나머지를 둘 다 돌려주기.
- **부분 함수**: 실패 가능한 함수에서, 반환값은 성공/실패 표시로 쓰고 진짜 결과는 출력 매개변수로.

**슬라이드 연결**: 두 용도의 구체 코드가 슬라이드 3(여러 값)·4(부분 함수)입니다.

## 슬라이드 3: Multiple Return Values

### 원문 내용
> ```c
> int div(int n, int m, int *q) {
>   *q = n / m;
>   return n % m;
> }
> ```
> - The quotient is written to the output parameter q
> - The remainder is produced as the return value

### 번역
> 코드: `div`는 몫 `n/m`을 출력 매개변수 `*q`에 써넣고, 나머지 `n%m`을 반환값으로 돌려준다.
> - 몫은 출력 매개변수 `q`에 쓰인다
> - 나머지는 반환값으로 생산된다

### 해설
한 함수가 **몫과 나머지 두 값**을 돌려주는 전형적 패턴입니다. 반환값(나머지) 하나로는 부족하니, 몫은 `*q`에 써서 호출자에게 전달합니다. `q`가 출력 매개변수.

## 슬라이드 4: Partial Functions

### 원문 내용
> ```c
> int div(int n, int m, int *q) {
>   if (m == 0) {
>     return -1;
>   }
>   *q = n / m;
>   return 0;
> }
> ```
> - The quotient is written to the output parameter q
> - The return value signifies success or failure

### 번역
> 코드: `m==0`(0으로 나눔)이면 `-1`을 반환(실패), 아니면 몫을 `*q`에 쓰고 `0`을 반환(성공).
> - 몫은 출력 매개변수 `q`에 쓰인다
> - **반환값은 성공/실패를 나타낸다**

### 해설

**개념 설명 — 부분 함수와 에러 코드**

**부분 함수(partial function)**는 일부 입력에서 정의되지 않는(실패하는) 함수입니다. 여기서 `m==0`이면 나눗셈이 불가능하므로 실패. C 관례는 반환값을 **에러 코드**(0=성공, 음수=실패)로 쓰고, 진짜 결과(몫)는 출력 매개변수로 분리합니다. 이 패턴이 슬라이드 5에서 말하는 "에러 나기 쉬움"의 근원입니다.

**슬라이드 연결**: 이 방식의 문제점이 슬라이드 5, 그 위험을 보여 주는 예가 슬라이드 6.

## 슬라이드 5: Disadvantages of Output Parameters

### 원문 내용
> - Output parameters do not directly violate memory safety, but undermine readability
>   - Parameters are primarily intended for input, not output
>   - Pointer-type parameters can be used for input, returning multiple values, or partial functions, which can be confusing
> - Partial functions implemented with output parameters are especially error-prone
>   - Programmers may forget to check the return value

### 번역
> - 출력 매개변수는 메모리 안전성을 직접 침해하진 않지만, **가독성을 해친다**
>   - 매개변수는 본래 입력용인데 출력에 쓰임
>   - 포인터 매개변수가 입력·다중 반환·부분 함수 등 여러 의미로 쓰여 혼란스러움
> - 출력 매개변수로 구현한 부분 함수는 **특히 에러를 일으키기 쉽다**
>   - 프로그래머가 **반환값(에러 코드) 확인을 잊을 수 있다**

### 해설

**개념 설명**

출력 매개변수는 메모리를 깨뜨리진 않지만(포인터가 유효하다면), **의도가 불명확**합니다. 포인터 인자만 보고는 그게 입력인지 출력인지, 실패 가능 함수인지 알 수 없죠. 특히 부분 함수에서 **프로그래머가 반환값(에러 코드) 검사를 깜빡하면**, 실패했는데도 출력 매개변수의 (쓰이지 않은 쓰레기) 값을 사용하는 버그가 납니다. 슬라이드 6이 바로 그 장면.

## 슬라이드 6: Example (Good vs Bad)

### 원문 내용
> ```c
> int div(int n, int m, int *q) {
>   if (m == 0) { return -1; }
>   *q = n / m;
>   return 0;
> }
> ```
> **Good:**
> ```c
> if (div(n, m, &x) == 0) {
>   // use x
> }
> ```
> **Bad:**
> ```c
> div(n, m, &x);
> // use x
> ```

### 번역
> - **좋은 코드**: 반환값이 0(성공)인지 확인한 뒤에만 `x`를 사용.
> - **나쁜 코드**: 반환값을 확인하지 않고 곧장 `x`를 사용 → 실패 시 `x`는 초기화 안 된 쓰레기 값일 수 있음.

### 해설

**개념 설명**

같은 `div`를 호출해도, "나쁜 코드"는 에러 코드를 무시해 **실패 시 미초기화 변수 `x`를 읽는** 버그를 냅니다. 컴파일러는 막아 주지 않습니다 — 반환값 무시가 합법이니까요. 이것이 출력 매개변수 + 에러 코드 방식의 근본 위험이고, Rust의 `Result`/`Option`이 해결하는 지점입니다(슬라이드 12: 패턴 매칭이 실패 처리를 강제).

**슬라이드 연결**: Rust의 대안(ADT)이 슬라이드 7부터.

## 슬라이드 7: ADTs in Rust

### 원문 내용
> - Among diverse algebraic data types (ADTs), tuples, Option, and Result are especially useful
>   - Multiple return values and partial functions can be implemented with these types

### 번역
> - 다양한 **대수적 자료형(ADT)** 중에서도 **튜플(tuple), `Option`, `Result`**가 특히 유용하다
>   - 다중 반환값과 부분 함수를 이 타입들로 구현할 수 있다

### 해설

**배경 지식 — 대수적 자료형(ADT)**

**ADT(algebraic data type)**는 다른 타입들을 곱(product)·합(sum)으로 조합한 타입입니다.
- **튜플 `(A, B)`** = 곱 타입: A와 B를 **동시에** 담음 → 다중 반환에 적합.
- **`Option<T>`** = `Some(T)` 또는 `None`의 합 타입: "값이 있거나 없음" → 단순 실패(부가 정보 없음)에 적합.
- **`Result<T, E>`** = `Ok(T)` 또는 `Err(E)`의 합 타입: "성공값 T 또는 에러값 E" → 에러 정보가 필요한 실패에 적합.

이 셋이 C 출력 매개변수의 두 용도(다중 반환·부분 함수)를 **타입 안전하게** 대체합니다.

**슬라이드 연결**: 각각의 사용이 슬라이드 8(튜플)·9(Option)·10(Result).

## 슬라이드 8: Multiple Return Values (Rust 튜플)

### 원문 내용
> ```rust
> fn div(n: i32, m: i32) -> (i32, i32) {
>   (n / m, n % m)
> }
> ```
> - The quotient and the remainder are returned as a tuple

### 번역
> 코드: `div`가 `(몫, 나머지)` **튜플**을 직접 반환.
> - 몫과 나머지를 튜플로 반환한다

### 해설
슬라이드 3의 C 코드(출력 매개변수 + 반환값)를 Rust로 옮기면, 출력 매개변수가 사라지고 **둘 다 반환값(튜플)**이 됩니다. 시그니처 `-> (i32, i32)`만 봐도 "두 값을 돌려준다"가 명확 — 가독성↑.

## 슬라이드 9: Partial Functions with Option

### 원문 내용
> ```rust
> fn div(n: i32, m: i32) -> Option<i32> {
>   if m == 0 {
>     None
>   } else {
>     Some(n / m)
>   }
> }
> ```
> - The quotient is returned as an Option
> - None signifies failure, while Some contains the quotient on success

### 번역
> 코드: `m==0`이면 `None`(실패), 아니면 `Some(몫)`(성공)을 반환.
> - 몫을 `Option`으로 반환한다
> - `None`은 실패를, `Some`은 성공 시 몫을 담는다

### 해설
슬라이드 4의 부분 함수를 `Option`으로. 에러 코드(-1/0)와 출력 매개변수가 사라지고, **타입 하나(`Option<i32>`)**가 "실패 가능"을 표현합니다. 단, 실패 이유(어떤 에러인지)는 담지 못함 → 그게 필요하면 `Result`(슬라이드 10).

## 슬라이드 10: Partial Functions with Result

### 원문 내용
> ```rust
> fn div(n: i32, m: i32) -> Result<i32, String> {
>   if m == 0 {
>     Err(String::from("division by zero"))
>   } else {
>     Ok(n / m)
>   }
> }
> ```
> - The quotient is returned as a Result
> - Err contains an error message on failure, while Ok contains the quotient on success

### 번역
> 코드: 실패 시 `Err("division by zero")`(에러 메시지 포함), 성공 시 `Ok(몫)`.
> - 몫을 `Result`로 반환한다
> - `Err`는 실패 시 에러 메시지를, `Ok`는 성공 시 몫을 담는다

### 해설
`Result<T, E>`는 `Option`과 달리 **실패 이유 E**를 담습니다. C의 에러 코드(-1, -2 등 숫자)가 의미했던 "왜 실패했나"를 타입 안전한 값으로 표현. `Option`(이유 불필요) vs `Result`(이유 필요)의 선택은 슬라이드 29의 변환 규칙에서 자동 결정됩니다.

## 슬라이드 11: Advantages of ADTs

### 원문 내용
> - ADTs improve readability by conveying the intent with return types
>   - Tuples express the intent of returning multiple values
>   - Option and Result express the possibility of failure
> - Partial functions implemented with Option or Result are less error-prone
>   - The compiler requires programmers to explicitly handle the possibility of failure

### 번역
> - ADT는 **반환 타입으로 의도를 전달**해 가독성을 높인다
>   - 튜플은 "여러 값을 반환한다"는 의도를, `Option`/`Result`는 "실패 가능성"을 표현
> - `Option`/`Result`로 구현한 부분 함수는 **에러를 덜 일으킨다**
>   - 컴파일러가 프로그래머에게 **실패 가능성을 명시적으로 처리하도록 요구**한다

### 해설

**개념 설명 — 왜 더 안전한가**

핵심은 마지막 줄입니다. `Option`/`Result`에서 진짜 값을 꺼내려면 **반드시 `None`/`Err` 경우를 함께 다뤄야**(패턴 매칭) 컴파일이 됩니다. 즉 슬라이드 6의 "나쁜 코드"(실패 확인 누락)가 **컴파일 단계에서 불가능**해집니다. C는 에러 코드를 무시해도 통과하지만, Rust는 강제합니다.

**슬라이드 연결**: 이 강제를 보여 주는 예가 슬라이드 12.

## 슬라이드 12: Example (패턴 매칭 강제)

### 원문 내용
> ```rust
> fn div(n: i32, m: i32) -> Option<i32> {
>   if m == 0 { None } else { Some(n / m) }
> }
>
> match div(n, m) {
>   None => {
>     // handle failure
>   }
>   Some(x) => {
>     // use x
>   }
> }
> ```
> - To obtain the quotient, programmers must use pattern matching, which forces them to handle the failure case

### 번역
> 코드: `div`의 결과에서 몫을 얻으려면 `match`로 `None`(실패)과 `Some(x)`(성공)를 **모두** 처리해야 한다.
> - 몫을 얻으려면 패턴 매칭을 써야 하고, 이는 **실패 경우 처리를 강제**한다

### 해설
`match`는 모든 경우를 다루지 않으면 컴파일 에러(exhaustiveness 검사). 따라서 `None` 가지를 빼먹을 수 없어, 슬라이드 6의 "Bad" 같은 버그가 원천 차단됩니다. C의 약점이 Rust 타입 시스템으로 해소되는 장면.

**슬라이드 연결**: 이제 "그럼 C 출력 매개변수를 ADT로 자동 변환하자"가 슬라이드 13.

## 슬라이드 13: Translating Output Parameters to ADTs

### 원문 내용
> - As ADTs can be used instead, output parameters are considered unidiomatic in Rust and discouraged
> - Ideal C-to-Rust translators should translate output parameters to direct return of ADTs

### 번역
> - ADT로 대체 가능하므로, 출력 매개변수는 Rust에서 **관용적이지 않고(unidiomatic) 권장되지 않는다**
> - 이상적인 C-to-Rust 변환기는 출력 매개변수를 **ADT의 직접 반환**으로 변환해야 한다

### 해설
변환의 목표 선언: C의 `int f(..., int *out)`을 Rust의 `fn f(...) -> (..., T)` 또는 `-> Option<T>`/`-> Result<T,E>`로. 그러려면 "어떤 포인터 인자가 출력 매개변수인지", "실패 가능한지", "반환값이 성공/실패를 뜻하는지"를 알아내야 합니다 → 슬라이드 14의 도전 과제.

## 슬라이드 14: Challenges

### 원문 내용
> - Identifying output parameters
>   - Not every pointer-type parameter is an output parameter
> - Classifying output parameters
>   - Whether failure is possible or not
> - Inferring the meaning of the return value
>   - Whether it signifies success or failure
> - Can be solved with static analysis

### 번역
> - **출력 매개변수 식별**: 모든 포인터 매개변수가 출력 매개변수는 아니다
> - **출력 매개변수 분류**: 실패가 가능한가 아닌가
> - **반환값의 의미 추론**: 그것이 성공/실패를 나타내는가
> - 이 모두 정적 분석으로 풀 수 있다

### 해설

**개념 설명 — 세 가지 질문**

변환에 필요한 세 가지 판단:
1. **식별**: 포인터 인자 중 무엇이 *출력*용인가? (입력용 포인터도 있으니 구분 필요 — 슬라이드 19~20의 핵심.)
2. **분류**: 그 함수는 실패할 수 있나? (실패 없으면 튜플, 있으면 Option/Result.)
3. **반환값 의미**: 반환값이 성공/실패 코드인가, 진짜 데이터인가?

이 셋을 슬라이드 16~29의 분석이 차례로 답합니다.

## 슬라이드 16: Abstract Read/Write Sets

### 원문 내용
> - Abstract read set: R = (𝒫(Param), ⊆)
>   - Pointer-type parameters that may have been read before being written to while reaching the current program point
> - Abstract write set: W = (𝒫(Param), ⊇)
>   - Pointer-type parameters that must have been written to before being read while reaching the current program point
> - Intuition: parameters contained in the abstract write set at the function return are output parameters

### 번역
> - **추상 읽기 집합 R = (포인터 매개변수들의 멱집합, ⊆)**:
>   - 현재 지점에 도달하는 동안 **쓰이기 전에 읽혔을 수 있는(may read before write)** 포인터 매개변수들
> - **추상 쓰기 집합 W = (포인터 매개변수들의 멱집합, ⊇)**:
>   - 현재 지점에 도달하는 동안 **읽히기 전에 반드시 쓰인(must write before read)** 포인터 매개변수들
> - **직관**: 함수 반환 시점의 쓰기 집합에 들어 있는 매개변수가 곧 **출력 매개변수**다

### 해설

**개념 설명 — 출력 매개변수의 형식적 정의**

"출력 매개변수"를 어떻게 기계가 판단할까요? 핵심 통찰:
> 출력 매개변수는 **함수가 (입력으로 읽지 않고) 값을 써넣기만 하는** 포인터다.

이를 두 집합으로 추적합니다:
- **읽기 집합 R (may, ⊆)**: "쓰기 전에 읽혔을 수 있는" 포인터. 이런 포인터는 **입력**으로 쓰인 것 → 순수 출력이 아님. may·합집합(보수적: 한 경로에서라도 먼저 읽으면 입력 의심).
- **쓰기 집합 W (must, ⊇)**: "읽히기 전에 반드시 쓰인" 포인터. 이런 포인터는 **출력**. must·교집합(확실: 모든 경로에서 먼저 써야 출력 보장).

**직관**: 함수 반환 시 W에 든 포인터 = 출력 매개변수. (모든 경로에서, 읽기 없이, 값을 써넣은 포인터.) R에 들면 입력 성격이 섞인 것.

두 집합의 격자 방향이 다름에 주의: R은 ⊆(may, 작을수록 좋음), W는 ⊇(must, 클수록 좋지만 보수적으로 교집합). 강의 7~8의 may/must·합/교 구분의 재등장.

**슬라이드 연결**: 상태·JOIN이 슬라이드 17, 전이 규칙이 슬라이드 18, 예제가 19~23.

## 슬라이드 17: Analysis State and Join

### 원문 내용
> - State = R × W
> - JOIN(v) = ⨆_{u∈pred(v)} ⟦u⟧
>   - Forward analysis

### 번역
> - 상태 = R × W (읽기 집합과 쓰기 집합의 쌍)
> - JOIN(v) = v의 모든 **선행자(predecessor)** u의 분석값의 **결합(⨆)**
>   - **전방(forward) 분석**

### 해설

**개념 설명**

상태는 `(R, W)` 쌍입니다. 전방 분석이므로 JOIN은 선행자들을 모읍니다. 단, R과 W의 결합(⨆)이 각자의 격자 방향을 따른다는 점이 미묘합니다:
- R(⊆)의 join = 합집합(∪): 어느 선행 경로에서든 "쓰기 전 읽기"가 있었으면 합쳐 보존.
- W(⊇)의 join = 교집합(∩): 모든 선행 경로에서 "읽기 전 쓰기"여야 W에 유지.

즉 분기 합류에서 R은 커지고(보수적으로 입력 의심 보존), W는 작아집니다(확실한 출력만 유지). 이 비대칭이 슬라이드 22(분기로 W가 비는 예)에서 드러납니다.

## 슬라이드 18: Constraint Rules

### 원문 내용
> Let JOIN(v) = (r, w).
> - entry: ⟦v⟧ = (∅, ∅)
> - `y = *x`:
>   ⟦v⟧ = (r ∪ {x}, w) if x ∉ w; (r, w) otherwise
> - `*x = e`:
>   ⟦v⟧ = (r, w ∪ {x}) if x ∉ r; (r, w) otherwise

### 번역
> JOIN(v)=(r, w)라 하자.
> - **진입(entry)**: ⟦v⟧ = (∅, ∅) — 시작 시 읽지도 쓰지도 않음
> - **`y = *x`** (포인터 x를 통해 읽음):
>   - x가 아직 쓰기 집합 w에 없으면 → R에 x 추가: (r∪{x}, w) (쓰기 전에 읽었으므로 입력 성격)
>   - x가 이미 w에 있으면 → 변화 없음 (이미 썼다가 읽는 것이므로 출력 유지)
> - **`*x = e`** (포인터 x를 통해 씀):
>   - x가 아직 읽기 집합 r에 없으면 → W에 x 추가: (r, w∪{x}) (읽기 전에 썼으므로 출력 성격)
>   - x가 이미 r에 있으면 → 변화 없음 (이미 읽혔으므로 출력으로 안 침)

### 해설

**개념 설명 — "쓰기 전 읽기" vs "읽기 전 쓰기"를 추적하는 법**

전이 규칙의 핵심은 **순서**입니다. 같은 포인터라도 먼저 무엇을 했느냐로 입력/출력이 갈립니다:
- **`y = *x` (읽기)**: 만약 아직 안 썼다면(`x∉w`) → "쓰기 전에 읽음" = 입력 → R에 추가. 이미 썼었다면(`x∈w`) → "썼다가 읽음"이니 출력 성격 유지(아무것도 안 함).
- **`*x = e` (쓰기)**: 만약 아직 안 읽혔다면(`x∉r`) → "읽기 전에 씀" = 출력 → W에 추가. 이미 읽혔다면(`x∈r`) → 입력으로 이미 분류됐으니 W에 넣지 않음.

이 "first action wins" 규칙으로, 각 포인터가 입력(R)인지 출력(W)인지를 도달 경로마다 추적합니다.

**슬라이드 연결**: 슬라이드 19~23이 이 규칙을 다양한 코드에 적용한 추적 예제(시험 단골).

## 슬라이드 19: Constraint Rules — Example 1

### 원문 내용
> ```c
> void foo(int *p) {
>   // r = {}, w = {}
>   *p = 42;
>   // r = {}, w = {p}
> }
> ```
> - p is an output parameter

### 번역
> 코드: `*p = 42`로 p에 씀. 진입 `({},{})`, 쓰기 후 `({}, {p})`.
> - **p는 출력 매개변수**다 (반환 시 W에 p가 있음)

### 해설
가장 단순한 경우. p를 읽지 않고 쓰기만 함 → 반환 시 W={p} → 출력 매개변수. 슬라이드 16의 직관("반환 시 W에 든 것이 출력") 확인.

## 슬라이드 20: Constraint Rules — Example 2

### 원문 내용
> ```c
> void foo(int *p) {
>   // r = {}, w = {}
>   int x = *p;
>   // r = {p}, w = {}
>   *p = x + 1;
>   // r = {p}, w = {}
> }
> ```
> - p is not an output parameter
>   - Without taking p, the function cannot decide the value of x

### 번역
> 코드: 먼저 `x = *p`로 p를 **읽고**, 그 다음 `*p = x+1`로 씀. 읽기 후 `({p},{})`, 쓰기 후에도 `({p},{})`(이미 r에 p가 있어 W에 안 들어감).
> - **p는 출력 매개변수가 아니다**
>   - p를 입력으로 받지 않으면 x의 값을 결정할 수 없으므로

### 해설

**개념 설명**

여기서 p는 먼저 **읽힙니다**(`x = *p`) → R에 들어감. 이후 쓰기(`*p = x+1`)는 슬라이드 18 규칙상 "x가 이미 r에 있으므로 W에 추가 안 함". 결국 반환 시 W={} → **출력 매개변수 아님**. 직관적으로도 `*p`의 기존 값을 읽어 +1 하므로, p는 **입력**(기존 값이 필요)입니다. 변환 시 일반 입력 인자로 남깁니다.

## 슬라이드 21: Constraint Rules — Example 3

### 원문 내용
> ```c
> int foo(int *p) {
>   // r = {}, w = {}
>   *p = 42;
>   // r = {}, w = {p}
>   int x = *p;
>   // r = {}, w = {p}
>   return x;
>   // r = {}, w = {p}
> }
> ```
> - p is an output parameter
>   - The function can decide the value of x even without taking p

### 번역
> 코드: 먼저 `*p = 42`로 **쓰고**, 그 다음 `x = *p`로 읽음. 쓰기 후 `({},{p})`, 읽기 후에도 `({},{p})`(이미 w에 p가 있어 R에 안 들어감).
> - **p는 출력 매개변수**다
>   - p를 입력으로 받지 않아도 x의 값을 결정할 수 있으므로

### 해설

**개념 설명 — 슬라이드 20과 정반대**

순서가 뒤집혔습니다. p를 먼저 **쓰고**(W에 추가) 나중에 읽습니다. 읽기 시 "x가 이미 w에 있으므로 R에 추가 안 함"(슬라이드 18). 그래서 반환 시 W={p} → **출력 매개변수**. 직관: `*p`에 42를 써넣은 뒤 그걸 읽은 것이라, p의 *기존* 값은 필요 없음(입력 아님). 슬라이드 20 vs 21은 **읽기/쓰기 순서가 출력 여부를 가른다**는 슬라이드 18 규칙의 정수를 보여 줍니다.

## 슬라이드 22: Constraint Rules — Example 4

### 원문 내용
> ```c
> void foo(int *p) {
>   // r = {}, w = {}
>   if (...) {
>     // r = {}, w = {}
>     *p = 42;
>     // r = {}, w = {p}
>   } else {
>     // r = {}, w = {}
>     int x = *p;
>     // r = {p}, w = {}
>   }
>   // r = {p}, w = {}
> }
> ```
> - p is not an output parameter
>   - Without taking p, the function cannot decide the value of x

### 번역
> 코드: then 가지는 `*p=42`(쓰기) → `({},{p})`, else 가지는 `x=*p`(읽기) → `({p},{})`. 합류 시 R은 합집합 `{}∪{p}={p}`, W는 교집합 `{p}∩{}={}` → `({p},{})`.
> - **p는 출력 매개변수가 아니다**

### 해설

**개념 설명 — 분기 합류에서 R·W의 비대칭**

슬라이드 17의 비대칭 결합이 여기서 결정적입니다. 한 경로(else)에서 p를 입력으로 읽으므로:
- R(합집합)은 `{p}`를 보존 → "입력일 수 있음".
- W(교집합)는 then에서만 썼고 else에선 안 썼으니 `{}`로 비워짐 → "모든 경로에서 출력이라 보장 못 함".

반환 시 W={} → **출력 매개변수 아님**. 한 경로에서라도 입력으로 쓰이면 출력으로 못 박을 수 없다는 must(교집합)의 보수성입니다.

## 슬라이드 23: Constraint Rules — Example 5

### 원문 내용
> ```c
> int foo(int *p) {
>   // r = {}, w = {}
>   int x = -1;
>   // r = {}, w = {}
>   if (...) {
>     // r = {}, w = {}
>     *p = 42;
>     // r = {}, w = {p}
>     x = 0;
>     // r = {}, w = {p}
>   }
>   // r = {}, w = {}
>   return x;
> }
> ```
> - p is an output parameter, but the abstract write set at the return is empty

### 번역
> 코드: `if`가 참일 때만 `*p=42`로 쓰고 `x=0`. then 끝 `({},{p})`, 하지만 if를 안 거치는 경로(else 없음=암묵적 통과)와 합류하면 W 교집합 `{p}∩{}={}`.
> - **p는 출력 매개변수이지만, 반환 시점의 추상 쓰기 집합이 비어 있다**

### 해설

**개념 설명 — 분석의 한계와 다음 슬라이드의 동기**

여기서 문제가 생깁니다. **실제로 p는 출력 매개변수**입니다(쓰일 때가 있으니까). 그런데 if를 통과하지 않는 경로에서는 p에 쓰지 않으므로, 합류 후 W={} → 분석은 "출력 아님"이라고 (잘못) 결론냅니다.

핵심은 이것이 **부분 함수**라는 점입니다: if 통과(성공, x=0, p에 씀) vs 미통과(실패, x=-1, p 안 씀). "성공 시에만 출력에 쓴다"는 패턴인데, 단순 W 분석은 성공/실패 경로를 구분 못 해 W가 비어 버립니다. 이 한계를 극복하려고 **쓰기 집합 민감 분석**(슬라이드 24)이 등장합니다.

**슬라이드 연결**: 이 문제를 푸는 것이 슬라이드 24~28.

## 슬라이드 24: Write Set Sensitivity

### 원문 내용
> - State = W → R
> - Distinguish different write sets

### 번역
> - 상태 = **W → R** (쓰기 집합을 키로, 읽기 집합을 값으로 하는 사상)
> - 서로 다른 **쓰기 집합을 구분**한다

### 해설

**개념 설명 — 경로를 쓰기 집합으로 구분하기**

슬라이드 23의 문제는 "p에 쓴 경로"와 "안 쓴 경로"가 합류하며 뭉개진 것입니다. 해법: **쓰기 집합별로 따로** 상태를 유지합니다. 상태를 단일 `(R,W)`가 아니라 **사상 `W → R`** — 즉 "각 가능한 쓰기 집합 W마다 그에 해당하는 읽기 집합 R" — 으로 둡니다.

이는 강의 10의 **경로/문맥 민감(sensitivity)** 아이디어의 한 형태입니다: 정보를 뭉개지 않고 갈래별로 분리 유지 → 정밀도↑(비용↑). 여기선 "쓰기 집합"이 갈래를 구분하는 기준(success는 W={p}, failure는 W={}).

**슬라이드 연결**: 적용 예가 슬라이드 25.

## 슬라이드 25: Write Set Sensitivity — Example

### 원문 내용
> ```c
> int foo(int *p) {
>   // {}: {}
>   int x = -1;
>   // {}: {}
>   if (...) {
>     // {}: {}
>     *p = 42;
>     // {}: {}
>     x = 0;
>     // {p}: {}
>   }
>   // {}: {}
>   // {p}: {}
>   return x;
> }
> ```
> - p is an output parameter, and failure is possible

### 번역
> 코드: 이제 상태가 `W: R` 형태. then 가지 끝은 `{p}: {}`(쓰기 집합 {p}에 읽기 {}), if를 안 거친 경로는 `{}: {}`. 합류 시 **둘을 뭉개지 않고 둘 다 유지** → `{}: {}` 그리고 `{p}: {}`.
> - **p는 출력 매개변수이고, 실패가 가능하다**

### 해설

**개념 설명**

이제 반환 시점에 **두 개의 쓰기 집합**이 살아남습니다: `{p}`(성공 경로)와 `{}`(실패 경로). 이로써 분석은:
- p가 **어떤 경로(성공)에서는 출력**됨을 안다(W={p} 존재) → 출력 매개변수 인정.
- 동시에 **실패 경로(W={})도 존재**함을 안다 → "실패 가능 = 부분 함수".

슬라이드 23의 한계가 해소됐습니다. 더 나아가 "성공/실패를 반환값으로 어떻게 구분하나"는 슬라이드 26의 정수 집합 도메인이 답합니다.

## 슬라이드 26: Integer Set Domain

### 원문 내용
> - Set domain: V = ({A | A ⊆ ℤ ∧ |A| ≤ k} ∪ {ℤ}, ⊆)
>   - An abstract value is a set of at most k integers, or the set of all integers
> - State = W → (R × (Var → V))
>   - Can decide return values associated with different write sets

### 번역
> - **정수 집합 도메인 V**: 크기가 **최대 k**인 정수 집합들, 또는 **전체 정수 집합 ℤ**(너무 커지면 ⊤로 올림), 순서는 ⊆
> - 상태 = **W → (R × (Var → V))**: 쓰기 집합마다, 읽기 집합과 더불어 **각 변수의 가능한 정수값 집합**을 추적
>   - 서로 다른 쓰기 집합에 연관된 **반환값**을 결정할 수 있다

### 해설

**개념 설명 — 반환값까지 추적하기**

부분 함수를 Option/Result로 바꾸려면 "반환값이 성공/실패를 어떻게 구분하나"를 알아야 합니다(슬라이드 4의 0=성공, -1=실패). 그래서 상태에 **변수의 정수값 추적**을 추가합니다.

- **정수 집합 도메인 V**: 변수가 가질 수 있는 정수들의 집합. 단 무한정 커지지 않게 **크기 k로 제한**, 넘으면 ℤ(전체=⊤)로 추상화.⁹ 강의 5~6의 추상 도메인·갈루아 연결 아이디어.
- **상태 `W → (R × (Var→V))`**: 쓰기 집합별로, 읽기 집합과 함께 각 변수의 값 집합을 유지. → 성공 경로(W={p})의 반환값 집합 vs 실패 경로(W={})의 반환값 집합을 분리해 구할 수 있음.

**각주**

⁹ 왜 집합 도메인이고 구간(interval) 도메인이 아닌가? 슬라이드 28이 정확히 이 비교를 합니다. 핵심은 "성공값과 실패값이 섞이지 않게 **정확히 구분**"해야 하는데, 구간은 `[-1,5]`처럼 둘을 뭉개 버려 곤란하기 때문입니다.

**슬라이드 연결**: 예제가 슬라이드 27, 집합 vs 구간 비교가 슬라이드 28.

## 슬라이드 27: Integer Set Domain — Example 1

### 원문 내용
> ```c
> int foo(int *p) {
>   // {}: {}, [x: {}]
>   int x = -1;
>   // {}: {}, [x: {-1}]
>   if (...) {
>     // {}: {}, [x: {-1}]
>     *p = 42;
>     // {}: {}, [x: {-1}]
>     x = 0;
>     // {p}: {}, [x: {0}]
>   }
>   // {}: {}, [x: {-1}]
>   // {p}: {}, [x: {0}]
>   return x;
> }
> ```
> - On failure, −1 is returned
> - On success, 0 is returned

### 번역
> 코드: 쓰기 집합별로 x의 값을 추적. 실패 경로 `{}: ..., [x:{-1}]`, 성공 경로 `{p}: ..., [x:{0}]`.
> - **실패 시 -1 반환, 성공 시 0 반환**

### 해설

**개념 설명**

이제 분석이 완전한 그림을 그립니다:
- W={} (실패, p 안 씀) → x=-1 반환.
- W={p} (성공, p 씀) → x=0 반환.

즉 "p는 출력 매개변수, 실패 가능, 성공=0/실패=-1"을 모두 알아냈습니다. 이 정보로 슬라이드 29의 변환 규칙이 `Result<i32, i32>`(성공 Ok(0의 자리값)·실패 Err(-1))로 변환합니다.

## 슬라이드 28: Integer Set Domain — Example 2 (집합 vs 구간)

### 원문 내용
> ```c
> int foo(int *p) {
>   int x = 0;
>   if (...) {
>     x = -1;
>   } else if (...) {
>     x = 2;
>   } else if (...) {
>     x = 5;
>   } else {
>     *p = 42;
>   }
>   return x;
> }
> ```
> - −1, 2, and 5 signify failure, while 0 signifies success
> - The set domain gives {−1, 2, 5} and {0} for the two write sets, respectively
> - The interval domain would give [−1, 5] and [0, 0], which have intersection, making it impossible to distinguish success and failure cases

### 번역
> 코드: 여러 분기가 x를 -1, 2, 5(모두 실패)로 두거나, 마지막 else에서 `*p=42`(성공, x는 0 유지).
> - -1, 2, 5는 실패를, 0은 성공을 뜻함
> - **집합 도메인**: 두 쓰기 집합에 대해 각각 `{-1,2,5}`(W={})와 `{0}`(W={p}) → 깔끔히 구분
> - **구간 도메인**이었다면: `[-1,5]`와 `[0,0]` → **교집합이 있어** 성공/실패를 구분 못 함

### 해설

**개념 설명 — 왜 집합이 구간보다 나은가 (도메인 선택의 교훈)**

이 슬라이드는 **추상 도메인 선택이 분석의 성패를 가르는** 좋은 사례입니다(강의 5~6·9의 주제). 실패값이 -1,2,5로 흩어져 있을 때:
- **집합 도메인**: `{-1,2,5}` vs `{0}` → 두 집합이 **서로소(disjoint)** → "반환값이 0이면 성공, 아니면 실패"로 명확히 분리. → `Result`로 변환 가능.
- **구간 도메인**: `[-1,5]`(실패값들의 최소~최대) vs `[0,0]`(성공값). 그런데 `[0,0] ⊆ [-1,5]` — **0이 실패 구간 안에 포함**되어, 반환값 0만 보고 성공/실패를 구분 불가!

즉 **구간은 "사이의 빈틈"을 메워 버려** 흩어진 값들을 구분 못 하지만, **집합은 정확한 원소만 유지**해 구분합니다. 이것이 슬라이드 26에서 (구간이 아닌) 집합 도메인을 택한 이유입니다. 단, 집합은 무한정 커질 수 있어 크기 k 제한·ℤ 올림이 필요(정밀도-비용 트레이드오프).

**슬라이드 연결**: 이 분석 결과를 변환으로 옮기는 규칙이 슬라이드 29.

## 슬라이드 29: Interpreting Analysis Results

### 원문 내용
> - At return, if every write set contains p, then p is a must-output parameter
>   - No failure case is possible
>   - Replaced with direct return of a tuple
> - At return, if some write set contains p and no read set contains p, then p is a may-output parameter
>   - Failure cases are possible
>   - If the success return value is unique and different from failure return values, replaced with direct return of a Result
>   - Otherwise, replaced with direct return of an Option

### 번역
> - 반환 시 **모든 쓰기 집합이 p를 포함**하면, p는 **반드시-출력(must-output) 매개변수**
>   - 실패 경우 없음 → **튜플**의 직접 반환으로 대체
> - 반환 시 **일부 쓰기 집합이 p를 포함**하고 **어떤 읽기 집합도 p를 포함하지 않으면**, p는 **혹시-출력(may-output) 매개변수**
>   - 실패 경우 가능
>   - 성공 반환값이 **유일하고 실패 반환값들과 다르면** → **`Result`**로 대체
>   - 그렇지 않으면 → **`Option`**으로 대체

### 해설

**개념 설명 — 분석 결과 → 어떤 ADT로? (결정표)**

지금까지의 모든 분석(W 민감 + 정수 집합)이 이 결정 규칙으로 수렴합니다:

1. **모든 경로에서 p에 씀** (모든 W가 p 포함) → 실패 없음 → **튜플** `(반환값, *p)`. (슬라이드 8·30)
2. **일부 경로만 p에 씀** + p가 입력 아님 → 실패 가능(부분 함수):
   - 성공값이 실패값들과 **구별 가능**(유일하고 다름) → **`Result`**(성공=Ok, 실패=Err에 그 값). (슬라이드 31)
   - 성공값이 실패값과 **구별 불가**(겹침) → **`Option`**(성공=Some, 실패=None; 반환값으로는 구분 못 하니 존재 여부로만). (슬라이드 32)

슬라이드 28의 집합 vs 구간 비교가 바로 "성공값이 실패값과 구별되는가"(Result 가능 여부)를 정확히 판단하기 위함이었습니다.

**슬라이드 연결**: 세 경우의 실제 변환이 슬라이드 30·31·32.

## 슬라이드 30: Translation — Example 1 (튜플)

### 원문 내용
> ```c
> int foo(int *p) {
>   *p = 42;
>   return 0;
> }
> ```
> ⇒
> ```rust
> fn foo() -> (i32, i32) {
>   (0, 42)
> }
> ```
> - p is a must-output parameter

### 번역
> p가 항상 쓰이는 must-output → 출력 매개변수와 반환값을 묶어 **튜플 `(0, 42)`** 반환.

### 해설
모든 경로에서 p에 씀 + 실패 없음 → 슬라이드 29의 첫 규칙 → 튜플. C의 `(반환값 0, *p에 쓴 42)`가 Rust `(0, 42)`로.

## 슬라이드 31: Translation — Example 2 (Result)

### 원문 내용
> ```c
> int foo(int *p) {
>   if (...) {
>     *p = 42;
>     return 0;
>   } else {
>     return -1;
>   }
> }
> ```
> ⇒
> ```rust
> fn foo() -> Result<i32, i32> {
>   if ... {
>     Ok(42)
>   } else {
>     Err(-1)
>   }
> }
> ```
> - p is a may-output parameter, 0 signifies success, and −1 signifies failure

### 번역
> 성공(0)일 때만 p에 쓰고, 실패(-1)는 구별되는 값 → **`Result`**: 성공 `Ok(42)`, 실패 `Err(-1)`.

### 해설
may-output + 성공값(0)이 실패값(-1)과 구별됨 → 슬라이드 29의 Result 규칙. 성공 시 출력값 42를 `Ok`에, 실패 코드 -1을 `Err`에. C의 에러 코드가 Rust의 타입 안전한 Result로 승격.

## 슬라이드 32: Translation — Example 3 (Option)

### 원문 내용
> ```c
> int foo(int *p) {
>   if (...) {
>     *p = 42;
>     return 0;
>   } else {
>     return 0;
>   }
> }
> ```
> ⇒
> ```rust
> fn foo() -> (i32, Option<i32>) {
>   if ... {
>     (0, Some(42))
>   } else {
>     (0, None)
>   }
> }
> ```
> - p is a may-output parameter, and 0 can signify both success and failure

### 번역
> 성공·실패 모두 0을 반환 → 반환값으로 구분 불가 → 출력 부분만 **`Option`**: 쓴 경우 `Some(42)`, 안 쓴 경우 `None`. 반환값 0은 튜플로 그대로 둠 → `(i32, Option<i32>)`.

### 해설

**개념 설명 — Result가 안 되는 경우**

여기선 성공·실패 둘 다 반환값 0입니다(슬라이드 28의 구간 문제와 유사: 구별 불가). 그래서 반환값으로는 성공/실패를 못 가르고, **출력이 있었는지 여부(Some/None)**로만 표현 → `Option<i32>`. 반환값 0 자체는 의미가 남아 있어 튜플로 유지(`(0, Some/None)`). 슬라이드 29의 "otherwise → Option" 규칙의 실현.

## 슬라이드 33: I/O in C

### 원문 내용
> - I/O functions in C are not memory-safe
>   - e.g., they do not check array bounds
> ```c
> FILE *fp = ...;
> char buf[10];
> fread(buf, 20, 1, fp); // buffer overflow
> ```

### 번역
> - C의 I/O 함수들은 **메모리 안전하지 않다** (배열 경계를 검사하지 않음)
> - 예: 크기 10인 `buf`에 20바이트를 읽으려 함 → **버퍼 오버플로**

### 해설

**개념 설명 — I/O 주제 시작**

여기서 강의의 **둘째 주제**가 시작됩니다(출력 매개변수와 독립). C의 I/O는 두 가지 안전 문제가 있습니다: (1) 메모리 안전성 — `fread`가 버퍼 크기를 모르고 넘치게 읽음(여기 예시), (2) 타입 안전성 — 모든 스트림이 같은 `FILE*` 타입이라 잘못된 연산을 막지 못함(슬라이드 36~37). Rust I/O는 둘 다 해결합니다(슬라이드 34, 38~41).

## 슬라이드 34: I/O in Rust

### 원문 내용
> - I/O functions in Rust are memory-safe
>   - e.g., they check array bounds
> ```rust
> let mut f = ...;
> let mut buf = [0u8; 10];
> f.read(&mut buf[..]); // read up to 10 bytes
> ```

### 번역
> - Rust의 I/O 함수들은 **메모리 안전**하다 (배열 경계 검사)
> - 예: `buf`의 슬라이스 `&mut buf[..]`를 넘기면, **버퍼 크기(10)만큼만** 읽음 → 오버플로 없음

### 해설
Rust의 `read`는 **슬라이스**(`&mut buf[..]`)를 받습니다 — 슬라이스는 포인터+길이를 함께 담으므로, 함수가 버퍼 크기를 알고 그 이상 안 읽습니다. 메모리 안전성 해결. 남은 문제(타입 안전성)는 스트림 종류 구분으로 이어집니다(슬라이드 35).

## 슬라이드 35: I/O Streams

### 원문 내용
> - Streams can have different origins
>   - Standard input/output/error, files
> - Streams can have different capabilities
>   - Readable, writable, seekable

### 번역
> - 스트림은 서로 다른 **출처(origin)**를 가질 수 있다: 표준 입력/출력/에러, 파일
> - 스트림은 서로 다른 **능력(capability)**을 가질 수 있다: 읽기·쓰기·탐색(seek) 가능

### 해설

**개념 설명 — 출처와 능력 (I/O 파트의 두 키워드)**

스트림(데이터 흐름)은 두 축으로 분류됩니다:
- **출처(origin)**: 어디서 온 스트림인가 — `stdin`(표준 입력), `stdout`, `stderr`, `file`(파일).
- **능력(capability)**: 무엇을 할 수 있는가 — `read`(읽기), `write`(쓰기), `seek`(위치 이동).

출처마다 가능한 능력이 다릅니다(예: stdin은 읽기만, 파일은 읽기·쓰기·탐색 모두). C는 이를 구분 안 하지만(슬라이드 36), Rust는 타입·트레이트로 구분합니다(슬라이드 38~40). 이 두 개념이 슬라이드 43의 분석 변수 `⟦x⟧_o`(출처)·`⟦x⟧_c`(능력)로 이어집니다.

## 슬라이드 36: Streams in C

### 원문 내용
> - Every stream has the same type FILE * regardless of its origin and capabilities
> ```c
> FILE *fp = stdout;
> fprintf(fp, "Hello, world!\n");
>
> fp = fopen("file.txt", "r");
> char buf[4];
> fread(buf, 4, 1, fp);
> ```

### 번역
> - C에서는 출처·능력과 무관하게 **모든 스트림이 같은 `FILE *` 타입**이다
> - 예: `fp`가 `stdout`(쓰기용)이었다가 파일(읽기용)로 바뀌어도 타입은 같은 `FILE*`

### 해설
C의 약점: `stdout`이든 읽기 전용 파일이든 모두 `FILE*`. 타입이 능력을 구분 못 하므로, 컴파일러가 "쓰기 전용 스트림에서 읽기" 같은 실수를 막지 못합니다(슬라이드 37).

## 슬라이드 37: Streams in C — Problems

### 원문 내용
> - Streams may be used for operations that they do not support
>   - Such operations do not violate memory safety but fail at runtime
> ```c
> FILE *fp = stdin;
> fprintf(fp, "Hello, world!\n");
> ```
> - Streams may be used after they have been closed
>   - Undefined behavior
> ```c
> fclose(fp);
> fprintf(fp, "Hello, world!\n");
> ```

### 번역
> - 스트림이 **지원하지 않는 연산**에 쓰일 수 있다(런타임에 실패): 예) 읽기 전용 `stdin`에 `fprintf`(쓰기) 시도
> - 스트림이 **닫힌 뒤에도** 쓰일 수 있다(미정의 동작): `fclose` 후 `fprintf`

### 해설

**개념 설명 — C의 두 가지 I/O 버그**

1. **지원 안 하는 연산**: `stdin`(읽기 전용)에 `fprintf`(쓰기). 메모리는 안 깨지지만 런타임 실패.
2. **닫힌 스트림 사용(use-after-close)**: `fclose` 후 사용 → 미정의 동작(강의 12의 use-after-free와 닮은 자원 수명 문제).

둘 다 C 타입 시스템이 못 막습니다. Rust는 (1)을 트레이트로, (2)를 소유권으로 막습니다(슬라이드 41).

## 슬라이드 38: Streams in Rust — Origins

### 원문 내용
> - Different types represent different origins
> ```rust
> let f0: Stdin = stdin();
> let f1: Stdout = stdout();
> let f2: Stderr = stderr();
> let f3: File = File::open("file.txt").unwrap();
> ```

### 번역
> - Rust에서는 **서로 다른 타입이 서로 다른 출처**를 나타낸다: `Stdin`, `Stdout`, `Stderr`, `File`

### 해설
C의 만능 `FILE*`이 Rust에서는 출처별 **구체 타입**(`Stdin`/`Stdout`/`Stderr`/`File`)으로 갈라집니다. 타입만 봐도 출처를 알 수 있음. 능력은 트레이트로 표현(슬라이드 39).

## 슬라이드 39: Streams in Rust — Capabilities

### 원문 내용
> - Different traits represent different capabilities
> ```rust
> fn f<R: Read>(r: R) {
>   let mut buf = [0u8; 4];
>   r.read(&mut buf);
> }
> fn g<W: Write>(w: W) {
>   w.write(b"Hello, world!\n");
> }
> fn h<S: Seek>(s: S) {
>   s.seek(SeekFrom::Start(0));
> }
> ```

### 번역
> - **서로 다른 트레이트가 서로 다른 능력**을 나타낸다: `Read`(읽기), `Write`(쓰기), `Seek`(탐색). 함수는 필요한 능력을 트레이트 바운드(`R: Read` 등)로 요구.

### 해설

**배경 지식 — 트레이트(trait)**

**트레이트**는 "이 타입이 무엇을 할 수 있는가"를 표현하는 Rust의 인터페이스(강의 2). `Read`를 구현한 타입만 `read`를 부를 수 있습니다. 함수가 `fn f<R: Read>(r: R)`이면 "읽기 가능한 무엇이든 받음". 출처(타입)와 능력(트레이트)을 분리해, **능력 단위로** 함수를 작성·검사할 수 있습니다.

## 슬라이드 40: Streams in Rust — Type/Trait Mapping

### 원문 내용
> - Each type implements the traits corresponding to its capabilities
>   - Stdin implements Read
>   - Stdout and Stderr implement Write
>   - File implements Read, Write, and Seek

### 번역
> - 각 타입은 자신의 능력에 해당하는 트레이트를 구현한다:
>   - `Stdin` → `Read`
>   - `Stdout`, `Stderr` → `Write`
>   - `File` → `Read`, `Write`, `Seek`

### 해설
출처(타입)와 능력(트레이트)의 대응표입니다. `Stdin`은 읽기만, `Stdout`/`Stderr`는 쓰기만, `File`은 셋 다. 이 대응이 변환의 핵심 — "이 스트림이 어떤 출처에서 와서 어떤 능력이 필요한가"를 알면 적절한 타입/트레이트를 고를 수 있습니다(슬라이드 49).

## 슬라이드 41: Streams in Rust — Advantages

### 원문 내용
> - Some unsupported operations are prevented at compile time
> ```rust
> let f: Stdin = stdin();
> f.write(b"Hello, world!\n"); // compile-time error
> ```
> - The ownership system prevents the use of closed streams
> ```rust
> drop(f);
> f.write(b"Hello, world!\n"); // compile-time error
> ```

### 번역
> - 일부 미지원 연산이 **컴파일 타임에 방지**됨: `Stdin`은 `Write`를 구현 안 하므로 `f.write(...)`는 컴파일 에러
> - **소유권 시스템**이 닫힌 스트림 사용을 방지: `drop(f)` 후 `f.write(...)`는 컴파일 에러

### 해설

**개념 설명**

슬라이드 37의 두 C 버그가 Rust에서 **컴파일 에러**가 됩니다:
- 능력 없는 연산(`Stdin`에 write): 트레이트 미구현 → 타입 에러.
- 닫힌 스트림 사용: `drop` 후 소유권 무효 → 컴파일 에러(강의 12의 가드 `drop` 후 사용 거부와 동일 원리).

런타임 실패가 컴파일 타임 검출로 승격. 이것이 C I/O를 Rust로 바꿀 동기입니다(슬라이드 42).

## 슬라이드 43: Origin and Capability Analysis

### 원문 내용
> - For each program variable x of type FILE *, we introduce constraint variables ⟦x⟧_o and ⟦x⟧_c
>   - ⟦x⟧_o denotes the set of possible origins of x
>   - ⟦x⟧_c denotes the set of capabilities required for x
> - Origins = {stdin, stdout, stderr, file}
> - Capabilities = {read, write, seek}

### 번역
> - `FILE *` 타입 변수 x마다 **두 제약 변수** `⟦x⟧_o`, `⟦x⟧_c`를 도입
>   - `⟦x⟧_o`: x의 가능한 **출처들의 집합**
>   - `⟦x⟧_c`: x에 **요구되는 능력들의 집합**
> - 출처 = {stdin, stdout, stderr, file}, 능력 = {read, write, seek}

### 해설

**개념 설명 — 강의 11과 똑같은 제약 기반 분석!**

여기가 이 강의의 **백미**입니다. 강의 11(제어 흐름 분석)에서 변수마다 `[x]`(가능한 함수 집합)를 두고 제약식을 풀었듯이, 여기서는 변수 x마다 **두 개의 집합 변수**를 둡니다:
- `⟦x⟧_o` = x가 가리킬 수 있는 **출처** 집합 (강의 11의 "함수 집합"에 대응).
- `⟦x⟧_c` = x에 필요한 **능력** 집합.

출처(4종)·능력(3종)이 **토큰** 역할을 합니다. 그리고 슬라이드 46에서 밝히듯, 이 제약식들은 강의 11의 **cubic 알고리즘으로 그대로** 풀립니다. 강의 11의 도구가 락도 함수도 아닌 I/O 타입 추론에 재사용되는 — 정적 분석 기법의 범용성을 보여 주는 대목.

**슬라이드 연결**: 제약 규칙이 슬라이드 44(생성·연산)·45(대입), 풀이가 46~48.

## 슬라이드 44: Constraint Rules — Construction and Operations

### 원문 내용
> - Stream constructions give origin constraints
>   - x = stdin : stdin ∈ ⟦x⟧_o
>   - x = stdout : stdout ∈ ⟦x⟧_o
>   - x = stderr : stderr ∈ ⟦x⟧_o
>   - x = fopen(...) : file ∈ ⟦x⟧_o
> - Stream operations give capability constraints
>   - fgetc(x) : read ∈ ⟦x⟧_c
>   - fputc(_, x) : write ∈ ⟦x⟧_c
>   - fseek(x, _, _) : seek ∈ ⟦x⟧_c

### 번역
> - **스트림 생성 → 출처 제약**:
>   - `x = stdin` ⟹ stdin ∈ ⟦x⟧_o (이하 stdout/stderr/fopen→file 동일)
> - **스트림 연산 → 능력 제약**:
>   - `fgetc(x)`(읽기) ⟹ read ∈ ⟦x⟧_c
>   - `fputc(_, x)`(쓰기) ⟹ write ∈ ⟦x⟧_c
>   - `fseek(x,_,_)`(탐색) ⟹ seek ∈ ⟦x⟧_c

### 해설

**개념 설명 — 토큰을 뿌리는 규칙 (강의 11의 규칙 1과 대응)**

- 스트림을 **만드는** 코드는 출처 토큰을 심습니다(`x=stdin`이면 stdin이 x의 출처). 강의 11의 `fn foo` ⟹ `foo∈[foo]`(함수 토큰 심기)와 같은 역할.
- 스트림을 **연산하는** 코드는 능력 토큰을 요구합니다(`fgetc(x)`면 x는 read 능력 필요).

이 두 종류 모두 `t ∈ x` 형태(강의 11 슬라이드 8의 첫 제약식)입니다. 대입을 통한 전파가 슬라이드 45.

## 슬라이드 45: Constraint Rules — Assignment

### 원문 내용
> - Constraints are propagated through assignments
>   - x = y : ⟦x⟧_o ⊇ ⟦y⟧_o ∧ ⟦x⟧_c ⊆ ⟦y⟧_c
> - Any origins possible for y are also possible for x
> - Any capabilities required for x are also required for y
>   - Analogy: subtyping (a type with more methods is a subtype)

### 번역
> - **대입을 통한 전파**: `x = y` ⟹ `⟦x⟧_o ⊇ ⟦y⟧_o` 그리고 `⟦x⟧_c ⊆ ⟦y⟧_c`
> - y의 가능한 출처는 모두 x의 가능한 출처이기도 하다 (출처는 y→x로 흐름)
> - x에 요구되는 능력은 모두 y에도 요구된다 (능력은 x→y로 흐름)
>   - **비유: 서브타이핑** (더 많은 메서드를 가진 타입이 서브타입)

### 해설

**개념 설명 — 두 정보가 반대 방향으로 흐른다 (미묘하지만 중요)**

`x = y`(y를 x에 대입)에서:
- **출처(origin)는 y → x 방향**: y가 가질 수 있는 출처는 x도 가질 수 있음(`⟦x⟧_o ⊇ ⟦y⟧_o`). 데이터(스트림 객체)가 y에서 x로 흐르니 자연스럽습니다 — 강의 11의 `x=y ⟹ [y]⊆[x]`와 같은 방향(값의 흐름).
- **능력(capability)은 x → y 방향**: x에서 어떤 연산을 하면, 그 객체는 실제로 y(원본)이므로 **y도 그 능력을 가져야** 함(`⟦x⟧_c ⊆ ⟦y⟧_c`). 요구사항이 사용처(x)에서 원본(y)으로 거슬러 흐릅니다.

**비유 — 서브타이핑(강의 3~4)**: "능력이 더 많은 타입이 서브타입"입니다. x로 쓰려면 y는 x가 요구하는 능력을 **다 갖춰야**(더 많이 가진 게 OK). 능력 요구가 반대로 흐르는 것은 함수 인자의 반변성(contravariance)과 같은 원리.¹⁰

**각주**

¹⁰ 출처는 공변(covariant, 값 흐름 따라), 능력 요구는 반변(contravariant, 요구 흐름 거슬러). 강의 4의 함수 서브타이핑(인자는 반변, 결과는 공변)과 통하는 구조입니다. 이 방향성을 헷갈리면 분석이 틀리니 시험 포인트.

## 슬라이드 46: Solving Constraints

### 원문 내용
> - Each constraint has one of the following forms:
>   - t ∈ x
>   - x ⊆ y
> - We can use the cubic algorithm

### 번역
> - 각 제약식은 다음 두 형태 중 하나다: `t ∈ x`, `x ⊆ y`
> - **cubic 알고리즘(강의 11)**을 그대로 쓸 수 있다

### 해설

**개념 설명 — 강의 11의 직접 재사용**

슬라이드 44·45의 제약식들을 보면 모두 `t∈x`(토큰 심기)와 `x⊆y`(포함 전파) 두 형태뿐입니다 — 강의 11 슬라이드 8의 세 형태 중 조건부(`t∈x⇒y⊆z`)는 없고 단순한 둘만. 따라서 강의 11의 **워크리스트 기반 cubic 알고리즘**으로 최소 해를 O(n³)에 구합니다.

이것이 "정적 분석을 배우는 이유"의 좋은 증거입니다: 강의 11에서 만든 **하나의 범용 알고리즘**이, 함수 호출 분석(강의 11)·출력 매개변수와 무관한 I/O 타입 추론(여기)에 재사용됩니다.

**슬라이드 연결**: 실제 풀이 예가 슬라이드 47~48.

## 슬라이드 47: Example — Constraints

### 원문 내용
> ```c
> x = fopen(...);
> y = stdin;
> if (...) {
>   z = x;
> } else {
>   z = y;
> }
> fgetc(z);
> ```
> - file ∈ ⟦x⟧_o
> - stdin ∈ ⟦y⟧_o
> - ⟦x⟧_o ⊆ ⟦z⟧_o, ⟦z⟧_c ⊆ ⟦x⟧_c
> - ⟦y⟧_o ⊆ ⟦z⟧_o, ⟦z⟧_c ⊆ ⟦y⟧_c
> - read ∈ ⟦z⟧_c

### 번역
> 코드: x는 파일, y는 stdin. 조건에 따라 z=x 또는 z=y. 그 후 `fgetc(z)`(z에서 읽기).
> 제약식: file∈⟦x⟧_o, stdin∈⟦y⟧_o; 대입으로 출처는 x,y→z(⊆⟦z⟧_o), 능력은 z→x,y(⟦z⟧_c⊆); read∈⟦z⟧_c.

### 해설

**개념 설명**

슬라이드 44·45 규칙을 기계적으로 적용:
- 생성: `file∈⟦x⟧_o`, `stdin∈⟦y⟧_o`.
- `z=x`: `⟦x⟧_o⊆⟦z⟧_o`(출처 x→z), `⟦z⟧_c⊆⟦x⟧_c`(능력 z→x). `z=y`도 동일하게.
- 연산 `fgetc(z)`: `read∈⟦z⟧_c`.

`if`의 두 분기는 둘 다 가능하다고 보고 양쪽 제약을 모두 생성(강의 11 슬라이드 4와 같은 보수적 처리). 해가 슬라이드 48.

## 슬라이드 48: Example — Solution

### 원문 내용
> - ⟦x⟧_o = {file}, ⟦x⟧_c = {read}
> - ⟦y⟧_o = {stdin}, ⟦y⟧_c = {read}
> - ⟦z⟧_o = {file, stdin}, ⟦z⟧_c = {read}

### 번역
> - x: 출처 {file}, 능력 {read}
> - y: 출처 {stdin}, 능력 {read}
> - z: 출처 {file, stdin}, 능력 {read}

### 해설

**단계별 유도**

- `⟦z⟧_o`: x(file)와 y(stdin) 양쪽에서 흘러오므로 `{file, stdin}`.
- `⟦z⟧_c`: `fgetc(z)`로 `read∈⟦z⟧_c`.
- 능력은 z→x, z→y로 흐르므로 `⟦x⟧_c⊇{read}`, `⟦y⟧_c⊇{read}` → x,y도 read 능력 필요.

**해석**: z는 출처가 둘(file 또는 stdin)이라 단일 타입을 못 줍니다 → 능력 트레이트(`Read`)로 추상화해야 함(슬라이드 49). x,y는 출처가 하나라 구체 타입(`File`,`Stdin`) 가능. 이 해석이 슬라이드 49의 변환 규칙.

## 슬라이드 49: Translation Rules

### 원문 내용
> - If a stream has a single origin, use the type corresponding to that origin
> - If a stream has multiple origins, use the trait corresponding to the required capabilities

### 번역
> - 스트림의 **출처가 하나**면 → 그 출처에 해당하는 **구체 타입**을 사용
> - 스트림의 **출처가 여럿**이면 → 요구되는 **능력에 해당하는 트레이트**를 사용

### 해설

**개념 설명 — 출처·능력 → 타입·트레이트**

분석 결과(`⟦x⟧_o`, `⟦x⟧_c`)를 Rust 타입으로:
- **단일 출처**: 그 타입을 직접(`{file}`→`File`, `{stdin}`→`Stdin`). 가장 구체적.
- **다중 출처**: 한 타입으로 못 묶으니, **공통 능력 트레이트**로 추상화(`Box<dyn Read>` 등). 출처가 file이든 stdin이든 read만 하면 되니 `dyn Read`면 충분.

이는 강의 11 슬라이드 18(CHA/RTA)의 "가능한 타입 집합이 여럿이면 공통 상위로 추상화"와 통하는 발상입니다.

**슬라이드 연결**: 실제 변환이 슬라이드 50.

## 슬라이드 50: Translation Example

### 원문 내용
> ```c
> x = fopen(...);
> y = stdin;
> if (...) { z = x; } else { z = y; }
> fgetc(z);
> ```
> ⇒
> ```rust
> let x: File;
> let y: Stdin;
> let z: Box<dyn Read>;
>
> x = File::open(...).unwrap();
> y = stdin();
> if ... {
>   z = Box::new(x);
> } else {
>   z = Box::new(y);
> }
> z.read(...);
> ```

### 번역
> 슬라이드 47~48의 해를 적용:
> - x(출처 {file}) → `File`, y(출처 {stdin}) → `Stdin` (단일 출처 → 구체 타입)
> - z(출처 {file,stdin}, 능력 {read}) → `Box<dyn Read>` (다중 출처 → 능력 트레이트)
> - `fgetc(z)` → `z.read(...)`

### 해설

**개념 설명 — 모든 조각이 맞춰지는 순간**

출처·능력 분석(cubic) → 변환 규칙(슬라이드 49) → 최종 Rust 코드. z는 두 출처를 합치므로 `Box<dyn Read>`(동적 디스패치 트레이트 객체)로, x·y는 구체 타입으로. C의 단일 `FILE*`이 출처·능력에 따라 적절한 타입/트레이트로 분화됐습니다. 메모리 안전(슬라이스)·타입 안전(능력 트레이트)을 모두 확보.

**배경 지식**: `Box<dyn Read>`는 "힙에 있는, Read를 구현한 어떤 타입"을 가리키는 **트레이트 객체**입니다. 출처가 컴파일 타임에 안 정해지므로(if 분기) 동적 디스패치가 필요 — 강의 11의 일급 함수·가상 메서드와 같은 "런타임에 대상이 정해지는" 상황.

## 슬라이드 51: Summary

### 원문 내용
> - Output parameters in C can be replaced with tuples, Option, and Result in Rust
> - Analysis tracks abstract read/write sets and integer values with write-set sensitivity, which distinguishes different write sets
> - C streams have the same type FILE *, while Rust has different types and traits for different origins and capabilities
> - Origin and capability analysis solves membership/subset constraints with the cubic algorithm

### 번역
> - C의 출력 매개변수는 Rust의 튜플·`Option`·`Result`로 대체 가능
> - 분석은 **추상 읽기/쓰기 집합**과 **정수값**을 추적하며, **쓰기 집합 민감(write-set sensitivity)**으로 서로 다른 쓰기 집합을 구분한다
> - C 스트림은 모두 `FILE *` 타입이지만, Rust는 출처·능력별로 다른 타입·트레이트를 가진다
> - **출처·능력 분석**은 멤버십(`t∈x`)·포함(`x⊆y`) 제약을 **cubic 알고리즘**으로 푼다

### 해설

**전체 정리 — 강의 13의 두 주제**

**주제 1: 출력 매개변수 → ADT**
- 읽기/쓰기 집합 분석(전방, R은 may·W는 must)으로 출력 매개변수 식별(반환 시 W에 든 것).
- 쓰기 집합 민감 + 정수 집합 도메인으로 부분 함수의 성공/실패와 반환값 구분.
- 결정표(슬라이드 29): must-output→튜플, may-output+구별가능→Result, 구별불가→Option.

**주제 2: I/O FILE* → 타입/트레이트**
- 출처·능력 분석: 변수마다 `⟦x⟧_o`(출처)·`⟦x⟧_c`(능력) 집합, 생성·연산이 토큰을 심고 대입이 전파(출처는 공변·능력은 반변).
- 제약식이 `t∈x`/`x⊆y`뿐 → **강의 11 cubic 알고리즘 재사용**.
- 단일 출처→구체 타입, 다중 출처→능력 트레이트(`Box<dyn Read>`).

**다른 강의와의 연결 (파일 간 연결성)**

- ← **강의 2 (Rust)**: ADT(`Option`/`Result`/튜플), 트레이트, 소유권(닫힌 스트림 방지).
- ← **강의 3~4 (타입·서브타이핑)**: 능력 전파의 공변/반변, "능력 많은 게 서브타입".
- ← **강의 5~6 (격자·도메인)**: R(⊆)·W(⊇)의 격자, 정수 집합 vs 구간 도메인 선택, k-제한 추상화.
- ← **강의 7~8 (데이터플로우)**: 읽기/쓰기 집합 전방 분석, may/must 구분.
- ← **강의 10 (절차간)**: 상향식 모듈러·함수 요약(두 주제 공통 틀).
- ← **강의 11 (제어 흐름·cubic)**: 출처·능력 분석이 cubic 알고리즘을 직접 재사용. 다중 출처→트레이트는 CHA/RTA의 "상위로 추상화"와 동형.
- ← **강의 12 (응용 1)**: 같은 "암묵 정보 복원" 패러다임, 상향식 요약.

**가장 큰 교훈**: 강의 11~13을 관통하는 것은 **"제약식 + cubic 알고리즘"**과 **"데이터플로우 + 함수 요약"**이라는 두 범용 도구가, 락·출력 매개변수·I/O라는 전혀 다른 문제들에 반복 적용된다는 점입니다. 정적 분석은 문제마다 새 기법을 만드는 게 아니라, **소수의 강력한 틀을 도메인에 맞게 변형**하는 것입니다.

## 마치며

강의 13은 강의 12와 함께 정적 분석의 **실전 응용**을 보여 줍니다. 두 독립 주제(출력 매개변수, I/O)를 통해, (1) 새 분석을 설계할 때 적절한 **추상 도메인 선택**(집합 vs 구간, 슬라이드 28)이 결정적임을, (2) **경로/쓰기집합 민감도**로 정밀도를 높이는 법을, (3) 강의 11의 **cubic 알고리즘이 얼마나 범용적인지**를 배웠습니다. 시험에서는 (a) 읽기/쓰기 집합 추적으로 출력 매개변수 판정(슬라이드 19~23), (b) 집합 도메인이 구간보다 나은 이유(슬라이드 28), (c) 출처·능력 제약식 세우고 cubic으로 풀기(슬라이드 47~48), (d) 출처 공변·능력 반변의 방향(슬라이드 45)이 자주 나옵니다.
