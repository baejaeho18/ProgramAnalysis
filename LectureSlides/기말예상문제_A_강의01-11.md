### 문제 1-1 [개념·서술] (S, 슬라이드 19~20)
**건전성(soundness)**과 **완전성(completeness)**을 각각 정의하고, 과근사(over-approximation)/과소근사(under-approximation), 거짓 음성(false negative)/거짓 양성(false positive)과의 대응을 밝혀라. 그리고 다음 코드에서 실제 가능한 x의 값이 {1, 2}일 때,
```c
if (...) { x = 1; } else { x = 2; }
return x;
```
(a) 건전한 분석이 말할 수 있는 답과 말할 수 없는 답, (b) 완전한 분석이 말할 수 있는 답과 말할 수 없는 답을 각각 예와 함께 답하라.

**풀이.**
- **건전성**: 분석이 "어떤 동작이 불가능하다"고 하면 실제로도 불가능하다. 가능한 동작을 **과근사**(실제 ⊆ 분석)하며, 실제 가능한 동작을 빠뜨리지 않으므로 **거짓 음성 없음**(대신 거짓 양성 = 헛경보는 가능).
- **완전성**: 분석이 "어떤 동작이 가능하다"고 하면 실제로도 가능하다. 가능한 동작을 **과소근사**(분석 ⊆ 실제)하며, 불가능한 것을 가능하다 하지 않으므로 **거짓 양성 없음**(대신 실제 가능한 것을 놓칠 수 있음).

(a) 건전한 분석은 {1,2}를 **포함하는** 집합이면 모두 답할 수 있다: "x는 1 또는 2", "x는 양의 정수", "x는 임의 정수" 모두 OK. 그러나 "x는 1"은 **불가** — 실제 가능한 값 2를 빠뜨리므로(과근사 위반 = unsound).
(b) 완전한 분석은 {1,2}에 **포함되는** 집합이면 모두 답할 수 있다: "x는 1", "x는 2", "x는 1 또는 2" 모두 OK. 그러나 "x는 양의 정수"는 **불가** — 실제론 불가능한 3, 4 등을 가능하다고 암시하므로(과소근사 위반 = incomplete).
가장 정밀한 답 "x는 1 또는 2"는 정확히 {1,2}이므로 건전이자 완전이다. 이렇게 둘 다 가질 수 있는 것은 이 코드에 루프·재귀가 없기 때문이며, 일반적으로는 Rice 정리(슬22)가 둘의 동시 달성을 막는다.

### 문제 1-2 [증명·유도] (M, 슬라이드 22~23)
Rice 정리를 진술하고, 다음 코드에 대해 "x가 1이 될 수 있는가?"라는 분석 질문이 **정지 문제(halting problem)만큼 어렵다**는 것을 환원(reduction) 논증으로 보여라. 이로부터 "건전성 또는 완전성 중 하나를 포기해야 한다"는 결론이 어떻게 따라오는지 설명하라.
```c
if (...) { f(); x = 1; } else { x = 2; }
return x;
```

**증명.**
**Rice 정리**: 튜링 완전 언어로 쓰인 프로그램의 동작에 관한 **비자명한(non-trivial) 성질은 모두 결정 불가능(undecidable)**하다. (비자명 = 어떤 프로그램은 갖고 어떤 프로그램은 안 갖는 의미 있는 성질.)

**환원 논증.** 위 코드에서 x가 1이 되려면 then 분기가 실행되고 `f()` 호출 **이후의** `x = 1`에 도달해야 한다. 즉 **x가 1이 될 수 있다 ⟺ f()가 종료한다**(종료해야만 다음 줄에 도달). 따라서 "x가 1이 될 수 있나?"를 항상 정확히 판정하는 알고리즘 A가 있다면, 임의의 함수 f에 대해 이 코드 틀에 f를 끼워 넣고 A를 돌려 **f의 정지 여부를 판정**할 수 있다. 그런데 정지 문제는 튜링이 결정 불가능함을 증명했으므로, 그런 A는 존재할 수 없다.

**결론 유도.** 정확한 판정(= 건전이면서 완전인 분석)이 불가능하므로, 분석은 반드시 **근사**해야 한다. 근사 방향이 두 가지뿐이다 — 가능한 동작을 더 크게 보는 과근사(건전성 유지, 완전성 포기)거나, 더 작게 보는 과소근사(완전성 유지, 건전성 포기). 따라서 비자명한 성질의 분석은 둘 중 하나를 선택해야 하며, 이 선택이 정적 분석 설계의 출발점이 된다(슬24~26: 변환엔 건전성, 테스트는 완전성).

### 문제 1-3 [개념·서술] (M, 슬라이드 25~26)
(a) 의미 보존 변환(semantics-preserving transformation)에는 왜 **건전한** 분석이 필요한지, "완전한 분석이 `x는 1`이라 말해도 else 가지를 제거할 수 없는" 이유를 들어 설명하라.
(b) 버그 찾기에서 건전한 분석과 완전한 분석의 장단점을 비교하고, 다익스트라의 격언 "테스트는 버그의 존재는 보일 수 있어도 부재는 결코 보일 수 없다"가 테스트(동적 분석)의 어떤 성질을 말하는지, 그리고 왜 사람들이 테스트를 보완하려고 **건전한 정적 분석**을 설계하는지 답하라.

**풀이.**
(a) `if (x == 1) {...} else {...}`에서 else를 지우려면 "x는 1 외의 값을 절대 갖지 않는다"는 **확신**이 필요하다. **완전한** 분석의 "x는 1"은 "x가 1일 수 있다"는 뜻일 뿐이다 — 완전한 분석은 가능한 동작을 놓칠 수 있으므로(과소근사), x가 1이 아닌 경우를 빠뜨렸을 수 있다. 그 상태에서 else를 지우면 실제 실행에서 의미가 바뀔 수 있다. 반면 **건전한** 분석의 "x는 1"은 과근사조차 {1}이라는 뜻이므로 다른 값은 절대 불가능 → else를 안전하게 제거할 수 있다. 따라서 **변환·검증에는 건전성**이 필요하다.
(b) 건전한 분석은 빠뜨림이 없으므로 **버그 부재를 증명**할 수 있지만 헛경보(false alarm)가 잦다. 완전한 분석은 경보가 모두 진짜지만(헛경보 없음) 일부 버그를 놓친다. **테스트는 완전한 분석**이다 — 실제 실행으로 관찰한 버그는 모두 진짜(거짓 양성 없음)지만, 돌려보지 않은 입력의 버그는 못 보므로 "버그가 없다"는 증명은 불가능하다(다익스트라의 격언이 정확히 이 점). 그래서 완전한 테스트가 못 하는 "부재 증명"을 맡기 위해 **건전한 정적 분석**을 만들어 둘을 상보적으로 쓴다.

### 문제 1-4 [개념·서술] (M, 슬라이드 27~29)
"모든 동작이 가능하다"고 답하는 분석은 **자명하게 건전(trivially sound)**하다. (a) 왜 그런지, 그리고 왜 그 분석이 쓸모없는지 설명하라. (b) 이로부터 도출되는 정적 분석 설계의 **필수 목표 2가지**와 **추가 목표 2가지**를 쓰고, 어느 목표들 사이에 trade-off가 흔히 존재하는지 답하라. (c) 정밀도(precision)의 정의를 "집합의 크기"로 쓰라.

**풀이.**
(a) 건전성은 "실제 가능한 동작을 빠뜨리지 않음"인데, "모든 게 가능하다"는 답은 모든 동작을 포함하므로 절대 아무것도 빠뜨리지 않는다 → 자명하게 건전. 그러나 "이 변수는 어떤 정수든 될 수 있다"는 항상 참이되 아무 정보도 주지 않으므로 변환·버그찾기·이해 어디에도 쓸 수 없다. 즉 **건전성만으로는 부족하고 정밀해야 유용**하다.
(b) **필수 목표**: ① 종료(termination) — 분석이 항상 유한 시간에 끝나야 함(강의 9의 위드닝이 보장 수단). ② 건전성(soundness) — 빠뜨리지 않아야 함(강의 18~20의 추상 해석이 수학적 기반). **추가 목표(유용성)**: ③ 효율(efficiency), ④ 정밀도(precision). trade-off는 흔히 **효율 ↔ 정밀도** 사이에 존재한다 — 더 정밀한 분석은 보통 더 느리다(예: 문맥 민감도 k 증가, 강의 10).
(c) 건전성을 유지하는 한(실제를 포함하는 한), **계산된 가능 동작 집합이 작을수록 더 정밀**하다. 예: 실제가 {1,2}일 때 "x는 1 또는 2" > "x는 양의 정수" > "x는 임의 정수" 순으로 정밀. 이는 통상의 precision = 참 양성 / 전체 양성 개념과 일치한다.

### 문제 1-5 [계산·추적] (S, 슬라이드 19~20)
어떤 프로그램에서 변수 x의 실제 가능한 값 집합이 정확히 {1, 2}이다. 다음 네 분석 결과 각각에 대해 (i) 건전한가, (ii) 완전한가를 판정하고 이유를 한 줄씩 쓰라.
(a) "x ∈ {1}"  (b) "x ∈ {1, 2, 3}"  (c) "x ∈ {1, 2}"  (d) "x ∈ ℤ (임의 정수)"

**풀이.**
판정 기준: 건전 ⟺ {1,2} ⊆ 답(빠뜨림 없음), 완전 ⟺ 답 ⊆ {1,2}(군더더기 없음).
- (a) {1}: {1,2} ⊄ {1} (2를 빠뜨림) → **건전 X**; {1} ⊆ {1,2} → **완전 O**.
- (b) {1,2,3}: {1,2} ⊆ {1,2,3} → **건전 O**; 3은 실제 불가능 → **완전 X**.
- (c) {1,2}: 정확히 일치 → **건전 O, 완전 O** (가장 정밀한 답).
- (d) ℤ: 모든 것을 포함 → **건전 O**(자명하게); 거의 모든 원소가 불가능 → **완전 X**. 건전한 답 중 가장 부정밀하다.
교훈: 건전한 답들 (b)(c)(d) 중에서 집합이 작을수록 정밀하며(슬28), (c)가 최선이다.

## 강의 2 — Introduction to Rust

### 문제 2-1 [개념·서술] (M, 슬라이드 10~12)
Rust의 **소유권(ownership)** 규칙을 서술하고, 다음 코드가 컴파일되지 않는 이유를 소유권 이동(move)과 use-after-free 방지의 관점에서 설명하라. 또 정수 타입이었다면 왜 에러가 안 나는지(슬라이드 11) 답하라.
```rust
let s = "hi".to_string();
let t = s;
drop(t); // 힙 메모리 해제
println!("{s}"); // ?
```

**풀이.**
**소유권 규칙**: 각 값은 **최대 한 변수가 소유**하며, 다른 변수에 대입하거나 함수에 넘기면 소유권이 **이동(move)**한다. 컴파일러는 소유권이 이동된 변수의 이후 사용을 금지한다.
위 코드에서 `let t = s;`로 문자열의 소유권이 s에서 t로 이동했고, s는 무효가 된다. `drop(t)`로 힙 메모리가 해제된 뒤 `println!("{s}")`가 s를 읽으면 해제된 메모리를 읽는 **use-after-free**가 된다. Rust 컴파일러는 "s는 이미 이동됨"이라는 정적 검사로 이 줄을 **컴파일 에러**로 거부한다 — C라면 런타임 크래시·보안 취약점이 될 버그가 컴파일 타임에 차단된다. 값이 한 소유자만 가지면 해제도 정확히 한 번만 일어나므로 이중 해제(double free)도 원천 차단된다.
정수라면: 정수 등 원시 타입은 **Copy**를 구현하므로 `let t = s`가 이동이 아니라 **복사**가 된다(슬11). 원본 s가 그대로 유효하므로 이후 사용에 문제가 없다. 힙 데이터(String, Vec)는 Copy가 아니므로 양쪽을 쓰려면 명시적 `clone()`(깊은 복사)이 필요하다.

### 문제 2-2 [개념·서술] (M, 슬라이드 14~15)
**앨리어싱 XOR 가변성(aliasing XOR mutability)** 규칙을 진술하고, 다음 코드가 거부되는 이유를 use-after-free 시나리오로 설명하라. 그리고 이 규칙이 너무 엄격할 때의 탈출구인 `RefCell<T>`가 같은 규칙을 **언제** 검사하는지, 그 대가는 무엇인지 답하라.
```rust
let mut v = vec![1, 2, 3];
let r = &v[0];
v.push(4); // 벡터 재할당 가능
println!("{r}"); // ?
```

**풀이.**
**규칙**: 같은 값에 대한 **공유 참조(&T)는 여러 개 공존 가능**하지만, **가변 참조(&mut T)는 다른 어떤 참조(공유든 가변이든)와도 공존 불가** — 즉 "공유(앨리어싱)와 변경(가변성)은 동시에 안 된다."
위 코드에서 `r`은 `v[0]`을 빌린 공유 참조다. 그 상태에서 `v.push(4)`는 v에 대한 가변 접근이며, 벡터가 가득 차 있으면 **메모리를 재할당**해 기존 버퍼를 해제할 수 있다. 그러면 r은 해제된 메모리를 가리키게 되어(`println!("{r}")`가 use-after-free) — 이를 막기 위해 컴파일러는 r이 살아 있는 동안 v의 가변 접근을 금지한다(컴파일 에러).
`RefCell<T>`는 공유 참조를 통해서도 내부를 바꿀 수 있게 하는 **내부 가변성** 장치인데, 같은 XOR 규칙을 **컴파일 타임 대신 런타임에** `borrow`/`borrow_mut`로 검사한다. 대가: 위반이 컴파일 에러가 아니라 **런타임 패닉**이 되고, 정적으로 보장되던 불변식이 약해져 정적 분석도 어려워진다.

### 문제 2-3 [개념·서술] (F, 슬라이드 28~34)
rustc 컴파일러 파이프라인의 다섯 표현(AST, HIR, THIR, MIR, 기계어)을 순서대로 나열하고 각 단계에서 무엇이 달라지는지 한 줄씩 쓰라. 그리고 (a) 대부분의 정적 분석에 **MIR**이 적합한 두 가지 이유, (b) 그럼에도 **타입 분석(강의 3~4)은 HIR**을 쓰는 이유를 슬라이드 34에 근거해 답하라.

**풀이.**
파이프라인: 소스 →(파싱)→ **AST** →(디슈가링·심볼 해석)→ **HIR** →(타입 검사)→ **THIR** →(낮추기)→ **MIR** →(빌림 검사·최적화·코드 생성)→ 기계어.
- **AST**: 코드를 텍스트가 아닌 트리로; 매크로 전개, 서브모듈 통합. 심볼은 아직 미해석.
- **HIR**: 디슈가링(`for`→`loop` 등)과 **심볼 해석**(각 x가 어느 선언인지 확정) 완료.
- **THIR**: 타입 검사 후 — 오버로딩 해소, 암묵적 강제 변환 명시화(`x`→`&*x`).
- **MIR**: **제어 흐름 그래프(CFG)** — 함수 = 기본 블록 + 간선, 블록 = 문장(대입)들 + 종결자(jump/switch/call/return).

(a) MIR이 적합한 이유: ① CFG 구조라 **실행 순서가 명시적** — 흐름 감각 분석(데이터플로우, 강의 7~9)에 필수. ② **언어 구문이 적어** 다룰 경우의 수가 작다.
(b) 타입 분석이 HIR을 쓰는 이유: 타입 분석은 흐름 무감각이라 실행 순서가 덜 중요하고, 결과가 **소스 구조에 가까워야** 하며 **부모 노드 순회**가 필요하다. HIR은 심볼이 해석되어 있으면서 소스에 가깝고 부모 순회가 편리하며, 타입이 잘못된(ill-typed) 코드도 분석할 수 있다(THIR은 타입 검사를 통과해야 만들어짐).

### 문제 2-4 [계산·추적] (M, 슬라이드 32~33·36~37)
(a) `fn add(x: i32, y: i32) -> i32 { x + y }`를 MIR의 Local 번호 규칙(`_0`, `_1`, ...)으로 번역하라.
(b) 다음 코드의 MIR을 기본 블록(bb0~bb3)으로 분해하고, 루프가 CFG에서 어떻게 표현되는지 밝혀라.
```rust
let mut x = 0; let mut y = 0;
while x < 10 { x += 1; y += x; }
return y;
```

**풀이.**
(a) 규칙: **`_0` = 반환값(RET), `_1`, `_2`, ... = 매개변수**(선언 순), 이후 = 지역 변수. 따라서 `add`의 MIR 본문은:
```
_0 = Add(_1, _2);
return;
```
(b) 슬라이드 33 그대로:
- **bb0**: `x = 0; y = 0;` 후 `jump bb1` (초기화)
- **bb1**: `t = x < 10;` 후 `switch t` (참 → bb2, 거짓 → bb3) (조건 검사)
- **bb2**: `x = x + 1; y = y + x;` 후 `jump bb1` (본문, 조건으로 복귀)
- **bb3**: `return y;` (탈출)

루프는 **bb2 → bb1 순환(역방향) 간선**으로 표현된다. 이 순환 간선 때문에 bb1의 상태가 자기 자신(본문을 거친 결과)에 의존하는 순환 방정식이 생기고, 이것이 강의 6~7의 고정점 반복과 강의 9의 위드닝이 필요해지는 구조적 원인이다.

### 문제 2-5 [개념·서술] (M, 슬라이드 19~23)
(a) struct와 enum이 각각 곱 타입·합 타입인 이유를 쓰고, 둘을 합쳐 무엇이라 부르는지 답하라. (b) `Option<T>`와 `Result<T,E>`의 변형(variant)들을 쓰고, 각각이 해결하는 문제(널 포인터 / 에러 처리)를 설명하라. (c) Rust에 예외(exception)가 없는 대신 에러가 어떻게 표현·전파되는지 `?` 연산자의 동작과 함께 답하라.

**풀이.**
(a) **struct**는 여러 필드를 **모두** 갖는 타입("이것 *그리고* 저것") = **곱(product) 타입**. **enum**은 여러 변형 중 **하나**인 타입("이것 *또는* 저것") = **합(sum) 타입**. 둘을 합쳐 **대수적 자료형(ADT, algebraic data type)**이라 부른다.
(b) `Option<T> = Some(T) | None` — 값의 선택적 존재를 타입으로 표현한다. 값을 꺼내려면 `match`로 `None` 경우를 반드시 다뤄야 하므로, 널 역참조 크래시(C/Java의 null 문제)가 타입 시스템 수준에서 제거된다. `Result<T,E> = Ok(T) | Err(E)` — 성공값 T 또는 **에러 정보 E**를 담는다. Option과 달리 실패의 이유를 전달할 수 있다.
(c) Rust는 예외 대신 에러를 `Option`/`Result` **값**으로 명시한다(복구 불가능한 상황만 `panic`으로 종료). `?` 연산자는 "실패(`None`/`Err`)면 그 값을 즉시 반환하고, 성공이면 안의 값을 꺼낸다"로 에러 전파를 간결하게 한다. 에러가 타입에 드러나므로 처리를 빠뜨릴 수 없다 — 강의 13의 C 에러 코드 → `Result` 변환이 이 장치를 활용한다.

### 문제 3-1 [계산·추적] (M, 슬라이드 11~14)
다음 함수에서 슬라이드 11의 규칙으로 타입 제약을 **모두** 수집하고 해를 구하라.
```rust
fn f(x, y) { x + y }
```

**풀이.**
제약 수집:
- 함수 정의 규칙: `⟦f⟧ = fn(⟦x⟧, ⟦y⟧) → ⟦x+y⟧` (함수 타입 = 매개변수 타입들 → 본문 마지막 식의 타입)
- 덧셈 규칙: `⟦x+y⟧ = ⟦x⟧ = ⟦y⟧ = i32` (피연산자와 결과 모두 i32)

해: 덧셈 규칙으로 `⟦x⟧ = ⟦y⟧ = ⟦x+y⟧ = i32`가 즉시 결정되고, 이를 함수 규칙에 대입하면 `⟦f⟧ = fn(i32, i32) → i32`.
모든 제약을 만족하는 해가 존재하므로 분석 결과는 "ok"(타입 오류 없음 보장). 타입 명시를 모두 지웠는데도 덧셈 하나가 모든 타입을 결정함을 보여 주는 예다.

### 문제 3-2 [계산·추적] (M, 슬라이드 15~16)
다음 고차 함수 프로그램의 제약을 수집하고 해를 구하라.
```rust
fn f(x) { x }
fn g(y) { y(1) }
fn h() { g(f) }
```

**풀이.**
제약:
- `fn f(x){x}`: `⟦f⟧ = fn(⟦x⟧) → ⟦x⟧`
- `fn g(y){y(1)}`: `⟦g⟧ = fn(⟦y⟧) → ⟦y(1)⟧`
- 호출 `y(1)`: `⟦y⟧ = fn(⟦1⟧) → ⟦y(1)⟧`, 그리고 `⟦1⟧ = i32`
- `fn h(){g(f)}`: `⟦h⟧ = fn() → ⟦g(f)⟧`
- 호출 `g(f)`: `⟦g⟧ = fn(⟦f⟧) → ⟦g(f)⟧`

풀이 과정: `g(f)`의 제약과 g의 정의 제약을 단일화하면(같은 생성자 fn의 인자끼리) `⟦y⟧ = ⟦f⟧`, `⟦y(1)⟧ = ⟦g(f)⟧`. `y(1)`의 제약으로 `⟦y⟧ = fn(i32) → ⟦y(1)⟧`인데 `⟦y⟧ = ⟦f⟧ = fn(⟦x⟧)→⟦x⟧`이므로 구조 분해로 `⟦x⟧ = i32`이고 `⟦y(1)⟧ = ⟦x⟧ = i32`.
최종 해: `⟦f⟧ = fn(i32)→i32`, `⟦y⟧ = fn(i32)→i32`, `⟦g⟧ = fn(fn(i32)→i32) → i32`, `⟦h⟧ = fn() → i32`. 해 존재 → ok. 함수를 인자로 넘기는 고차 프로그램의 타입도 단일화가 자동으로 추론한다.

### 문제 3-3 [계산·추적/개념] (M, 슬라이드 17~19)
다음 세 함수 각각에 대해 제약을 세우고, 분석 결과(유일해 / 해 없음 / 무한히 많은 해)를 판정하라. 무한히 많은 해인 경우 **주 타입(principal type)**을 답하라.
(a) `fn f(x) { if x { x + 1 } else { 0 } }`
(b) `fn f(x) { let y = x + 1; f }`
(c) `fn f(x) { x }`

**풀이.**
(a) 제약: if 규칙에서 `⟦x⟧ = bool`(조건은 불리언), 덧셈 규칙에서 `⟦x⟧ = i32`. 한 변수가 bool이자 i32일 수 없으므로 **해 없음 → "not ok"(타입 오류)**. 실제로도 x를 조건과 산술에 동시에 쓰는 것은 타입이 맞지 않는다.
(b) 제약: 본문이 f 자신을 반환하므로 `⟦f⟧ = fn(⟦x⟧) → ⟦f⟧`, 덧셈에서 `⟦x⟧ = i32`. 그러면 `⟦f⟧ = fn(i32) → fn(i32) → fn(i32) → ...`로 타입 변수가 **자기 자신을 포함**해 무한히 중첩된다. 재귀 타입 `μX. fn(i32)→X`가 있는 언어라면 해가 있지만, 우리 언어에는 없으므로 **해 없음**. (단일화에서는 occurs check가 이를 검출한다 — 강의 4 슬5.)
(c) 제약: `⟦f⟧ = fn(⟦x⟧) → ⟦x⟧`뿐. `⟦x⟧`를 어떤 타입으로 잡아도 만족 → `fn(i32)→i32`, `fn(bool)→bool`, ... **무한히 많은 해**. 그중 타입 변수를 남긴 **`fn(X) → X`가 주 타입** — 모든 구체 해를 포괄하는 가장 일반적인 해이며 다형성(polymorphism)의 토대다.

### 문제 3-4 [개념·서술] (S, 슬라이드 20)
슬라이드 20은 타입 추론을 선형 연립방정식 풀이에 유추한다. 선형방정식의 세 가지 결과(유일해/해 없음/무한히 많은 해)와 타입 분석의 세 결과를 대응시키고, 두 문제의 차이(왜 가우스 소거가 아니라 단일화로 푸는가)를 설명하라.

**풀이.**
대응:
| 선형방정식 | 예 | 타입 분석 | 의미 |
|---|---|---|---|
| 유일해 | x+y=4, x−y=2 → x=3,y=1 | 타입이 하나로 결정 | "ok" (예제 1·2) |
| 해 없음 | x+y=4, 2x+2y=5 (모순) | 제약 모순 | "not ok" = 타입 오류 (예제 3·4) |
| 무한히 많은 해 | x+y=4, 2x+2y=8 → x=4−y | 주 타입(타입 변수 잔존) | "ok", 다형성 (예제 5) |

차이: 선형방정식의 미지수는 **숫자**이고 등식은 수치 연산이라 가우스 소거로 푼다. 타입 제약의 미지수는 **타입(트리 구조의 항)**이고 등식은 "두 항이 같은 구조"라는 뜻이므로, 구조를 재귀적으로 분해하며 변수에 항을 바인딩하는 **단일화(unification)**로 푼다. 결과의 세 분류가 정확히 대응한다는 점이 이 유추의 핵심이며, 같은 "등식 연립" 관점이 강의 16의 선형 등식 도메인에서 다시 등장한다.

### 문제 3-5 [계산·추적/유도] (M, 슬라이드 23~32)
Union-Find에서 `MakeSet(A); MakeSet(B); MakeSet(C); MakeSet(D)` 후 다음을 순서대로 수행한다(슬라이드 26의 기본 Union: x의 루트를 y의 루트의 자식으로).
(1) `Union(A, B)` (2) `Union(C, D)` (3) `Union(B, D)` (4) `Find(A)`
(a) 각 단계 후 부모 구조를 추적하라. (b) (4)에서 **경로 압축**을 적용하면 구조가 어떻게 바뀌는지 쓰라. (c) 경로 압축과 union by rank를 함께 쓸 때의 시간 복잡도와, 그것이 어떤 분석을 빠르게 만드는지 답하라.

**풀이.**
(a)
- 초기: A, B, C, D 모두 자기 자신이 부모(각자 루트, 4개의 단독 그룹).
- (1) `Union(A,B)`: Find(A)=A, Find(B)=B, 다르므로 `A.parent ← B`. 그룹 {A,B}(루트 B), {C}, {D}.
- (2) `Union(C,D)`: `C.parent ← D`. 그룹 {A,B}(루트 B), {C,D}(루트 D).
- (3) `Union(B,D)`: Find(B)=B, Find(D)=D, `B.parent ← D`. 그룹 {A,B,C,D}(루트 D). 이때 A→B→D의 깊이 2 사슬이 생긴다.
- (4) `Find(A)`: A→B→D로 올라가 **D 반환**.

(b) 경로 압축: Find(A)가 지나간 경로의 모든 노드를 루트에 직접 연결 — `A.parent ← D`, `B.parent ← D`. 트리가 평탄해져(D 아래 A, B, C 나란히) 이후 Find가 O(1)에 가까워진다.
(c) 경로 압축 + union by rank(작은 랭크 트리를 큰 랭크 루트 아래에)를 함께 쓰면 **O(n·α(n))** — α는 역 아커만 함수로 실용 범위에서 4 이하의 사실상 상수, 즉 거의 선형. 이 효율이 단일화 기반 분석 — 이 강의의 타입 추론, 그리고 강의 14의 Steensgaard 포인터 분석 — 이 "거의 선형 시간"인 이유다.

### 문제 4-1 [계산·추적/서술] (M, 슬라이드 2~7)
단일화 구현은 **Union-Find**(타입 변수끼리의 동치)와 **사상 M**(타입 변수 ↔ 고유 타입 바인딩)의 두 메커니즘을 쓴다. 제약 `⟦x⟧ = ⟦y⟧`, `⟦y⟧ = i32`, `⟦x⟧ = ⟦z⟧`를 이 순서로 Unify로 처리할 때 각 단계의 Union-Find 상태와 M의 변화를 추적하고, 마지막에 `DeepResolve(⟦z⟧)`가 무엇을 반환하는지 답하라.

**풀이.**
(사전에 MakeSet(⟦x⟧), MakeSet(⟦y⟧), MakeSet(⟦z⟧) 호출, M은 모두 미정의.)
1. `Unify(⟦x⟧, ⟦y⟧)`: Resolve 결과 둘 다 미바인딩 타입 변수 → **둘 다 변수** 경우 → `Union(⟦x⟧, ⟦y⟧)`. 이제 {⟦x⟧,⟦y⟧}가 한 동치류(대표를 ⟦y⟧라 하자).
2. `Unify(⟦y⟧, i32)`: Resolve(⟦y⟧) = 대표 변수(미바인딩), Resolve(i32) = i32(고유 타입). **한쪽만 변수** 경우 → occurs check: i32 안에 그 변수가 없으므로 통과 → `M[대표] ← i32`. 이제 x·y의 동치류가 i32로 바인딩됨.
3. `Unify(⟦x⟧, ⟦z⟧)`: Resolve(⟦x⟧) = Find(⟦x⟧)의 대표에 M이 정의됨 → **i32**. Resolve(⟦z⟧) = 미바인딩 변수. 한쪽만 변수 → `M[⟦z⟧의 대표] ← i32`.

`DeepResolve(⟦z⟧)`: Find로 대표를 찾고 M에 i32가 바인딩되어 있으므로 재귀적으로 풀어 **i32** 반환. (DeepResolve는 Resolve와 달리 타입 안의 변수까지 끝까지 구체화한다 — 예컨대 `fn(X)→X`에서 X=i32가 밝혀졌다면 `fn(i32)→i32`를 돌려준다.)
요점: **변수=변수는 Union, 변수=고유타입은 M 기록, 같은 생성자끼리는 인자별 재귀 Unify, 다른 생성자는 실패** — 이 네 갈래가 Unify의 전부다.

### 문제 4-2 [개념·서술] (S, 슬라이드 5)
**occurs check**가 무엇이고 왜 필요한지 설명하라. `Unify(⟦f⟧, fn(i32) → ⟦f⟧)`를 처리할 때 무슨 일이 일어나는지, 그리고 이것이 강의 3 슬라이드 18의 어떤 예제와 대응하는지 답하라.

**풀이.**
occurs check는 "타입 변수 X를 타입 T로 바인딩하기 전에, **T 안에 X 자신이 나타나는지** 검사"하는 절차다. X가 T 안에 나타나면 `X = ...X...`라는 **무한 타입**(자기 자신을 포함하는 타입)이 만들어지므로 단일화를 **실패**시킨다.
`Unify(⟦f⟧, fn(i32)→⟦f⟧)`에서 좌변은 변수, 우변은 고유 타입이므로 바인딩을 시도하는데, `Occurs(⟦f⟧, fn(i32)→⟦f⟧)`가 우변의 인자들을 재귀 검사하다 반환 위치에서 ⟦f⟧ 자신을 발견 → **단일화 실패**(타입 오류 판정).
이는 강의 3 슬18의 `fn f(x){ let y = x+1; f }` 예제 — f가 자기 자신을 반환해 `⟦f⟧ = fn(i32)→⟦f⟧`가 되는 — 의 구현 수준 대응물이다. 재귀 타입 `μX. fn(i32)→X`를 지원하는 언어라면 해가 있지만, 우리 언어는 이를 금지하므로 occurs check가 "해 없음"을 올바르게 검출한다.

### 문제 4-3 [설계·응용] (F, 슬라이드 9~17)
튜플 타입과 프로젝션 `e.i`를 지원하도록 타입 분석을 확장하는 세 가지 시도를 정리하라.
(a) 1차 시도(`⟦e⟧ = (X0,...,X_{i-1}, ⟦e.i⟧)`)가 `let x = (1, true); x.0`을 잘못 거부하는 이유.
(b) 2차 시도(최대 길이 N으로 fresh 변수 패딩)가 `let x = (1, true); x.2`를 잘못 통과시키는 이유.
(c) 올바른 해법(◇ + 부등식)이 두 예제를 모두 올바르게 판정하는 과정과, 부등식이 구현에서 **언제** 검사되는지(슬라이드 17).

**풀이.**
(a) 1차 시도는 `e.i`에 대해 "e는 **정확히 i+1개짜리** 튜플"이라는 제약 `⟦e⟧=(X0,...,X_{i-1},⟦e.i⟧)`을 만든다. `x=(1,true)`에서 `⟦x⟧=(i32, bool)`(길이 2)인데 `x.0`이 `⟦x⟧=(⟦x.0⟧)`(길이 1)을 요구 → 길이 2 튜플과 길이 1 튜플은 다른 생성자(항수가 다름)라 단일화 실패 → **정상 코드를 잘못 거부**. 본질적 원인: `e.i`는 "**적어도** i+1개"를 뜻해야 하는데 길이를 고정해 버렸다.
(b) 2차 시도는 모든 튜플을 프로그램 내 최대 길이 N으로 **fresh 변수 패딩**해 길이를 통일한다. N=3이면 `⟦x⟧=(i32, bool, X3)`이 되고, 범위 밖 접근 `x.2`도 패딩 변수 X3와 단일화되어 **해가 존재** → "ok" 판정. 실제로는 길이 2 튜플의 `.2`는 오류이므로 분석이 오류를 **놓친다(unsound)**. 1차는 과엄격, 2차는 과관대.
(c) 올바른 해법은 두 장치를 더한다. ① 타입에 **"없는 원소" ◇**를 추가하고, 튜플 생성 시 진짜 원소 뒤를 ◇로 패딩: `⟦x⟧=(i32, bool, ◇)`. ② 프로젝션 `e.i`에는 fresh 변수 패딩 제약에 더해 **부등식 `⟦e.i⟧ ≠ ◇`**(접근하는 자리는 없는 원소가 아니어야 함)를 추가.
- `x.0`: `⟦x.0⟧ = i32`로 단일화되고 `i32 ≠ ◇` 만족 → **ok** (1차의 잘못된 거부 해소).
- `x.2`: `⟦x.2⟧ = ◇`로 단일화되는데 부등식 `⟦x.2⟧ ≠ ◇` 위반 → **해 없음, 거부** (2차의 놓침 해소).
구현: 단일화(Unify)는 **등식만** 풀 수 있으므로, **먼저 모든 등식을 Unify로 풀어 타입을 확정한 뒤, 부등식들을 사후 검사**한다 — 위반이 하나라도 있으면 "not ok". 이 사례는 분석 설계가 시행착오의 과정이며, 등식만으로 부족하면 새 장치(◇·부등식)를 도입해야 함을 보여 준다.

### 문제 4-4 [개념·서술] (M, 슬라이드 18~20)
(a) 다음 코드는 런타임 타입 오류가 없는데(동적 언어의 흔한 패턴) 우리의 타입 분석은 거부한다. 그 이유를 **흐름 무감각(flow-insensitive)**의 정의로 설명하라.
```rust
fn f() { let x = 1; let y = x + 2; x = true; if x { y } else { 0 } }
```
(b) 다음 코드도 거부된다. 그 이유(단형성)와 해법(let-다형성)을 쓰고, let-다형성이 강의 10의 어떤 개념과 유사한지, 그 비용은 무엇인지 답하라.
```rust
fn f(x) { x }
fn g() { f(1); f(true) }
```

**풀이.**
(a) 우리 분석은 **흐름 무감각** — 실행 순서를 무시하고 각 식별자에 **위치와 무관하게 단 하나의 타입**을 부여한다. 이 코드에서 `x+2`는 `⟦x⟧=i32`를, `x=true`와 `if x`는 `⟦x⟧=bool`을 강제하므로 모순 → "not ok". 실제 실행에선 x가 시점에 따라 i32였다가 bool이 되어 오류가 없으므로 이는 **헛경보**다. 지점마다 타입을 따로 추적하는 흐름 감각(flow-sensitive) 분석 — 강의 6~9의 데이터플로우 — 이 이 한계의 해법이다.
(b) 분석이 **단형(monomorphic)** — 함수 f에 단 하나의 타입만 부여한다. `f(1)`은 `⟦x⟧=i32`, `f(true)`는 `⟦x⟧=bool`을 요구해 모순 → 거부(헛경보; 실제 f는 제네릭 `fn f<T>(x:T)->T`로 안전). 해법은 **let-다형성**: f에 다형 타입 `∀X. fn(X)→X`를 주고 **각 호출 지점마다 X를 다르게 인스턴스화**한다 — `f(1)`에선 `fn(i32)→i32`, `f(true)`에선 `fn(bool)→bool`. 이는 Hindley-Milner의 핵심이다. "같은 함수를 호출 지점별로 구분해 다룬다"는 발상은 강의 10의 **문맥 민감(context-sensitive) 분석**(k-call-site)과 동형이다. 비용: 최악의 경우 **지수 시간** — 정밀도·비용 trade-off(강의 1 슬29)의 한 사례.

### 문제 4-5 [개념·서술] (M, 슬라이드 21~23)
(a) let-다형성으로도 거부되는 다음 코드에서, 매개변수 `y`가 다형적으로 인스턴스화될 수 없는 이유(고차 다형성의 부재)를 설명하라.
```rust
fn f(x) { x }
fn g(y) { y(1); y(true) }
fn h() { g(f) }
```
(b) 무제한 고차 다형성·다형 재귀를 허용하면 무슨 일이 생기는가? (c) 타입 분석이 잡지 **못하는** 런타임 오류 두 가지와 각각을 잡는 데 필요한 분석을 답하라.

**풀이.**
(a) let-다형성은 **let/fn으로 묶인 이름 있는 함수**만 일반화(∀)해 호출 지점마다 인스턴스화한다. `y`는 **매개변수**라서 g가 호출될 때 **하나의 타입으로 고정**된다 — g 본문 안에서 `y(1)`은 `⟦y⟧=fn(i32)→...`, `y(true)`는 `⟦y⟧=fn(bool)→...`를 요구해 모순. "다형 함수를 인자로 받아 여러 타입으로 쓰기"는 **고차(higher-rank) 다형성**인데 let-다형성에는 없다.
(b) 무제한 고차 다형성이나 다형 재귀(재귀 호출마다 다른 타입, 슬22의 `f(true,n-1)`/`f(0,n-1)` 예)를 허용하면 **제약 풀이가 결정 불가능(undecidable)**해진다. 표현력을 높이면 결정 가능성을 잃는다 — 강의 1의 Rice 정리가 타입 추론 안에서 재현되는 모습이며, 그래서 실용 언어는 다형성을 결정 가능한 범위(let-다형성)로 제한한다.
(c) ① **0으로 나누기** — 타입은 맞지만 값이 문제. 값의 범위를 추적하는 **구간 분석**(강의 9) 등 값 분석 필요. ② **스코프를 벗어난 스택 사용(dangling 참조)** — `fn f(){ let x=0; &x }`처럼 지역 변수의 참조를 반환하면 타입은 `&i32`로 맞지만 f 종료 후 무효. **수명/영역 분석(lifetime/region analysis)**(Rust 빌림 검사기, 강의 2 슬26)이 필요. 각 분석은 자기 영역의 오류만 잡는다.

### 문제 5-1 [증명·유도] (M, 슬라이드 8~10)
부분 순서 집합(poset)의 세 조건을 쓰고, 부호 도메인 `({⊥, −, 0, +, ⊤}, ⊑)`(⊥은 모두 이하, ⊤은 모두 이상, −·0·+는 서로 비교 불가)이 (a) poset임을 확인하고, (b) **전순서(total order)는 아님**을 증명하라. (c) `x ⊑ y`의 분석적 의미(슬라이드 9)를 쓰라.

**풀이.**
poset의 세 조건: **반사성**(∀x. x⊑x), **추이성**(x⊑y ∧ y⊑z ⇒ x⊑z), **반대칭성**(x⊑y ∧ y⊑x ⇒ x=y).
(a) 주어진 관계는 각 원소가 자기 자신과 관계되고(반사), ⊥⊑s⊑⊤ 형태의 연쇄가 일관되게 이어지며(추이: 예컨대 ⊥⊑−, −⊑⊤이고 실제 ⊥⊑⊤), 서로 다른 두 원소가 양방향으로 관계되는 경우가 없다(반대칭). 따라서 poset.
(b) 전순서는 추가로 **전체성**(∀x,y. x⊑y ∨ y⊑x)을 요구한다. 그런데 `+`와 `−`는 어느 쪽으로도 관계가 없다 — `+ ⊑ −`도 `− ⊑ +`도 정의에 없다(둘 다 ⊤보다 정밀하고 ⊥보다 부정밀하지만 서로 간에는 순서 없음). 전체성 반례가 존재하므로 전순서가 아니다. "부분" 순서라는 이름이 바로 이 비교 불가 쌍의 존재를 가리킨다.
(c) `x ⊑ y` = "**y는 x의 안전한 근사(safe approximation)**" 또는 "x는 y만큼은 정밀하다". 위로 갈수록 부정밀(안전·보수적), 아래로 갈수록 정밀. 강의 1의 과근사가 이 순서로 형식화된다 — 건전성 = "실제 ⊑ 분석 결과".

### 문제 5-2 [계산·추적] (M, 슬라이드 13~16, 25)
(a) 부호 격자에서 다음을 계산하라: `+ ⊔ 0`, `+ ⊔ −`, `+ ⊓ ⊤`, `+ ⊓ 0`, `⨆{−, 0, +}`, `⨅{−, ⊤}`.
(b) 멱집합 격자 `(𝒫({a,b,c}), ⊆)`에서 `{a} ⊔ {b}`, `{a,b} ⊓ {b,c}`, ⊥, ⊤을 답하라.
(c) join(⊔)이 프로그램 분석에서 맡는 역할을 한 문장으로 쓰라.

**풀이.**
(a) 부호 격자(⊤ / −,0,+ / ⊥)에서:
- `+ ⊔ 0`: +와 0을 모두 덮는 최소 원소 — 둘은 비교 불가이고 공통 상한은 ⊤뿐 → **⊤**.
- `+ ⊔ −` = **⊤** (같은 이유).
- `+ ⊓ ⊤`: + ⊑ ⊤이므로 작은 쪽이 흡수(슬15: x⊑y ⇒ x⊓y=x) → **+**.
- `+ ⊓ 0`: 공통 하한은 ⊥뿐 → **⊥** (양수이면서 0인 값은 없음 — 직관과 일치).
- `⨆{−,0,+}` = **⊤**, `⨅{−,⊤}` = **−** (− ⊑ ⊤이므로).
(b) 멱집합 격자에서 join=합집합, meet=교집합: `{a}⊔{b} = {a,b}`, `{a,b}⊓{b,c} = {b}`, **⊥ = ∅**, **⊤ = {a,b,c}**.
(c) join은 **여러 출처(특히 if 분기 합류점)의 추상 정보를 안전하게, 그러나 가장 타이트하게(최소 상한으로) 합치는** 연산이다 — 강의 5 슬5의 `c = + ⊔ (미정) = ⊤`, 강의 7의 JOIN(v)이 모두 이것이다.

### 문제 5-3 [개념·서술/판정] (M, 슬라이드 17~23)
(a) 격자와 완비 격자의 정의를 쓰고, "비어 있지 않은 유한 격자는 완비"라는 명제와 "격자이지만 완비가 아닌 예"를 들어라.
(b) 다음 Hasse 다이어그램이 격자인지 판정하라: 원소 {⊤, a, b, ⊥₁, ⊥₂}, 간선은 ⊥₁→a, ⊥₁→b, ⊥₂→a, ⊥₂→b, a→⊤, b→⊤ (즉 a·b가 공통 하향 원소를 **둘**(⊥₁, ⊥₂) 가지며 그 둘은 비교 불가).

**풀이.**
(a) **격자**: 임의의 **두 원소** x, y에 대해 x⊔y와 x⊓y가 존재하는 poset. **완비 격자**: 임의의 **부분집합** X(무한 포함)에 대해 ⨆X와 ⨅X가 존재하는 poset. 모든 완비 격자는 격자이고, **비어 있지 않은 유한 격자는 자동으로 완비**다(유한 부분집합의 join/meet을 두 원소 연산의 반복으로 얻을 수 있으므로). 격자이지만 완비가 아닌 예: **(ℕ, ≤)** — 두 원소의 max/min은 항상 있지만 ℕ 전체의 상한(⨆ℕ)이 없다.
(b) **격자가 아니다.** a와 b의 하한(공통 아래 원소)은 ⊥₁과 ⊥₂ 둘인데, 이 둘은 서로 비교 불가하므로 "가장 큰 하한"이 유일하게 정해지지 않는다 → `a ⊓ b`가 존재하지 않음. 격자 판정 요령: 모든 쌍에 대해 "공통 위쪽 중 가장 낮은 것이 유일한가(lub)"와 "공통 아래쪽 중 가장 높은 것이 유일한가(glb)"를 확인하고, 하나라도 깨지면 격자가 아니다(슬19~23의 예제 2·4가 이런 모양).

### 문제 5-4 [증명·유도] (S, 슬라이드 15)
poset에서 `x ⊔ y`가 존재할 때, **`x ⊑ y ⟺ x ⊔ y = y`**임을 lub의 정의(슬라이드 13)만으로 증명하라.

**증명.**
(⇒) `x ⊑ y`라 하자. y는 반사성으로 `y ⊑ y`이므로 y는 {x,y}의 상한이다. lub의 정의에서 `x⊔y`는 모든 상한보다 작거나 같으므로 `x⊔y ⊑ y`. 한편 `x⊔y`는 {x,y}의 상한이므로 `y ⊑ x⊔y`. 반대칭성으로 **`x⊔y = y`**.
(⇐) `x⊔y = y`라 하자. `x⊔y`는 {x,y}의 상한이므로 `x ⊑ x⊔y = y`, 즉 **`x ⊑ y`**. ∎
해설: 이 성질은 "순서와 join이 일관된다"는 것 — 더 큰 원소가 join에서 흡수된다. 쌍대로 `x ⊑ y ⟺ x⊓y = x`도 같은 방식으로 증명된다. 이 동치는 강의 6 슬19의 부등식→등식 변환(`x ⊒ f(x) ⟺ x = x⊔f(x)`)과 강의 8 슬39의 전파 워크리스트 정당화의 토대가 된다.

### 문제 5-5 [계산·추적] (M, 슬라이드 24~32)
(a) 격자의 **높이(height)**를 정의하고 다음 격자들의 높이를 구하라: ① 부호 격자 Sign, ② flat(A) (|A|=k), ③ 멱집합 격자 𝒫(A) (|A|=n), ④ 맵 격자 `Var → Sign` (|Var|=3), ⑤ 곱 격자 Sign × 𝒫({a,b}).
(b) `L^n ≅ A → L` (|A|=n)이 의미하는 바를 쓰고, 분석 상태가 왜 맵 격자 `Var→Sign`과 `CFG Node → (Var→Sign)`로 표현되는지 설명하라.
(c) 높이가 분석의 어떤 필수 목표와 연결되는지 답하라.

**풀이.**
(a) 높이 = **⊥에서 ⊤까지의 최장 경로 길이**(거치는 간선 수).
① Sign = flat({−,0,+}): ⊥ → (−|0|+) → ⊤로 **2**. ② flat(A)도 구조가 같아 **2**(k와 무관). ③ 𝒫(A): ∅에서 원소를 하나씩 더해 A까지 — **n**. ④ 맵 격자 높이 = |A|·height(L) = 3 × 2 = **6**. ⑤ 곱 격자 높이 = 각 높이의 합 = 2 + 2 = **4**.
(b) `L^n ≅ A→L`: n개 성분의 곱(튜플)과 n개 키를 가진 맵(함수)은 **동형** — i번째 성분 ↔ i번째 키로 일대일 대응하며 join·meet을 보존하므로, 이름만 다른 같은 격자다. 분석 상태는 "각 변수의 추상값"이므로 자연스럽게 **`Var→Sign`**(한 지점의 상태)이고, 분석 전체 결과는 "각 노드마다 그런 상태"이므로 **`CFG Node → (Var→Sign)`**(이중 맵). 순서·join은 모두 점별(pointwise)로 정의된다.
(c) **종료(termination)**. 고정점 반복(강의 6 Kleene)은 ⊥에서 단조 증가하는데, 한 변수의 값이 올라갈 수 있는 횟수가 높이로 제한되므로 **유한 높이 = 반복의 유한성 = 종료 보장**이며, 워크리스트 복잡도 O(n·h·k)의 h로도 등장한다(강의 7 슬33). 높이가 무한한 격자(구간)는 위드닝(강의 9)이 필요하다.

## 강의 6 — Lattice Theory (2)

### 문제 6-1 [개념·서술] (M, 슬라이드 2~6)
(a) 흐름 감각(flow-sensitive) 분석의 정의를 쓰고, 직선 코드의 방정식은 단순 대입으로 풀리는데 **루프가 있으면 왜 단순 대입으로 풀 수 없는지** 설명하라. (b) 그 해법으로서 "분석 = 고정점 찾기"의 정식화를 쓰라: 코드 `a = 42; b = a + input();`에 대한 함수 f와 고정점의 정의(슬라이드 6).

**풀이.**
(a) 흐름 감각 분석은 **문장의 순서를 고려해, 각 프로그램 지점마다 별도의 추상 상태**(예: `Var→Sign`)를 둔다(강의 4의 흐름 무감각 타입 분석과 대조). 직선 코드에선 각 지점의 방정식이 **앞선 지점에만** 의존하므로 위에서 아래로 대입하면 풀린다. 그러나 루프가 있으면 루프 헤드의 상태가 루프 본문(뒤쪽 지점)에 의존하고 본문은 다시 헤드에 의존하는 **상호 재귀(순환) 방정식**이 생긴다 — `x_head = ... x_body ...`, `x_body = ... x_head ...`. 어느 쪽도 먼저 계산할 수 없으므로(닭과 달걀) 단순 대입은 불가능하다.
(b) 모든 지점의 방정식을 하나의 함수로 묶는다:
`f : (Var→Sign)³ → (Var→Sign)³`, `f(x0, x1, x2) = ([a↦⊤, b↦⊤], x0[a↦+], x1[b↦ x1(a) +̂ ⊤])`.
f는 "현재의 모든 지점 상태를 받아 한 번 갱신한 상태"를 준다. **고정점**은 `f(x) = x`인 x — 더 갱신해도 변하지 않는 상태 = 방정식 시스템의 해 = 분석 결과다. 루프가 있어도 고정점은 정의되므로, "분석 = 격자 위 함수의 고정점 계산"이라는 일반 프레임이 성립한다.

### 문제 6-2 [증명·유도] (M, 슬라이드 7~9)
(a) **단조 함수**의 정의와 분석적 직관을 쓰라. (b) **분배적(distributive) 함수**(`f(x)⊔f(y) = f(x⊔y)`)는 항상 단조임을 증명하라. (c) "f가 단조 ⟺ ∀x,y. f(x)⊔f(y) ⊑ f(x⊔y)"에서 단조성이 분배성의 "부등식 버전"임을 설명하라.

**풀이.**
(a) `f : L1 → L2`가 **단조** ⟺ `∀x,y. x ⊑ y ⇒ f(x) ⊑ f(y)` (순서 보존). 분석적 직관: **"더 정밀한 입력이 덜 정밀한 출력을 낳지 않는다"** — 정보를 거꾸로 뒤집지 않는다.
(b) **증명.** f가 분배적이라 하고 `x ⊑ y`라 하자. 슬라이드(강의 5 슬15)의 동치로 `x⊔y = y`. 그러면
`f(y) = f(x⊔y) = f(x) ⊔ f(y)` (분배성).
다시 같은 동치를 역방향으로 적용하면 `f(x)⊔f(y) = f(y) ⟺ f(x) ⊑ f(y)`. 따라서 `x⊑y ⇒ f(x)⊑f(y)`, 즉 f는 단조. ∎ (역은 성립하지 않는다 — 단조이지만 비분배적인 함수가 존재한다.)
(c) 분배성은 join 보존이 **등식**으로 성립하는 것이고, 단조성은 같은 식이 **⊑(부등식)**으로만 성립하는 것이다(`f(x)⊔f(y) ⊑ f(x⊔y)` — "따로 분석해 합친 것"이 "합쳐서 분석한 것"보다 정밀하거나 같음). 등식이 성립하면(분배적) 분기 합류 후 분석과 경로별 분석이 일치해 정밀도 손실이 없고, 부등식만 성립하면(단조) 합류에서 정밀도를 잃을 수 있다 — 이 간극이 강의 6 슬18의 "의미적으로 가장 정밀한 답은 lfp보다 아래일 수 있다"의 원인이다.

### 문제 6-3 [개념·서술] (M, 슬라이드 12~15)
(a) 최소 고정점(lfp)의 정의를 쓰고, "잘 설계된 제약이면 모든 고정점이 건전한데 굳이 **최소** 고정점을 추구하는 이유"를 답하라. (b) **Tarski 정리**와 **Kleene 정리**를 각각 진술하고, 두 정리의 역할 차이(존재 vs 계산)를 설명하라.

**풀이.**
(a) x가 f의 고정점이고 **모든** 고정점 y에 대해 `x ⊑ y`이면 x는 **최소 고정점(lfp)**이다. 잘 설계된 제약 시스템에서는 모든 고정점이 건전한 결과를 주지만(과근사 쪽으로 안전), 고정점이 클수록 부정밀하다(군더더기가 많음). lfp는 **건전한 해 중 가장 정밀한(작은) 해**이므로 분석의 목표가 된다.
(b) **Tarski 정리**: L이 완비 격자이고 f : L→L이 단조이면 f는 최소 고정점을 가진다. — lfp의 **존재**를 보장하지만 찾는 방법은 주지 않는다.
**Kleene 정리**: L이 **유한 높이** 완비 격자이고 f가 단조이면 `lfp(f) = ⨆_{i≥0} f^i(⊥)` — 즉 증가 사슬 `⊥ ⊑ f(⊥) ⊑ f²(⊥) ⊑ ...`을 고정점에 도달할 때까지 계산하면 lfp를 얻는다. — lfp의 **계산법**을 준다.
역할 분담: Tarski가 "정답이 반드시 있다"(분석의 정당성)를, Kleene이 "⊥에서 f를 반복하면 유한 단계에 그 정답에 도달한다"(알고리즘과 종료)를 보장한다. 두 정리의 전제 — 완비 격자(강의 5), 단조성(슬7), 유한 높이 — 가 곧 분석 설계의 체크리스트다.

### 문제 6-4 [계산·추적] (M, 슬라이드 16~17)
문제 6-1(b)의 함수 f에 단순 고정점 알고리즘(`x ← ⊥; while x ≠ f(x): x ← f(x)`)을 적용해 ⊥, f(⊥), f²(⊥), f³(⊥)를 **표로** 추적하고 lfp를 구하라. (추상 덧셈은 ⊥이 흡수원: `⊥ +̂ ⊤ = ⊥`; `+ +̂ ⊤ = ⊤`.)

**풀이.**
f(x0,x1,x2) = ([a↦⊤,b↦⊤], x0[a↦+], x1[b↦x1(a)+̂⊤]). ⊥ = 세 지점 모두 [a↦⊥, b↦⊥].

| 반복 | x0 | x1 | x2 |
|---|---|---|---|
| ⊥ | [a↦⊥, b↦⊥] | [a↦⊥, b↦⊥] | [a↦⊥, b↦⊥] |
| f(⊥) | [a↦⊤, b↦⊤] | [a↦+, b↦⊥] | [a↦⊥, b↦⊥] |
| f²(⊥) | [a↦⊤, b↦⊤] | [a↦+, b↦⊤] | [a↦+, b↦⊤] |
| f³(⊥) | [a↦⊤, b↦⊤] | [a↦+, b↦⊤] | [a↦+, b↦⊤] |

단계별 확인:
- **f(⊥)**: x0 성분은 상수 [⊤,⊤]. x1 = ⊥의 x0(전부 ⊥)에서 a만 + → [a↦+, b↦⊥]. x2 = ⊥의 x1에서 b↦ ⊥(a) +̂ ⊤ = ⊥ +̂ ⊤ = ⊥ → 변화 없음.
- **f²(⊥)**: x1 = f(⊥)의 x0 = [⊤,⊤]에서 a↦+ → [a↦+, b↦⊤]. x2 = f(⊥)의 x1 = [a↦+, b↦⊥]에서 b↦ + +̂ ⊤ = ⊤ → [a↦+, b↦⊤].
- **f³(⊥)**: 모든 성분이 f²(⊥)와 같음 → **고정점 도달, lfp = f²(⊥)**.

해설: 반복마다 정보가 한 지점씩 앞으로 전파된다(1회차에 진입·1행, 2회차에 2행). 직선 코드라 2회 만에 수렴했지만, 루프가 있으면 더 오래 걸리고, 무한 높이 격자에선 영영 안 멈출 수 있다(강의 9의 동기).

### 문제 6-5 [증명·유도] (M, 슬라이드 15·18~19)
(a) Kleene 반복 `⊥, f(⊥), f²(⊥), ...`이 (i) 단조 증가 사슬을 이루고 (ii) 유한 높이 격자에서 반드시 멈춤을 증명하라. (b) 부등식 제약 `x ⊒ f(x)`가 등식 `x = x ⊔ f(x)`와 동치임을 증명하라. (c) 단순 고정점 알고리즘의 시간 복잡도가 무엇에 의해 결정되는지 답하라.

**증명.**
(a)(i) 귀납법. 기저: ⊥는 최소 원소이므로 `⊥ ⊑ f(⊥)`. 귀납 단계: `f^i(⊥) ⊑ f^{i+1}(⊥)`라 가정하면 f의 **단조성**으로 `f(f^i(⊥)) ⊑ f(f^{i+1}(⊥))`, 즉 `f^{i+1}(⊥) ⊑ f^{i+2}(⊥)`. 따라서 `⊥ ⊑ f(⊥) ⊑ f²(⊥) ⊑ ...`는 증가 사슬이다.
(ii) 격자의 높이가 h(유한)이면 진(strict) 증가가 일어날 수 있는 횟수는 최대 h번이다 — 사슬에서 값이 진증가할 때마다 격자에서 한 단계 이상 올라가는데 ⊥→⊤ 최장 경로가 h이므로. 따라서 어떤 k ≤ h에서 `f^k(⊥) = f^{k+1}(⊥)`가 되어 멈추고, 이 값이 고정점이며 Kleene 정리에 의해 lfp다. ∎
(b) (⇒) `x ⊒ f(x)`이면 강의 5 슬15의 동치(`a⊑b ⟺ a⊔b=b`)에서 a=f(x), b=x로 두어 `f(x) ⊔ x = x`, 즉 `x = x ⊔ f(x)`. (⇐) `x = x⊔f(x)`이면 `f(x) ⊑ x⊔f(x) = x`(join은 상한이므로), 즉 `x ⊒ f(x)`. ∎ — 이 변환 덕에 포함 제약(`[y]⊆[x]`, 강의 11·14)도 등식 고정점으로 풀 수 있다.
(c) 두 인자의 곱: **격자의 높이**(반복 횟수의 상한 — (a)에서 증명) × **매 반복의 비용**(f(x) 계산과 동치 검사). 그래서 높이가 작을수록, f가 쌀수록 빠르며, 워크리스트(강의 7)는 "바뀐 성분만 재계산"으로 후자를 줄인 것이다.

## 강의 7 — Dataflow Analysis (1)

### 문제 7-1 [개념·서술] (M, 슬라이드 2~4)
**단조 프레임워크(monotone framework)**의 구성 요소를 나열하고, "인스턴스화"가 무엇을 뜻하는지 설명하라. 부호 분석과 상수 전파가 같은 프레임워크의 다른 인스턴스라는 말의 구체적 의미(무엇이 같고 무엇이 다른가)를 답하라.

**풀이.**
구성 요소: ① **CFG**(노드 = 문장/블록, 간선 = 제어 흐름), ② **유한 높이의 완비 격자**(추상 정보의 도메인 — 격자 원소가 한 노드의 추상 정보), ③ 각 노드 v에 격자 원소를 값으로 갖는 **제약 변수 ⟦v⟧**, ④ 노드마다 다른 노드 변수들과의 관계를 적은 **단조 우변의 데이터플로우 제약식**. 모든 제약이 단조 (부)등식이면 고정점 알고리즘으로 풀 수 있다(강의 6).
**인스턴스화** = 이 빈 틀에 "격자 + 제약 부여 규칙"을 채워 구체 분석을 만드는 것.
부호 분석과 상수 전파의 비교: **같은 것** — 제약의 형태(`⟦v⟧ = JOIN(v)[x ↦ eval(JOIN(v), e)]`, entry는 ⊤, 그 외는 JOIN), JOIN(선행자 ⊔), 고정점 풀이 알고리즘. **다른 것** — 격자(부호: `Var→Sign`, 상수 전파: `Var→flat(ℤ)`)와 그에 맞는 eval·추상 연산자 op̂(부호: 부호 연산표, 상수: "둘 다 상수면 실제 계산, 아니면 ⊤"). 즉 격자만 갈아 끼우면 다른 분석이 나온다 — 이것이 프레임워크의 위력이다.

### 문제 7-2 [계산·추적] (M, 슬라이드 7~13)
다음 코드의 CFG 노드 v1(entry), v2(`a=42`), v3(`b=87`), v4(`if x`), v5(`c=a+b`), v6(`c=a−b`), v7(return)에 대해 부호 분석 제약식을 모두 쓰고 해를 구하라. 특히 v7에서 c의 부호를 join 계산으로 보여라.
```c
a = 42; b = 87;
if x { c = a + b; } else { c = a - b; }
return;
```

**풀이.**
제약식(슬12~13):
- `⟦v1⟧ = ⊤` (entry: 모든 변수 부호 미정)
- `⟦v2⟧ = ⟦v1⟧[a ↦ +]` (42의 부호)
- `⟦v3⟧ = ⟦v2⟧[b ↦ +]`
- `⟦v4⟧ = ⟦v3⟧` (조건 노드는 상태 유지)
- `⟦v5⟧ = ⟦v4⟧[c ↦ +̂(⟦v4⟧(a), ⟦v4⟧(b))]`
- `⟦v6⟧ = ⟦v4⟧[c ↦ −̂(⟦v4⟧(a), ⟦v4⟧(b))]`
- `⟦v7⟧ = ⟦v5⟧ ⊔ ⟦v6⟧` (합류: 선행자 join)

해: ⟦v2⟧ = [a↦+, b↦⊤, c↦⊤], ⟦v3⟧ = ⟦v4⟧ = [a↦+, b↦+, c↦⊤].
- v5: `+̂(+, +) = +` (양수+양수=양수) → [a↦+, b↦+, c↦+].
- v6: `−̂(+, +) = ⊤` (양수−양수는 부호 미정: 42−87<0, 87−42>0 모두 가능) → [a↦+, b↦+, c↦⊤].
- v7: 점별 join — a: +⊔+ = +, b: +⊔+ = +, **c: + ⊔ ⊤ = ⊤** → ⟦v7⟧ = [a↦+, b↦+, c↦⊤].

최종: 반환 시점에 a, b는 확실히 양수이고 c는 모름(⊤). 분기 합류에서 join이 두 경로 정보를 안전하게 합치는 모습(강의 5 슬5와 동일한 결과)이다.

### 문제 7-3 [증명·유도] (M, 슬라이드 10·14~15)
추상 덧셈표 +̂에서 (a) `0 +̂ x = x`, `+ +̂ − = ⊤`, `⊥ +̂ x = ⊥`인 각각의 이유(건전성)를 쓰고, (b) `+̂`가 **단조**임을 구체적인 행 하나(`+ +̂ ·` 행: 인자가 0 → + → ⊤로 커질 때)로 확인하라. (c) 전체 전이 함수의 단조성이 어떻게 "조각별로" 확립되는지 답하라.

**풀이.**
(a) 건전성 기준: 추상 결과는 두 피연산자의 모든 구체값 조합의 실제 합을 포함해야 한다.
- `0 +̂ x = x`: 0 + (x에 속한 임의 값) = 그 값 자신 → 부호가 변하지 않으므로 x 그대로가 정확하고 건전.
- `+ +̂ − = ⊤`: 양수+음수는 결과가 양수(5+(−1))·0(1+(−1))·음수(1+(−5)) 모두 가능 → 셋을 다 덮는 최소 추상값은 ⊤. −나 +로 답하면 가능한 결과를 빠뜨려 unsound.
- `⊥ +̂ x = ⊥`: ⊥은 "가능한 값 없음"(도달 불가) — 한쪽이 불가능하면 덧셈 자체가 일어나지 않으므로 결과도 값 없음.
(b) 0 ⊑ + ⊑ ⊤(격자에서 0과 +는 비교 불가지만, 0 ⊑ ⊤, + ⊑ ⊤; 단조성 확인은 ⊑ 사슬을 따라 한다). `+ +̂ 0 = +`, `+ +̂ + = +`, `+ +̂ ⊤ = ⊤`이고 비교 가능한 입력 쌍에 대해 0⊑⊤이면 결과 +⊑⊤, +⊑⊤이면 +⊑⊤ — 인자가 격자에서 올라갈 때 결과가 내려가는 경우가 없으므로 단조.
(c) 강의 6 슬9~10의 성질 — 상수 함수·⊔·⊓·맵 갱신·곱 함수·합성이 모두 단조성을 보존 — 을 쓴다. 전이 함수는 "JOIN(⊔들) → eval(op̂들의 합성) → 맵 갱신"으로 만들어지므로, 기본 조각(op̂, ⊔, 갱신)이 단조임만 확인하면 전체 f의 단조성이 **자동으로** 따라온다. 이 모듈성 덕에 설계자는 추상 연산자 표만 검증하면 된다.

### 문제 7-4 [계산·추적] (M, 슬라이드 19~22)
상수 전파 분석(격자 `Var → flat(ℤ)`, op̂: 둘 다 상수면 실제 계산, 한쪽이 ⊤면 ⊤, ⊥이면 ⊥)을 다음 코드에 적용해 각 줄 이후의 상태를 추적하고, 그 결과로 가능한 최적화(치환) 코드를 쓰라.
```c
a = 3;
b = a * 2;
c = a + input();
a = a * b;
e = a + c;
```

**풀이.**
| 줄 | 평가 | 상태(관련 변수) |
|---|---|---|
| `a = 3` | 3 | a=3 |
| `b = a * 2` | 3 ×̂ 2 = 6 (둘 다 상수 → 실제 계산) | a=3, b=6 |
| `c = a + input()` | 3 +̂ ⊤ = ⊤ | a=3, b=6, c=⊤ |
| `a = a * b` | 3 ×̂ 6 = 18 | a=18, b=6, c=⊤ |

```c
a = 3;
b = 6;
c = 3 + input();
a = 18;
e = 18 + c;
```
해설: 분석이 "b는 확실히 6, (4행 이후) a는 확실히 18"을 보장하므로 치환이 의미 보존이다(강의 1의 "변환엔 건전성"). `input()`이 섞인 c·e는 ⊤라 부분 치환만 가능하다(`a+c` → `18+c`).

### 문제 7-5 [개념·서술/유도] (F, 슬라이드 23~33)
네 고정점 알고리즘 — 단순(Naive), Round Robin, Chaotic Iteration, 워크리스트 — 의 차이를 정리하고, (a) Chaotic이 비실용적인 이유, (b) 워크리스트가 그것을 `dep`으로 해결하는 방식(전방 분석에서 dep이 무엇인지 포함), (c) 워크리스트의 최악 복잡도 **O(n·h·k)**의 유도(각 인자의 의미와 "왜 h가 곱해지는가")를 답하라.

**풀이.**
- **단순**: 매 반복 **모든** 성분 fi를 옛 x로 재계산 후 일괄 갱신. 대부분 성분은 변하지 않으므로 중복 계산이 많다.
- **Round Robin**: 성분을 순서대로 돌며 **즉석 갱신**(`xi ← fi(x)`, 갱신값을 같은 반복에서 바로 사용 — Gauss-Seidel 방식). 정보가 더 빨리 전파되어 수렴이 빨라질 수 있고, 갱신 순서는 최종 결과와 무관하게 같은 lfp를 준다.
- **Chaotic**: 매번 "바뀔 성분(`xi ≠ fi(x)`) 하나"를 골라 갱신. 갱신 횟수는 최소화되지만 —
(a) **비실용적인 이유**: "바뀔 i"를 찾으려면 결국 fi들을 계산해 봐야 한다 — 피하려던 비용을 선택 과정에서 그대로 지불한다(닭과 달걀).
(b) **워크리스트**: "무엇이 바뀌면 무엇을 다시 계산해야 하는가"라는 **의존성을 미리 기록**한다. `dep(v)` = v의 정보에 의존하는 노드들의 집합 — **전방 분석(부호·상수 전파)에서는 dep = succ**(v의 상태가 바뀌면 v를 선행자로 갖는 후속 노드들의 JOIN이 영향받으므로). 알고리즘: 모든 노드를 W에 넣고, 꺼낸 노드의 fi를 계산해 **값이 바뀐 경우에만** 갱신하고 `dep(vi)`를 W에 추가. W가 비면(고정점) 종료. 탐색 없이 영향받는 노드만 재계산한다.
(c) **O(n·h·k) 유도**: 한 노드의 값은 격자에서 **단조 증가만** 하므로 최대 h번(격자 높이만큼)만 진짜로 바뀔 수 있다 → 각 노드가 "값이 바뀌어 재처리를 유발"하는 횟수 ≤ h. 노드가 n개이고 |dep(v)|가 상수로 유계이면 총 재처리 횟수는 O(n·h)이고, 재처리마다 fi 계산 비용 k가 들므로 전체 **O(n·h·k)**. 유한 높이 h가 종료와 비용을 동시에 좌우한다 — h가 무한(구간 도메인)이면 위드닝이 필요하다(강의 9).

## 강의 8 — Dataflow Analysis (2)

### 문제 8-1 [계산·추적] (M, 슬라이드 2~6)
다음 코드에 **살아있는 변수 분석**(후방·may, `⟦v⟧` = 노드 앞에서 살아있는 변수 집합)을 손으로 돌려라. 규칙: `x=e`는 `⟦v⟧ = JOIN(v) \ {x} ∪ vars(e)`, `if x`는 `JOIN(v) ∪ {x}`, return은 ∅, JOIN은 **후속자들의 합집합**.
```c
x = input();
if input() { y = x; } else { y = 1; }
z = y;
```

**풀이.**
후방 분석이므로 끝(return 격인 `z=y` 이후)에서 시작해 위로 전파한다. (z는 이후에 읽히지 않는다고 가정.)
1. `z = y` 앞: JOIN = ∅ (이후 아무것도 안 읽힘). kill z, gen vars(y)={y} → **{y}**.
2. then 가지 `y = x` 앞: JOIN = {y} (`z=y` 앞 상태가 후속). kill y, gen {x} → **{x}**.
3. else 가지 `y = 1` 앞: JOIN = {y}. kill y, gen ∅(상수) → **∅**.
4. `if input()` 앞: JOIN = 후속 둘의 **합집합** = {x} ∪ ∅ = {x}. `input()`은 프로그램 변수가 아니므로 추가 없음 → **{x}**.
5. `x = input()` 앞: JOIN = {x}. kill x, gen ∅ → **∅**.

요약: 시작 시 아무것도 안 살아있고, `x=input()` 후 x가 살아있으며(나중에 `y=x`에서 읽힐 수 있음), 두 분기 직후엔 y만 살아있다 — 슬라이드 2의 주석과 일치. 응용: "not live" 판정이 확실하므로(may 분석의 신뢰 가능한 쪽), 죽은 변수의 레지스터를 회수할 수 있다(슬3).

### 문제 8-2 [계산·추적] (M, 슬라이드 7~12)
다음 코드에 **사용 가능 식 분석**(전방·must, `⟦v⟧` = 노드 뒤에서 available한 비자명 식 집합)을 적용하라. 규칙: `x=e`는 `⟦v⟧ = (JOIN(v) ∪ exprs(e)) ↓x`(↓x는 x를 포함한 식 제거), entry는 ∅, JOIN은 **선행자들의 교집합**. 마지막 줄에서 어떤 식을 재사용할 수 있는가?
```c
x = y + 1;
if input() { y = z + 1; } else { x = z + 1; }
w = (z + 1) + (y + 1);
```

**풀이.**
1. entry: **∅** (역멱집합 격자에서 ⊤ = ∅ — 시작 시 아무 식도 계산 안 됨).
2. `x = y+1` 뒤: gen {y+1}, kill(↓x): y+1은 x를 포함하지 않으므로 유지 → **{y+1}**.
3. then `y = z+1` 뒤: (JOIN={y+1} ∪ {z+1}) ↓y — y가 바뀌므로 **y를 포함한 식 y+1 제거** → **{z+1}**.
4. else `x = z+1` 뒤: ({y+1} ∪ {z+1}) ↓x — x 포함 식 없음 → **{y+1, z+1}**.
5. 합류(w 줄 앞): must이므로 **교집합** — {z+1} ∩ {y+1, z+1} = **{z+1}**.
6. `w = (z+1)+(y+1)` 뒤: gen exprs = {z+1, y+1, (z+1)+(y+1)}, kill ↓w 없음 → {z+1, y+1, (z+1)+(y+1)}.

재사용: 합류 시점에 **z+1만 available** — 양쪽 분기에서 모두 계산되었기 때문이다. 따라서 `zplus1 = z+1`로 저장해 마지막 줄에서 재계산 없이 재사용할 수 있다(슬9의 최적화). y+1은 then 가지에서 y가 변경되어 무효화되므로 재사용 불가. "available" 판정이 틀리면 잘못된 값을 재사용하게 되므로 must(교집합)가 필수다.

### 문제 8-3 [개념·서술] (F, 슬라이드 24~29)
데이터플로우 분석의 **4분면 분류표**를 완성하라: 네 고전 분석(도달 정의·살아있는 변수·사용 가능 식·매우 바쁜 식)을 (전방/후방) × (may/must)에 배치하고, 각 축이 결정하는 것 — 전방/후방이 JOIN·dep 방향을, may/must가 격자·join 연산을 — 을 정리하라. 각 분석의 대표 응용도 한 가지씩 쓰라.

**풀이.**
| | **전방(forward)** | **후방(backward)** |
|---|---|---|
| **may** | 도달 정의(reaching definitions) | 살아있는 변수(live variables) |
| **must** | 사용 가능 식(available expressions) | 매우 바쁜 식(very busy expressions) |

축의 의미:
- **전방/후방**: 전방 = **과거** 동작 정보(어느 정의가 값을 만들었나, 어떤 식이 이미 계산됐나) — entry에서 시작, **JOIN = pred**, dep = succ. 후방 = **미래** 동작 정보(나중에 읽힐까, 반드시 계산될까) — return에서 시작, **JOIN = succ**, dep = pred.
- **may/must**: may = **가능성**(어느 한 경로에서라도 성립) — **멱집합 격자 (𝒫, ⊆), join = 합집합**. must = **필연**(모든 경로에서 성립) — **역멱집합 격자 (𝒫, ⊇), join = 교집합**.

응용: 도달 정의 → def-use 그래프(최적화 기반), 살아있는 변수 → 레지스터 할당, 사용 가능 식 → 중복 계산 제거, 매우 바쁜 식 → 코드 호이스팅(반드시 계산될 식을 분기 앞으로).
이 표는 새 분석 설계의 가이드이기도 하다: "무엇을 묻는가"(과거/미래 × 가능/필연)가 칸을 정하고, 칸이 격자·JOIN·전이의 골격을 정한다(슬30~31의 초기화 변수 분석).

### 문제 8-4 [증명·유도] (M, 슬라이드 25~28)
"may 분석 = 건전(sound), must 분석 = 완전(complete)"이라는 주장은 틀렸다. (a) may/must와 sound/complete가 각각 무엇에 관한 분류인지 구분하고, (b) live variable(may)이 건전한 분석인 이유와 available expression(must)이 건전한 분석인 이유를 각각 "어느 방향의 판정이 신뢰되는가"로 설명하라.

**풀이.**
(a) **may/must는 "무엇을 추적하는가"**의 분류다 — may는 가능성(어느 경로에서든 성립할 수 있는 사실), must는 필연(모든 경로에서 반드시 성립하는 사실). **sound/complete는 "근사의 방향"**(과근사/과소근사)의 분류다. 두 축은 독립적이며, 슬26이 명시하듯 **네 고전 분석은 모두 건전하되 불완전**하다.
(b) **live(may)의 건전성**: 분석이 live = {x}라 하면, "x 외의 변수가 살아있어야 하는 실행은 불가능하다"는 판정 — 즉 **"not live" 쪽 판정에 거짓 음성이 없다**(집합에 없는 변수는 정말 안 읽힘). 대신 집합에 든 변수가 실제로는 안 읽힐 수도 있다(거짓 양성 = 과근사). 빠뜨리면(실제 읽힐 변수를 not live로) 레지스터 회수가 프로그램을 깨뜨리므로, 합집합으로 모든 가능성을 포함하는 것이 건전성이다.
**available(must)의 건전성**: 분석이 available = {x+y}라 하면, "x+y를 계산하지 않은 실행은 불가능하다"는 판정 — **"available" 쪽 판정에 거짓 음성이 없다**(집합에 든 식은 정말 계산되어 있음). 대신 실제로 available인 식이 집합에서 빠질 수 있다(보수적). 과장하면(계산 안 된 식을 available로) 잘못된 값을 재사용하므로, 교집합으로 확실한 것만 남기는 것이 건전성이다.
요약: may는 "집합 밖"이, must는 "집합 안"이 신뢰되는 쪽이고, 둘 다 그 신뢰가 깨지지 않게 근사하므로 **둘 다 건전**하다.

### 문제 8-5 [설계·응용] (M, 슬라이드 30~32)
"어떤 변수가 한 지점에서 **반드시 초기화되었는가**"를 판정하는 **초기화된 변수 분석**을 4분면 분류로부터 설계하라: (a) 전방/후방과 may/must 중 어디에 속하는지와 그 근거, (b) 격자·JOIN·제약 규칙(`x=e`, entry), (c) 다음 코드에서 합류 후 x·y의 초기화 여부 판정.
```c
if input() { x = 1; y = x + 1; } else { y = 2; }
z = y + x;
```

**풀이.**
(a) "**반드시**(모든 경로에서)" → **must**. "초기화는 이미 일어난 일(**과거** 속성)" → **전방**. 따라서 **전방-must** 칸(available expression과 같은 칸).
(b) 칸이 골격을 결정한다: 격자 = **역멱집합 `(𝒫(Var), ⊇)`**, **JOIN(v) = ⋂_{u∈pred(v)} ⟦u⟧**(선행자 교집합). 규칙: `x = e`: `⟦v⟧ = JOIN(v) ∪ {x}` (x가 초기화됨; 초기화는 사라지지 않으므로 kill 없음), `entry`: `⟦v⟧ = ∅` (시작 시 아무것도 초기화 안 됨 — 이 격자의 ⊤).
(c) then 가지 끝: ∅ ∪ {x} ∪ {y} = {x, y}. else 가지 끝: {y}. 합류: **{x,y} ∩ {y} = {y}** → 합류 후 **y는 반드시 초기화**, **x는 보장 없음**(else 경로에서 미초기화). 따라서 `z = y + x`의 x 사용은 "미초기화 변수 사용 가능성" 경고 대상이다. 전이 함수 형태 `⟦v⟧ = t_v(JOIN(v))`(슬32)에 정확히 들어맞는 설계다.

## 강의 9 — Widening

### 문제 9-1 [증명·유도] (M, 슬라이드 3·5~6·16~17)
구간 도메인의 순서는 `[l₁,h₁] ⊑ [l₂,h₂] ⟺ l₂ ≤ l₁ ∧ h₁ ≤ h₂`이다. (a) 이 도메인의 높이가 **무한**임을 무한 진증가 사슬을 제시해 증명하라. (b) 그 결과 Kleene식 반복(강의 6)이 왜 실패할 수 있는지를 `x = 0; while input() { x = x + 1; }`의 루프 헤드 상태 수열로 보여라. (c) Tarski 정리는 이 상황에서 무엇을 보장하고 무엇을 보장하지 못하는가?

**풀이.**
(a) 사슬 `[0,0] ⊑ [0,1] ⊑ [0,2] ⊑ [0,3] ⊑ ···`을 보자. 각 단계에서 하한은 0으로 같고 상한이 진증가하므로 `[0,n] ⊑ [0,n+1]`이며 `[0,n] ≠ [0,n+1]` — 진증가 무한 사슬이다. 높이는 ⊥→⊤ 최장 사슬 길이인데 이 사슬이 무한하므로 **높이 무한**. ∎
(b) 루프 헤드의 join 반복: 진입 [0,0]; 본문 1회 후 [1,1]과 join → [0,1]; 본문([0,1]+[1,1]=[1,2])과 join → [0,2]; 다음 [0,3]; ... — 반복 n회 후 [0,n]으로 **상한이 계속 자라 영영 수렴하지 않는다**. Kleene 정리의 전제(유한 높이)가 깨졌기 때문이다.
(c) Tarski 정리(완비 격자 + 단조 ⇒ lfp 존재, `lfp(f) = ⨅{x | f(x) ⊑ x}`)는 **lfp의 존재**는 여전히 보장한다(구간 도메인은 완비 격자다). 그러나 **유한 단계 안에 그것을 찾는 방법**은 보장하지 못한다. 추가로 유용한 사실: `f(x) ⊑ x`인 x(pre-fixed point)에 대해 `lfp(f) ⊑ x` — 어떤 방법으로든 pre-fixed point에 도달하면 그것은 lfp의 건전한 과근사다. 이것이 위드닝의 정당화 근거가 된다(문제 9-4).

### 문제 9-2 [계산·추적] (S~M, 슬라이드 4·8~9)
구간 도메인에서 다음을 계산하라.
(a) `[1,5] ⊔ [8,10]`, (b) `[1,5] ⊓ [6,10]`, (c) `[0,10] ⊓ [5,∞]`,
(d) `⊕₊([2,5], [3,3])`, (e) `⊕₋([5,8], [2,3])`, (f) `eval(σ, x+3)` (σ(x)=[2,5]), (g) `eval(σ, input())`.

**풀이.**
- (a) join = `[min(1,8), max(5,10)]` = **[1,10]**. 두 구간을 포함하는 최소 구간 — 사이의 빈틈(6~7)도 메워지므로 과근사가 생긴다.
- (b) meet = 교집합: max(1,6)=6 > min(5,10)=5 → 교집합 없음 → **⊥**.
- (c) `[max(0,5), min(10,∞)]` = **[5,10]**.
- (d) 덧셈 `[l₁+l₂, h₁+h₂]` = **[5,8]**.
- (e) 뺄셈 `[l₁−h₂, h₁−l₂]` = `[5−3, 8−2]` = **[2,6]** (최솟값은 "가장 작은 것 − 가장 큰 것").
- (f) eval(σ,x)=[2,5], eval(σ,3)=[3,3], ⊕₊ → **[5,8]**.
- (g) 입력은 임의 값 → **⊤ = [−∞,∞]**.
해설: 추상 연산의 일반 정의는 "두 구간의 모든 값 조합에 op를 적용한 결과의 min·max"이고, 덧셈·뺄셈은 그것이 닫힌 공식으로 떨어진 경우다. 건전성: 실제 결과는 항상 계산된 구간 안에 있다.

### 문제 9-3 [계산·추적] (M, 슬라이드 11~15)
기본 구간 분석은 다음 코드에서 y를 [−∞,∞]로밖에 알지 못한다. **제어 민감(control sensitivity)** 전이 함수와 filter(`filter_≤([l,h],n) = [l,h] ⊓ [−∞,n]`, `filter_>([l,h],n) = [l,h] ⊓ [n+1,∞]` 및 그 유사형)를 적용해 각 지점의 x·y 구간을 추적하고, 최종 y가 어떻게 개선되는지 보여라.
```c
// x: [-∞, ∞]
if x < 0 { y = -x; } else { y = x; }
```

**풀이.**
기본 분석(슬11): 조건을 무시하므로 양쪽 분기 모두 x=[−∞,∞] → `y=−x`도 `y=x`도 [−∞,∞] → 합류 후 **y=[−∞,∞]** (조건 정보 전혀 활용 못 함).
제어 민감 분석(슬12~15): 조건 노드의 전이가 (상태, 다음 노드) 쌍의 집합을 반환하며 분기별로 필터링한다.
- **then(x<0 참)**: x ← [−∞,∞] ⊓ [−∞,−1] = **[−∞,−1]**. `y = −x`: −[−∞,−1] = **[1,∞]**.
- **else(x≥0 참)**: x ← [−∞,∞] ⊓ [0,∞] = **[0,∞]**. `y = x` → **[0,∞]**.
- 합류: y = [1,∞] ⊔ [0,∞] = **[0,∞]**.

개선: y가 [−∞,∞]에서 **[0,∞](항상 비음수)**로 — "절댓값" 코드의 의미를 분석이 잡아냈다. filter는 meet(⊓)으로 조건이 배제하는 값을 잘라내며, 항상 건전하다(조건을 만족하는 실제 값은 필터 결과에 남는다). 이 필터가 문제 9-5의 루프 탈출 구간 계산([11,∞], [11,11])에도 핵심으로 쓰인다.

### 문제 9-4 [증명·유도] (M, 슬라이드 18~20)
(a) 위드닝 연산자 ∇ : L × L → L의 **두 조건**을 쓰라. (b) 반복 `x₀ = ⊥, x_{i+1} = x_i ∇ f(x_i)`가 유한 단계에 멈추고, 멈춘 값 x_k가 `lfp(f) ⊑ x_k`를 만족함을 증명하라. (c) ∇가 **대칭일 필요가 없는** 이유를 좌·우 인자의 역할로 설명하고, 구간 위드닝 `[0,5] ∇ [1,6]`과 `[1,5] ∇ [0,6]`을 계산하라.

**풀이.**
(a) ① `∀x,y. x ⊔ y ⊑ x ∇ y` (join 이상으로 과근사 — 두 인자를 모두 덮음). ② 임의의 증가 사슬 `z₀ ⊑ z₁ ⊑ ···`에 대해 `y₀ = z₀, y_{i+1} = y_i ∇ z_{i+1}`로 정의한 수열이 **유한 단계 후 안정**(수렴)한다.
(b) **종료**: 수열 x₀, x₁, ...에서 x_{i+1} = x_i ∇ f(x_i)이고 조건 ①로 `x_i ⊑ x_i ∇ f(x_i) = x_{i+1}` — 증가 수열이다. 조건 ②가 바로 "∇로 만든 증가 수열은 유한 단계에 안정"을 보장하므로 어떤 k에서 `x_{k+1} = x_k`. **건전성**: 그때 `f(x_k) ⊑ x_k ∇ f(x_k) = x_{k+1} = x_k` (조건 ①에서 `f(x_k) ⊑ x_k ∇ f(x_k)`). 즉 x_k는 **pre-fixed point**(`f(x_k) ⊑ x_k`)이고, Tarski 정리의 `lfp(f) = ⨅{x | f(x)⊑x}`에 의해 **`lfp(f) ⊑ x_k`** — 결과는 정답(lfp)의 과근사이므로 건전하다. ∎
(c) 알고리즘에서 좌측 인자는 **이전 반복까지의 누적값**, 우측 인자는 **이번 반복의 새 값**이다. "어느 쪽 경계가 움직였는가"(불안정한가)를 판단해 움직인 쪽만 무한대로 보내야 하므로 두 인자의 역할이 다르다 → 대칭일 이유가 없다. 계산(규칙: 하한은 `l₁ ≤ l₂`면 l₁ 유지, 아니면 −∞; 상한은 `h₁ ≥ h₂`면 h₁ 유지, 아니면 ∞):
- `[0,5] ∇ [1,6]`: 하한 0≤1 → 0 유지; 상한 5<6(올라감, 불안정) → ∞. 결과 **[0,∞]**.
- `[1,5] ∇ [0,6]`: 하한 1>0(내려감, 불안정) → −∞; 상한 5<6 → ∞. 결과 **[−∞,∞]**.
직관: 안정된 경계는 유지하고, 움직이는 경계는 즉시 무한으로 보내 수렴을 강제한다 — 정밀도를 지불하고 종료를 산다.

### 문제 9-5 [계산·추적] (F, 슬라이드 22~28)
다음 코드에 (1) 위드닝 반복, (2) 루프 탈출 구간, (3) **내로잉(narrowing)** 반복을 차례로 손으로 수행하라. (구간 내로잉: `[l₁,h₁] △ [l₂,h₂]`는 l₁=−∞면 l₂ 아니면 l₁, h₁=∞면 h₂ 아니면 h₁.)
```c
x = 0;
while x <= 10 { x = x + 1; }
```

**풀이.**
**(1) 위드닝 단계** (루프 헤드 상태를 추적, `z ← x_head ∇ (새 유입값)`):
| 단계 | 유입 | 루프 헤드 x |
|---|---|---|
| 초기 진입 | [0,0] | [0,0] |
| 1회: 본문 filter_≤([0,0],10)=[0,0], +1 → [1,1] | [1,1] | [0,0] ∇ [1,1] = **[0,∞]** (상한 0<1 → ∞) |
| 2회: 본문 filter_≤([0,∞],10)=[0,10], +1 → [1,11] | [1,11] | [0,∞] ∇ [1,11] = **[0,∞]** (0≤1, ∞≥11 → 변화 없음) |

수렴: 루프 헤드 **[0,∞]**, 본문 내부 [0,10], 본문 끝 [1,11].
**(2) 루프 탈출**: 조건 x≤10이 거짓 → `filter_>([0,∞],10) = [0,∞] ⊓ [11,∞]` = **[11,∞]**.
**(3) 내로잉 단계** (위드닝 결과에서 시작, `z ← x_head △ (유입값들의 join)`):
- 유입 join = 초기 [0,0] ⊔ 본문 끝 [1,11] = **[0,11]**.
- `[0,∞] △ [0,11]`: 하한 0 ≠ −∞ → 0 유지; 상한 ∞ → 우측 11 채택. 결과 **[0,11]**.
- 재계산: 본문 filter_≤([0,11],10)=[0,10], +1 → [1,11]; 유입 join = [0,0]⊔[1,11] = [0,11]; `[0,11] △ [0,11]` = [0,11] — **안정(수렴)**.
- 탈출: `filter_>([0,11],10)` = [0,11] ⊓ [11,∞] = **[11,11]**.

최종 비교: 위드닝만 — 헤드 [0,∞], 탈출 [11,∞] (건전하나 거침). 내로잉 후 — 헤드 **[0,11]**, 탈출 **[11,11]** (실제로 루프 후 x는 정확히 11 — 정밀!). 교훈: 위드닝은 무한대로 점프해 종료를 강제하고(정밀도 손실), 내로잉은 그 과근사를 하강 반복으로 회복한다. 내로잉의 조건 `y ⊑ x ⇒ y ⊑ x△y ⊑ x`가 결과가 여전히 건전(원래 과근사 범위 내)임을 보장한다.

## 강의 10 — Interprocedural Analysis

### 문제 10-1 [개념·서술] (M, 슬라이드 2~5)
(a) 절차내(intraprocedural) 분석과 절차간(interprocedural) 분석을 정의하라. (b) 절차간 분석을 위해 CFG를 어떻게 확장하는지 — 호출 노드, entry, return, after-call 노드의 역할과 연결 — 를 설명하고, (c) 호출 노드 `x = f(e1,...,en)`과 return 노드의 전이 함수가 각각 무엇을 하는지(매개변수 전달 / 반환값 전달) 쓰라.

**풀이.**
(a) **절차내 분석**: 각 함수의 본문을 다른 함수와의 상호작용 없이 독립적으로 분석. 호출되는 함수의 반환값·부작용을 모르므로 보수적으로 처리할 수밖에 없다. **절차간 분석**: 여러 함수와 함수 호출을 포함한 **전체 프로그램**을 분석 — 호출을 통해 정보가 함수 경계를 넘어 전파된다.
(b) 전체 프로그램의 CFG를 하나로 잇는다: **호출 노드**(`x = f(...)`)에서 **f의 entry 노드**로 간선을 긋고, f의 모든 return을 모은 **return 노드**에서 호출 지점의 **after-call 노드**(호출 직후 이어질 코드)로 간선을 긋는다. 이렇게 하면 호출자의 인자 → 피호출자의 매개변수, 피호출자의 반환값 → 호출자의 변수라는 데이터 흐름을 그래프 간선으로 추적할 수 있다.
(c) **호출 노드 전이**: 현재 상태 σ에서 실인자들을 평가해 매개변수에 매핑한 새 상태 `[x1 ↦ eval(e1,σ), ..., xn ↦ eval(en,σ)]`를 만들어 entry(f)로 보낸다. 그리고 f의 return 상태 σ_return이 정해지면 `σ[x ↦ σ_return(RET)]`(반환값을 x에 할당)을 after-call 노드로 보낸다. **return 노드 전이**: 그 함수를 호출한 **모든 호출 지점 v_i**에 대해, v_i에서의 상태에 반환값을 반영한 `σ_{v_i}[x_i ↦ σ(RET)]`을 각 after(v_i)로 전파한다 — 한 번의 return이 여러 호출 지점으로 분기하는 이 지점이 바로 문맥 무감각 분석의 부정밀(절차간 무효 경로)이 생기는 곳이다(문제 10-2).

### 문제 10-2 [계산·추적] (M, 슬라이드 13·20)
다음 프로그램을 (a) **문맥 무감각**(k=0) 분석과 (b) **k=1 call string** 분석으로 각각 손으로 돌려 y, z의 구간을 구하고 비교하라. (호출 지점: then 가지의 호출 = C1, else 가지의 호출 = C2.)
```c
fn foo(a) { RET = a + a; return; }

if input() { x = 1; y = foo(x); }   // C1
else       { x = 2; z = foo(x); }   // C2
```

**풀이.**
(a) **문맥 무감각**: 두 호출 지점의 정보가 foo 안에서 **합쳐진다**.
- foo의 a: [1,1] ⊔ [2,2] = **[1,2]**.
- RET = a + a: [1,2] + [1,2] = **[2,4]**.
- return이 모든 after-call로 같은 값을 전파 → **y: [2,4], z: [2,4]**.
실제론 y=2, z=4뿐인데 [2,4]로 부정밀하다. 원인: "C1로 들어가 C2로 나오는" 식의 **절차간 무효 경로**(interprocedurally invalid path)의 데이터 흐름이 섞이기 때문.
(b) **k=1 call string**: 문맥 = 최근 호출 지점 1개. foo가 두 문맥으로 분리 분석된다.
- 문맥 (C1): a = [1,1], RET = [1,1]+[1,1] = **[2,2]** → return 시 push(c_i, C1) = (C1)을 만족하는 호출 지점 C1로만 복귀 → **y: [2,2]**.
- 문맥 (C2): a = [2,2], RET = **[4,4]** → **z: [4,4]**.

비교: k=1이 두 호출의 영향을 완전히 분리해 **정확한 결과**(y=2, z=4)를 준다. 문맥 민감의 본질 — 같은 함수라도 호출 문맥별로 추상 상태를 따로 유지해 무효 경로를 차단하는 것 — 이 드러나는 최소 예제다.

### 문제 10-3 [계산·추적] (F, 슬라이드 22~23)
중첩 호출이 있는 다음 프로그램에서 (a) **k=1**이 왜 정밀도를 잃는지 bar의 문맥을 추적해 보이고, (b) **k=2**가 어떻게 회복하는지 보여라. (foo 내부의 bar 호출 지점 = C3.)
```c
fn bar(c) { RET = c; return; }
fn foo(a) { b = bar(a); RET = b + b; return; }   // bar 호출 = C3

if input() { x = 1; y = foo(x); }   // C1
else       { x = 2; z = foo(x); }   // C2
```

**풀이.**
(a) **k=1**: foo는 (C1)·(C2)로 구분되어 a가 각각 [1,1]·[2,2]로 정확하다. 그러나 foo 안에서 bar를 호출할 때 `push((C1), C3) = (C3)`, `push((C2), C3) = (C3)` — k=1이라 호출열이 **C3 하나로 잘려(truncate)** 두 경로가 **같은 문맥 (C3)**이 된다.
- bar의 (C3): c = [1,1] ⊔ [2,2] = **[1,2]**, RET = [1,2].
- 양쪽 foo로 b = [1,2]가 돌아가고, RET = b + b = **[2,4]** → **y: [2,4], z: [2,4]** — bar 수준에서 다시 섞여 부정밀.
(b) **k=2**: `push((C1), C3) = (C3, C1)`, `push((C2), C3) = (C3, C2)` — bar가 **두 문맥으로 분리**된다.
- bar의 (C3,C1): c = [1,1], RET = [1,1]. bar의 (C3,C2): c = [2,2], RET = [2,2].
- foo(C1): b = [1,1], RET = [2,2] → **y: [2,2]**. foo(C2): b = [2,2], RET = [4,4] → **z: [4,4]**.

교훈: k는 "정밀도가 유지되는 호출 깊이"다 — 호출 체인이 k보다 깊어지는 지점에서 문맥이 잘려 정보가 섞인다. k를 키우면 회복되지만 문맥 수가 지수적으로 늘어난다(문제 10-5).

### 문제 10-4 [증명·유도/계산] (M, 슬라이드 16~19)
k-call-site 민감도에서 (a) Context = Call^{<k}의 의미와 ε·부분 호출열·길이 k 호출열 각각의 해석을 쓰라. (b) push 연산을 정의하고 k=2에서 `push(ε, C1)`, `push((C1), C3)`, `push((C3,C1), C5)`를 계산하라. (c) return 시 "push(c_i, v_i) = c를 만족하는 c_i로 복귀"하는 역추적 규칙이 왜 필요한지 — 한 함수가 여러 곳에서 호출될 때를 들어 — 설명하라.

**풀이.**
(a) 문맥은 **호출 지점들의 열**이다. **ε**(빈 열) = 호출 스택 없음(main 최상위). **(v₁,...,v_m), m<k** = 높이 정확히 m인 호출 스택 — v₁이 현재 함수를 부른 지점, v_m은 main 안의 호출 지점. **(v₁,...,v_k)** = 높이 **k 이상**인 호출 스택 — k개를 넘는 오래된 호출은 잘라낸(truncate) 것이므로 "최근 k개만 기억".
(b) `push((v₁,...,v_m), v₀)` = m < k이면 `(v₀, v₁, ..., v_m)`(맨 앞에 추가), m = k이면 `(v₀, v₁, ..., v_{k−1})`(맨 앞에 추가하고 가장 오래된 v_k를 버림). k=2에서:
- `push(ε, C1) = (C1)` (길이 0 < 2).
- `push((C1), C3) = (C3, C1)` (길이 1 < 2).
- `push((C3,C1), C5) = (C5, C3)` (길이 2 = k → C1 탈락).
(c) 한 함수 f가 여러 지점(v₁, v₂, ...)에서 호출되면, f의 return에 도달한 상태는 **자기가 어느 호출에서 왔는지**에 따라 돌아갈 곳이 다르다. 문맥 c가 그 이력을 담고 있으므로, `push(c_i, v_i) = c`를 만족하는 (호출 지점 v_i, 호출자 문맥 c_i) 조합을 찾아 **그 호출 지점의 after-call로만** 반환값을 전파한다. 예: `x = foo(1)`(v1)과 `y = foo(2)`(v2)가 있을 때, c = (v1)인 return은 x에만, c = (v2)인 return은 y에만 반환값을 쓴다 — 이 역추적이 없으면 반환값이 모든 호출 지점으로 흘러 문맥 무감각과 같아진다.

### 문제 10-5 [개념·서술] (M, 슬라이드 24·26~30)
(a) k-call-site 분석의 비용이 k에 어떻게 의존하는지(`height((Call^{<k} → Var → Sign)ⁿ) = O(c^k · m · n)`)를 해석하고, 실무에서 k 선택이 어떻게 이루어지는지 쓰라. (b) **functional approach**(Context = State)의 아이디어, "함수 요약(function summary)"의 정의, 정밀도가 **최적**인 이유, 그리고 비용(`O(5^m · m · n)`)을 설명하라. (c) 실무 변형인 parameter sensitivity와 object sensitivity를 한 줄씩 설명하라.

**풀이.**
(a) c = |호출 지점|, m = |변수|, n = |노드|일 때 가능한 문맥 수가 **c^k**(길이 ≤ k의 호출열 조합)이고, 각 (노드, 문맥)마다 변수 m개의 상태를 유지하므로 격자 높이(= 비용 인자)가 **O(c^k·m·n)** — **k에 지수적**. 그래서 k=1도 부족할 때가 있지만(중첩 호출, 문제 10-3) k≥2는 일반적으로 너무 비싸며, 실무에서는 **호출 지점별로 k를 휴리스틱으로 다르게** 선택한다(중요한/뜨거운 함수만 깊게).
(b) **functional approach**: 문맥 = **호출 시점의 추상 상태(State)** 자체. 각 노드의 격자 원소가 맵 `m_v : State → State ∪ {unreachable}`이고, 함수 f의 exit 노드의 맵 `m_exit`가 곧 **함수 요약** — "추상 진입 상태 ↦ 추상 종료 상태"로 함수 전체의 효과를 모델링한다(전이 함수가 한 명령의 효과라면 요약은 함수 전체의 효과). 정밀도: 같은 함수라도 **들어오는 상태가 다르면 완전히 분리**해 분석하므로 **모든 호출을 인라인한 것과 동일한 최적 정밀도**이고 절차간 무효 경로가 완전히 사라진다. 비용: State = Var→Sign이면 상태 공간이 5^m이라 높이가 **O(5^m·m·n)** — 변수 수에 지수적이라 매우 비싸다.
(c) **parameter sensitivity**: 문맥을 **함수 매개변수들의 추상값**으로 한정(포인터·전역 변수가 없으면 functional과 동등). **object sensitivity**: 객체지향 언어에서 문맥을 **수신자 객체(receiver)의 추상값**으로 정의 — 같은 메서드라도 호출 대상 객체별로 분리 분석하며, OO 프로그램 분석에서 널리 쓰인다. 모두 "완전한 functional은 비싸니 문맥을 상태의 일부로 줄이자"는 선택적 적용이다.

## 강의 11 — Control Flow Analysis

### 문제 11-1 [개념·서술] (S, 슬라이드 2)
제어 흐름 분석(CFA)에서 **"함수가 값(first-class)"**이라는 전제가 왜 호출 그래프 구성을 비자명하게 만드는지, 그리고 결과 호출 그래프가 왜 **보수적 과근사(over-approximation)**여야 하는지 설명하라. 만약 과근사 대신 과소근사(일부 가능한 호출을 누락)를 하면 어떤 문제가 생기는가?

**풀이.**
함수가 값이면 `x()`에서 `x`가 어떤 함수를 담고 있는지가 실행 경로에 따라 달라져 코드만으로 정해지지 않는다. CFA는 각 호출 지점에서 **불릴 수 있는 모든 함수를 빠짐없이** 포함해야 한다(may 정보). 과근사는 실제로 안 불릴 함수를 일부 포함해도 안전하지만, **과소근사는 실제 가능한 호출 대상을 누락**하므로, 이를 토대로 한 절차간 분석(강의 10)이 그 경로의 데이터 흐름을 못 보아 **unsound**해진다 — 예컨대 "이 변수는 절대 음수가 안 됨" 같은 거짓 결론을 내려 잘못된 최적화·검증으로 이어진다. 안전성의 비대칭성(빠뜨리면 치명적, 더 포함하면 정밀도만 손해) 때문에 과근사를 택한다.

### 문제 11-2 [계산·추적] (M, 슬라이드 3~7)
다음 코드에 CFA 제약식을 세우고 최소 해를 구하라.
```
fn f() {...}  fn g() {...}
a = f;
b = g;
if ... { c = a; } else { c = b; }
d = c;
```
각 변수의 `[·]`를 구하라.

**풀이.**
제약식(슬3 규칙): 함수 정의에서 `f∈[f]`, `g∈[g]`; 대입에서 `[f]⊆[a]`, `[g]⊆[b]`, `[c=a]`로 `[a]⊆[c]`, `[c=b]`로 `[b]⊆[c]`(분기 조건은 무시 — 양쪽 다 가능하다고 보수적으로 가정), `[c]⊆[d]`.
최소 해: `[f]={f}`, `[g]={g}`, `[a]={f}`, `[b]={g}`, **`[c]={f,g}`**(분기로 a·b를 모두 받음), **`[d]={f,g}`**(c를 복사).
해설: 최소 해란 모든 제약을 만족하는 집합 할당 중 각 집합이 가장 작은 것 — 빈 집합에서 출발해 제약이 요구하는 토큰만 더하면 자연히 얻어진다. 이후 `d()` 같은 호출이 있다면 호출 그래프에 d → f와 d → g 두 간선이 그려진다.

### 문제 11-3 [계산·추적] (M, 슬라이드 10~15)
3차 알고리즘으로 다음 제약을 **처리 순서대로** 적용하며 각 변수의 `sol`, `succ`, `cond`의 변화를 추적하라.
제약(이 순서): (1) `t∈x ⇒ y⊆z`, (2) `x⊆y`, (3) `t∈x`.

**풀이.**
- (1) `t∈x ⇒ y⊆z`: 이 시점 `x.sol`에 t 없음(조건 거짓) → 발동하지 않고 **`x.cond(t).add(y,z)`** (잠재움).
- (2) `x⊆y`: `AddEdge(x,y)` → `x.succ={y}`. x.sol이 비어 있어 흘려보낼 토큰 없음.
- (3) `t∈x`: `AddToken(t,x)` → `x.sol={t}`, `W={(t,x)}`. 이어 `Propagate()`:
  - `(t,x)` 꺼냄. ① `x.cond(t)`에 `(y,z)`가 있음 → **`AddEdge(y,z)`** → `y.succ={z}` (잠든 조건부가 깨어남). ② `x.succ={y}`이므로 `AddToken(t,y)` → `y.sol={t}`, `W={(t,y)}`.
  - `(t,y)` 꺼냄. `y.cond(t)` 비었고, `y.succ={z}` → `AddToken(t,z)` → `z.sol={t}`.
  - W가 비어 종료.

최종: `x.sol = y.sol = z.sol = {t}`; `x.succ={y}`, `y.succ={z}`; `x.cond(t)={(y,z)}`.
교훈: 조건부 제약이 먼저 와서 cond에 잠들었다가, 나중에 `t∈x`가 성립하는 순간 Propagate가 깨워 간선을 추가하고, 그 간선을 따라 토큰이 연쇄 전파된다. 처리 순서가 달라도 최소 해는 동일하다(단조성과 lfp 유일성).

### 문제 11-4 [증명·유도] (M, 슬라이드 16)
3차 알고리즘이 **O(n³)** 시간에 동작함을 (토큰 O(n), 변수 O(n), `t∈x` 제약 O(n), `x⊆y`/조건부 제약 O(n²) 가정 하에) 유도하라. 지배항이 어디서 나오는지 밝히고, "각 (t,v) 쌍이 워크리스트에 최대 한 번 들어간다"는 사실이 어디서 보장되는지 답하라.

**풀이.**
- **(t,v) 쌍의 1회성**: `AddToken`의 가드 `if t ∉ x.sol`이 보장한다 — 같은 토큰을 같은 변수에 두 번 넣지 않으므로, 각 (t,v)는 평생 최대 한 번 W에 들어간다. 따라서 Propagate의 총 반복 수 ≤ |토큰| × |변수| = O(n²).
- `AddEdge`의 총 호출: 무조건 포함 제약과 조건부 제약이 합쳐 O(n²)개이고 각 조건부는 최대 한 번 발동 → O(n²)회. 간선도 중복 추가가 가드로 차단되어 최대 O(n²)개.
- **지배항 — AddToken의 총 호출 수**: 토큰 전파는 간선을 따라 일어난다. 간선이 최대 O(n²)개이고, 각 간선 `x→y`를 따라 흐를 수 있는 토큰이 최대 O(n)개이므로, AddToken 호출 총수는 O(n²) × O(n) = **O(n³)**.
- 집합 갱신·검사는 (비트벡터 등으로) O(1)로 가정. 따라서 전체 **O(n³)**.
종료는 단조성 — 토큰과 간선이 **추가만 되고** 모두 유한 — 으로 보장된다. 이 "cubic bottleneck"은 같은 제약 형태를 쓰는 Andersen 포인터 분석에도 그대로 적용되며, 사이클 제거·위상 정렬 순서·공유 비트 벡터 등이 실전 개선책이다(슬17).

### 문제 11-5 [개념·서술] (F + S, 슬라이드 18)
객체지향 언어의 가상 메서드 호출 `x.m(...)`에 대해 **이름·시그니처 매칭 / CHA / RTA** 세 방법의 정밀도를 비교하고, 왜 후보 집합 크기가 `이름매칭 ⊇ CHA ⊇ RTA`인지 설명하라. 또 이 문제가 슬라이드 2~17의 일급 함수 CFA와 본질적으로 같은 문제인 이유를 한 문장으로 답하라.

**풀이.**
- **이름·시그니처 매칭**: 이름이 m이고 인자 타입이 맞는 *모든* 메서드를 후보로. 가장 크고 부정밀.
- **CHA(클래스 계층 분석)**: x의 **선언 타입 T와 그 서브클래스들**의 m만 후보. 런타임 타입은 T이거나 T의 자손일 수밖에 없으므로 그 밖을 제외해도 안전 → 이름매칭의 부분집합.
- **RTA(신속 타입 분석)**: CHA에 더해, 프로그램에서 **실제로 인스턴스화(`new`)되는** 클래스만 남김. 한 번도 생성되지 않는 클래스의 메서드는 불릴 수 없으므로 제외해도 안전 → CHA의 부분집합.
따라서 `이름매칭 ⊇ CHA ⊇ RTA`이고 셋 모두 안전한 과근사이며, RTA가 가장 정밀하다(더 정밀하게는 제약 기반 CFA를 객체에 적용).
**같은 문제인 이유**: 둘 다 "호출 지점에서 실제 호출 대상이 코드만으로 정해지지 않으므로(일급 함수 / 동적 디스패치), 가능한 대상의 집합을 보수적으로 구해 호출 그래프를 만든다"는 동일한 문제다.

### 문제 X-1 [개념·서술] (X: 강의 1 ↔ 7~9)
Rice 정리(강의 1)는 비자명한 성질의 정확한 판정이 불가능함을 말한다. 데이터플로우 분석(강의 7~8)과 구간 분석(강의 9)이 이 한계에 **어떻게 대응하도록 설계**되었는지 — (a) 근사의 방향, (b) 그 설계가 보이는 구체적 장치(JOIN, ⊤, 필터, 위드닝) — 를 정리하고, (c) 구간 분석이 실제로는 안전한 코드에 헛경보를 내는 예를 하나 구성하라.

**풀이.**
(a) 모두 **건전성(과근사)을 택하고 완전성을 포기**한다. "분석이 불가능하다고 한 동작은 정말 불가능"을 지키는 대신, 실제로는 일어나지 않는 동작도 가능하다고 보고할 수 있다(헛경보).
(b) 과근사를 구현하는 장치들: **JOIN**(강의 7) — 어느 분기가 실행될지 모르므로 모든 선행 경로의 정보를 ⊔로 합쳐 빠뜨림을 차단. **⊤** — `input()`처럼 알 수 없는 값은 "모든 값 가능"으로 안전하게 처리. **필터 없이 조건 무시**(기본 분석) 또는 **건전한 필터**(제어 민감, 강의 9) — 조건 활용도 meet으로 과근사를 유지하며 한다. **위드닝**(강의 9) — 정확한 lfp 계산이 안 끝날 수 있으니 lfp **위쪽**(pre-fixed point)으로 점프해 종료를 강제 — 종료마저 과근사로 산다.
(c) 예:
```c
x = input();
if x >= 1 { y = 10 / x; }   // 실제로 x ≥ 1이라 안전
```
기본(제어 무감각) 구간 분석은 then 가지에서도 x = [−∞,∞]로 보므로 "분모가 0일 수 있음" 헛경보를 낸다. 실제로는 0 나누기가 불가능하지만, 분석은 조건 정보를 잃었다 — Rice 정리상 어떤 건전한 분석이든 이런 헛경보 사례를 가질 수밖에 없으며, 제어 민감·관계형 도메인 등은 헛경보를 **줄이는**(없애지는 못하는) 정밀도 개선이다.

### 문제 X-2 [증명·유도] (X: 강의 5~6 ↔ 7~8)
워크리스트 알고리즘의 복잡도 O(n·h·k)(강의 7 슬33)에서 h는 격자 높이다. (a) 강의 5의 격자 구성 법칙(곱·맵의 높이)을 사용해, 변수 m개의 부호 분석 상태 격자 `Var→Sign`의 높이와, 강의 8의 멱집합 분석(원소 m개)의 높이를 구하라. (b) 이를 대입해 강의 8 슬23의 결론 "이 분석들은 O(n·m²)"을 유도하라. (c) 이 모든 것의 이론적 뿌리인 Kleene 정리와 워크리스트 알고리즘의 관계를 설명하라.

**풀이.**
(a) **맵 격자 높이 = |키| × height(값 격자)**(강의 5 슬29). `Var→Sign`은 m × 2 = **2m**(Sign의 높이는 2). **멱집합 격자 𝒫(원소 m개)의 높이 = m**(∅에서 원소를 하나씩 더해 전체까지) — live variables의 𝒫(Var), available expressions의 𝒫(Expr) 모두 해당(역멱집합도 높이는 같다 — 순서만 뒤집힘).
(b) 강의 8의 네 분석에서 h = m(멱집합 높이)이고, 전이 함수 계산 비용 k = O(m)(집합 연산이 원소 수에 비례). 따라서 O(n·h·k) = O(n · m · m) = **O(n·m²)**. ∎
(c) Kleene 정리(강의 6)는 "유한 높이 + 단조 ⇒ ⊥에서 f를 반복하면 lfp에 유한 단계로 도달"을 보장하는 **이론**이고, 워크리스트는 그 반복에서 "바뀐 성분이 의존하는 노드만 재계산"하도록 **효율화한 구현**이다. 같은 lfp에 도달함은 갱신 순서 무관성(단조성·lfp 유일성, 강의 7 슬26)이 보장한다. h가 반복 횟수의 상한이 되는 이유도 Kleene 증명의 "진증가는 높이만큼만 가능"에서 온다 — 격자 이론이 알고리즘의 종료·비용을 직접 결정하는 구조다.

### 문제 X-3 [개념·서술/유도] (X: 강의 3~4 ↔ 11)
타입 분석(강의 3~4)은 **등식 제약 + 단일화(Union-Find)**로 거의 선형 시간 O(n·α(n))에 풀리고, CFA(강의 11)는 **포함 제약 + cubic 알고리즘**으로 O(n³)에 풀린다. (a) 두 제약 시스템의 형태 차이(등식 vs 포함·조건부)를 비교하라. (b) 등식 제약이 왜 Union-Find로 충분한지, 포함 제약은 왜 그래프 전파가 필요한지 설명하라. (c) "포함 제약을 등식으로 바꿔 풀면 빨라지지만 정밀도를 잃는다"는 trade-off를 두 분석의 관점에서 논하라.

**풀이.**
(a) 타입 제약은 `⟦x⟧ = ⟦y⟧`, `⟦x⟧ = C(T₁,...,Tₙ)` 형태의 **대칭적 등식**이다. CFA 제약은 `t ∈ x`, `x ⊆ y`, `t∈x ⇒ y⊆z` 형태로 — `x ⊆ y`는 **방향이 있고**(y가 x를 포함, 역은 아님), 조건부는 해가 자라야 발동되는 동적 구조다.
(b) **등식은 동치 관계**(반사·대칭·추이)를 이루므로, "같다"는 정보를 동치류 합치기(Union)로 누적하고 대표 비교(Find)로 질의하면 끝난다 — 항의 구조 분해(같은 생성자끼리 인자 Unify)까지 합쳐도 거의 선형. 반면 **포함은 비대칭**이라 동치류로 뭉갤 수 없다 — `[y]⊆[x]`는 y의 토큰이 x로 "흐른다"는 단방향 정보이므로, 변수를 노드·포함을 간선으로 한 그래프에서 **토큰을 전파**해야 하고, 간선 O(n²) × 토큰 O(n)의 전파가 cubic의 지배항이 된다(강의 11 슬16).
(c) 포함 제약을 등식으로 강화하면(`x ⊆ y`를 `x = y`로) 모든 변수가 Union-Find 동치류로 합쳐져 **거의 선형**이 되지만, 단방향이어야 할 흐름이 양방향이 되어 한쪽에만 속하던 토큰이 양쪽에 다 속하게 된다 — **집합이 커져 정밀도 하락**(과근사는 유지되므로 여전히 건전). 이것이 정확히 "정밀하지만 cubic"과 "거칠지만 선형"의 trade-off이며, 타입 분석의 단일화가 빠른 이유(문제가 본래 등식)와 CFA가 비싼 이유(문제가 본래 포함)를 동시에 설명한다. (이 두 노선은 강의 14의 Andersen(포함)과 Steensgaard(등식) 포인터 분석으로 그대로 이어진다.)

### 문제 X-4 [증명·유도] (X: 강의 9 ↔ 5~6)
(a) Kleene 정리(강의 6)의 전제 중 구간 도메인(강의 9)이 위반하는 것을 지적하고, 위드닝이 그 빈자리를 어떻게 메우는지 — ∇의 수렴 조건(조건 ②)이 Kleene의 "유한 높이" 역할을 어떻게 대신하는지 — 설명하라. (b) 위드닝 반복의 결과 x_k가 "확장적 함수"(강의 6 슬8, `x ⊑ f(x)`) 개념과 어떻게 연결되는지, 그리고 lfp(f) ⊑ x_k가 Tarski 정리의 어느 부분에서 나오는지 답하라.

**풀이.**
(a) Kleene의 전제는 ① 완비 격자, ② f 단조, ③ **유한 높이**다. 구간 도메인은 ①·②는 만족하나 ③을 위반한다([0,0]⊑[0,1]⊑... 무한 사슬). 유한 높이의 역할은 "증가 사슬이 유한 단계에 멈춤"인데, ∇의 조건 ② — "**임의의** 증가 사슬 z₀⊑z₁⊑...에 대해 yᵢ₊₁ = yᵢ ∇ zᵢ₊₁ 수열이 유한 단계에 수렴" — 가 정확히 같은 보장을 **격자 구조 대신 연산자에** 부과한 것이다. 즉 격자가 못 주는 종료를 연산자가 준다: 반복식을 `x_{i+1} = x_i ∇ f(x_i)`로 바꾸면 f(xᵢ)들이 만드는 사슬에 조건 ②가 적용되어 유한 수렴한다.
(b) ∇의 조건 ①(`x⊔y ⊑ x∇y`)에 의해 `x_i ⊑ x_i ∇ f(x_i) = x_{i+1}` — 즉 한 단계 갱신 함수 `g(x) = x ∇ f(x)`는 **확장적**이다(강의 6 슬8의 정의 그대로). 확장적이므로 수열은 단조 증가하고, 수렴점 x_k에서 `f(x_k) ⊑ x_k∇f(x_k) = x_k`가 성립해 x_k는 **pre-fixed point**다. Tarski 정리의 표현 `lfp(f) = ⨅{x | f(x) ⊑ x}` — lfp는 모든 pre-fixed point의 meet, 따라서 모든 pre-fixed point 이하 — 에서 곧바로 **lfp(f) ⊑ x_k**. 결론: 위드닝은 "Kleene의 종료 보장"을 잃은 자리에 "Tarski의 건전성 보장"을 채워, 정확한 lfp 대신 **lfp의 건전한 과근사를 유한 시간에** 준다.

### 문제 X-5 [개념·서술] (X: 강의 10 ↔ 11)
강의 10의 절차간 분석은 "각 호출 지점에서 어떤 함수가 불리는지 안다"를 암묵적으로 전제했다. (a) 함수 포인터·일급 함수가 있는 언어에서 이 전제가 깨지는 이유와, CFA(강의 11)가 절차간 분석의 **전처리**가 되는 구조를 설명하라. (b) CFA가 만든 호출 그래프가 과근사일 때(실제보다 간선이 많을 때) 절차간 분석의 건전성·정밀도에 각각 어떤 영향이 있는가? (c) 반대로 호출 그래프에서 간선 하나가 누락되면 무슨 일이 생기는지, 구체적 시나리오로 답하라.

**풀이.**
(a) 강의 10의 CFG 확장(호출 노드 → entry(f), return → after-call)은 "호출 노드마다 대상 함수 f"를 알아야 간선을 그릴 수 있다. C의 직접 호출 `foo()`라면 이름이 코드에 박혀 있어 공짜지만, `x()`(x는 함수 값)에서는 x에 어떤 함수가 담길지 실행 경로에 따라 달라 자명하지 않다. CFA는 각 변수가 가리킬 수 있는 함수 집합 `[x]`를 제약 풀이로 구해 **호출 지점 → 가능한 대상 함수들**의 호출 그래프를 만들고, 절차간 분석은 그 간선 위에 매개변수·반환값 전이를 얹는다 — 따라서 CFA가 선행 단계다.
(b) 간선이 실제보다 많으면(과근사): 절차간 분석이 일어나지 않을 호출 경로의 데이터 흐름까지 합치므로 **정밀도는 떨어지지만 건전성은 유지**된다 — 실제 실행의 모든 흐름이 여전히 포함되기 때문. CFA의 cubic 제약(`f∈[y] ⇒ [z]⊆[a_f] ∧ [RET_f]⊆[x]`)이 정확히 "가능한 대상마다 인자·반환 흐름을 활성화"하는 구조라 둘은 자연스럽게 맞물린다.
(c) 간선 누락(과소근사) 시나리오: `x = foo` 가 어떤 경로로 일어날 수 있는데 CFA가 이를 놓쳐 호출 그래프에 `x() → foo` 간선이 없다고 하자. 그러면 절차간 분석은 foo의 매개변수로 인자가 흐르는 것도, foo의 반환값이 호출 결과로 흐르는 것도 보지 못한다 — 예컨대 foo가 음수를 반환할 수 있는데 분석은 "호출 결과는 항상 양수"라고 결론 내릴 수 있고, 이를 믿은 최적화·검증이 실제 실행에서 깨진다(**unsound**). 그래서 호출 그래프는 반드시 may(과근사)여야 한다(문제 11-1과 동일한 안전성 비대칭).

### 문제 X-6 [증명·유도] (X: 강의 6 ↔ 7·11)
"단조성 + 유한성"이 종료를 보장하는 패턴이 세 알고리즘 — (i) 단순 고정점(강의 6), (ii) 데이터플로우 워크리스트(강의 7), (iii) cubic의 Propagate(강의 11) — 에서 각각 어떻게 나타나는지 통일적으로 정리하라. 각 알고리즘에 대해 "단조 증가하는 유한한 양"이 무엇인지 명시하고, 그 양의 상한이 복잡도의 어느 인자가 되는지 답하라.

**풀이.**
공통 패턴: **상태가 어떤 유한한 순서 구조에서 증가만 하고(단조), 진증가 횟수가 유계이므로, "변화가 있을 때만 일하는" 루프는 반드시 멈춘다.**
- (i) **단순 고정점**: 증가하는 양 = 전체 상태 `x ∈ L` (사슬 `⊥ ⊑ f(⊥) ⊑ f²(⊥) ⊑ ...`, f의 단조성으로 증가 — 문제 6-5(a)). 진증가 상한 = **격자 높이 h** → 반복 횟수 ≤ h, 복잡도의 "높이" 인자.
- (ii) **워크리스트**: 증가하는 양 = 각 노드의 상태 xᵢ (값이 바뀔 때만 갱신하고, 갱신은 ⊔에 의한 증가). 노드 하나가 바뀔 수 있는 횟수 ≤ h → 총 재처리 ≤ n·h → **O(n·h·k)**의 n·h 부분. 워크리스트가 비는 것 = 더 이상 바뀌는 노드가 없음 = 고정점.
- (iii) **cubic의 Propagate**: 증가하는 양 = 각 변수의 `sol` 집합과 간선 집합 `succ` (AddToken·AddEdge 모두 가드로 중복을 막고 **추가만** 한다). (t,v) 쌍이 W에 들어가는 횟수 ≤ 1 → Propagate 반복 ≤ |T|×|V| = O(n²); 간선 O(n²) × 토큰 O(n)이 AddToken 총량 **O(n³)**의 지배항.
요약: 세 경우 모두 "단조 + 유한"이 종료 증명의 전부이고, **그 유한한 양의 크기(높이 h, n·h, n³)가 곧 시간 복잡도의 상한**이 된다. 격자 이론(강의 5~6)이 이 셋을 하나의 정리로 묶는 공용어다.

### 문제 X-7 [개념·서술] (X: 강의 5 ↔ 8·12 예고)
강의 8의 may/must 분석은 격자 선택부터 다르다. (a) may 분석이 멱집합 `(𝒫(A), ⊆)`를, must 분석이 역멱집합 `(𝒫(A), ⊇)`를 쓰는 이유를 강의 5의 격자 구성(슬25)으로 설명하라. (b) 두 격자에서 ⊥·⊤·join이 각각 무엇인지 표로 정리하고, live variable(후방 분석)의 return 노드 규칙 `⟦v⟧ = ∅`과 available expression(전방 분석)의 entry 규칙 `⟦v⟧ = ⊤ = ∅`에서 — 같은 ∅이 한쪽에선 ⊥, 다른 쪽에선 ⊤인 이유를 설명하라.

**풀이.**
(a) 격자의 **순서가 "안전한 근사" 방향을 정의**한다(강의 5 슬9: x⊑y면 y가 더 보수적). may 분석에서 보수적인 쪽은 "집합을 **크게**"(가능성을 더 포함 — 누락이 위험)이므로 큰 집합이 위가 되는 **⊆ 순서**(멱집합)를 쓰고, join = ∪로 가능성을 모은다. must 분석에서 보수적인 쪽은 "집합을 **작게**"(확신을 덜 — 과장이 위험)이므로 작은 집합이 위가 되는 **⊇ 순서**(역멱집합)를 쓰고, join = ∩으로 공통만 남긴다. 같은 𝒫(A)에서 순서만 뒤집으면 join/meet, ⊥/⊤이 모두 맞바뀐다는 것이 강의 5 슬25의 요점이다.
(b)
| | (𝒫(A), ⊆) — may | (𝒫(A), ⊇) — must |
|---|---|---|
| ⊥ | ∅ | A (전체) |
| ⊤ | A (전체) | ∅ |
| join(⊔) | 합집합 ∪ | 교집합 ∩ |

live variable의 return 규칙 `∅`: 후방 분석의 **시작점**으로, "반환 후엔 아무 변수도 안 읽힌다"는 **가장 정밀하고 확실한 정보** — may 격자에서 ∅은 ⊥(최소·가장 정밀)이다. available expression의 entry 규칙 `∅`: "시작 시 아무 식도 계산 안 됨"이라는 **가장 보수적인 정보** — must 격자(⊇)에서는 작은 집합이 위이므로 ∅이 **⊤**(가장 부정밀·보수적)이다. 같은 기호 ∅이 격자 순서에 따라 정반대의 극값이 된다는 점이, "격자를 먼저 정해야 분석의 의미가 정해진다"는 교훈을 준다.

### 문제 X-8 [개념·서술] (X: 강의 4 ↔ 10)
let-다형성(강의 4 슬20)과 k-call-site 문맥 민감 분석(강의 10)은 "호출 지점 구분"이라는 같은 발상을 공유한다. (a) 두 기법에서 "무엇이 호출 지점마다 복제·인스턴스화되는가"를 비교하라. (b) 두 기법이 공유하는 비용 문제(지수 폭발)를 각각의 복잡도로 쓰라. (c) let-다형성의 한계(매개변수로 받은 함수는 단형, 강의 4 슬21)에 대응하는 문맥 민감 분석의 한계(강의 10)는 무엇인가?

**풀이.**
(a) **let-다형성**: 함수의 **타입**이 ∀X로 일반화되고, 각 호출 지점에서 X가 그 지점의 인자 타입으로 **인스턴스화**된다 — `f(1)`에서 `fn(i32)→i32`, `f(true)`에서 `fn(bool)→bool`. **k-call-site**: 함수의 **추상 상태(분석)**가 문맥(최근 k개 호출 지점 열)마다 **분리 유지**된다 — (foo,(C1))의 a=[1,1]과 (foo,(C2))의 a=[2,2]. 전자는 타입 수준, 후자는 값(상태) 수준의 "호출 지점별 복제"다.
(b) let-다형성: 최악 **지수 시간**(인스턴스화의 중첩 — Hindley-Milner의 알려진 최악 복잡도, 강의 4 슬20). k-call-site: 문맥 수 **c^k**(c = 호출 지점 수)로 **k에 지수적**(강의 10 슬24의 O(c^k·m·n)). 둘 다 "구분을 늘릴수록 정밀해지지만 조합이 폭발"하는 같은 구조다.
(c) let-다형성은 **매개변수로 받은 함수 y를 다형적으로 쓸 수 없다**(g 안에서 y(1); y(true) 불가 — 고차 다형성 부재). 대응하는 문맥 민감의 한계는 **k 절단(truncation)**: 호출 체인이 k보다 깊어지면 문맥이 잘려 그보다 깊은 호출들이 같은 문맥으로 합쳐진다(강의 10 슬22의 k=1에서 bar의 (C3) 합쳐짐). 두 경우 모두 "구분의 깊이에 한계를 둬서 결정 가능성/비용을 지키는" 설계이며, 무제한 구분은 결정 불가능(다형 재귀)하거나 비용이 폭발(k=∞)한다.

### 문제 X-9 [계산·추적] (X: 강의 4 ↔ 6~7)
강의 4 슬18의 코드(흐름 무감각 타입 분석이 거부)를 단순화한 다음 코드를 생각하자. 타입을 격자 `flat({int, bool})`(⊥ / int, bool / ⊤)의 추상값으로 보고, **흐름 감각** 분석(각 지점마다 `x ↦ 타입` 상태, 강의 6~7의 프레임워크)을 돌려라.
```c
v1: x = 1;        // (1)
v2: y = x + 2;    // (2)  — x가 int여야 함
v3: x = true;     // (3)
v4: if x { ... }  // (4)  — x가 bool이어야 함
```
(a) 각 지점 이후의 x 타입을 추적하고, (2)와 (4)의 타입 요구가 모두 충족됨을 보여라. (b) 흐름 무감각 분석(강의 4)은 왜 같은 코드를 거부하는지 제약으로 보여라. (c) 이 대비가 주는 일반 교훈을 쓰라.

**풀이.**
(a) 흐름 감각 추적(전방, 각 노드 이후 상태):
| 지점 | x의 타입 |
|---|---|
| v1 이후 | int (1을 대입) |
| v2 이후 | int (x는 안 바뀜; `x+2`는 현재 x=int를 요구 — **충족**) |
| v3 이후 | **bool** (재대입이 타입을 덮어씀 — 지점별 상태라 가능) |
| v4 | `if x`는 현재 x=bool을 요구 — **충족** |

두 사용 지점의 요구가 **그 시점의** x 타입과 각각 맞으므로 분석은 통과한다(실제로도 런타임 타입 오류 없음 — 동적 언어의 흔한 패턴).
(b) 흐름 무감각 타입 분석은 x에 **위치와 무관한 단 하나의 타입 변수 ⟦x⟧**를 둔다. 수집되는 제약: `x = 1`에서 ⟦x⟧ = int(덧셈 규칙 포함), `x = true`와 `if x`에서 ⟦x⟧ = bool. `int = bool`은 다른 생성자라 단일화 실패 → **"not ok"(헛경보)**.
(c) **상태를 지점별로 쪼개면(흐름 감각) 같은 변수의 시간에 따른 변화를 표현할 수 있어 헛경보가 줄어든다** — 그 대가는 지점 수만큼 커진 상태 공간(격자 `(Var→L)ⁿ`)과 고정점 계산 비용이다. 강의 4의 한계(슬18)가 강의 6~7의 프레임워크로 해소되는 구조이며, "정밀도는 구분(지점·문맥·경로)을 늘려서 산다"는 과목 전체의 패턴(흐름 감각·문맥 민감·경로 민감)의 첫 사례다.

### 문제 X-10 [계산·추적] (X: 강의 2 ↔ 7·9)
강의 2 슬33의 MIR(문제 2-4(b)의 bb0~bb3)을 대상으로 구간 분석을 돌리려 한다.
```
bb0: x = 0; y = 0; jump bb1
bb1: t = x < 10; switch t (T: bb2, F: bb3)
bb2: x = x + 1; y = y + x; jump bb1
bb3: return y
```
(a) bb1의 상태가 어떤 노드들에 의존하는지(JOIN의 선행자) 밝히고, 이 CFG 구조가 왜 고정점 반복을 강제하는지 설명하라. (b) x에 대해 join만 쓰는 반복이 만드는 상태 수열(루프 헤드 bb1 기준, 처음 3회)을 쓰고, (c) 위드닝을 적용한 수렴 결과와 (제어 민감 필터 가정 시) bb3에서의 x 구간을 구하라.

**풀이.**
(a) bb1의 선행자는 **bb0(초기 진입)과 bb2(루프 본문에서 복귀)** — JOIN(bb1) = ⟦bb0⟧ ⊔ ⟦bb2⟧. 그런데 bb2의 상태는 bb1(필터 통과 후)에 의존하므로 **bb1 ⇄ bb2 순환 의존**이 생긴다(강의 6 슬5의 상호 재귀 방정식). 어느 쪽도 먼저 확정할 수 없으므로 ⊥에서 시작해 수렴까지 반복하는 고정점 계산이 필요하다 — MIR의 역방향 간선(bb2→bb1) 하나가 분석 방법론 전체(고정점·위드닝)를 끌고 들어오는 셈이다.
(b) join만 쓰는 반복(x만 추적, bb1 도착 시점):
- 1회: [0,0] (bb0에서).
- 2회: [0,0] ⊔ (본문: filter_<([0,0],10)=[0,0], +1 → [1,1]) = **[0,1]**.
- 3회: [0,1] ⊔ [1,2] = **[0,2]**. — 이후 [0,3], [0,4], ... 로 **수렴하지 않는다**(구간 격자의 무한 높이).
(c) 위드닝: [0,0] ∇ [1,1] = **[0,∞]** (상한 불안정 → ∞). 다음 반복: 본문 filter_<([0,∞],10) = [0,9], +1 → [1,10]; [0,∞] ∇ [1,10] = [0,∞] — **수렴**. bb3 진입은 조건 `x < 10` 거짓 경로이므로 filter_≥([0,∞], 10) = **[10,∞]**. (내로잉을 더 돌리면 bb1이 [0,10]으로 좁혀지고 bb3는 [10,10]까지 회복된다 — 강의 9 슬28과 같은 패턴.)
교훈: 강의 2의 컴파일러 구조(MIR CFG)와 강의 7~9의 분석 이론이 정확히 한 무대에서 만난다 — Assignment 4가 바로 이 조합이다.

### 문제 X-11 [개념·서술] (X: 강의 1 ↔ 7)
상수 전파(강의 7 슬22)는 `b = a * 2`를 `b = 6`으로 치환하는 최적화를 가능하게 한다. (a) 이 치환의 안전성이 강의 1의 어떤 원칙(건전성/완전성 중 무엇)에 의존하는지, "완전하지만 불건전한" 상수 분석이 있다면 왜 이 치환에 쓸 수 없는지 논하라. (b) 상수 전파의 flat(ℤ) 격자에서 ⊤로 답하는 것과 구체 상수로 답하는 것의 의미를 건전성 관점에서 비교하라. (c) `c = a + input()`이 ⊤가 되는 것은 정밀도 손실인가, 불가피한 건전성인가?

**풀이.**
(a) 치환은 **의미 보존 변환**이므로 "a는 3 외의 값일 수 없다"는 **확신** — 즉 **건전성** — 이 필요하다(강의 1 슬25). 완전하지만 불건전한 분석의 "a = 3"은 "a가 3일 수 있다"일 뿐, 다른 실행에서 a가 5일 가능성을 빠뜨렸을 수 있다. 그 상태로 `a*2`를 6으로 굳히면 a=5인 실행에서 b가 10이어야 할 것이 6이 되어 **프로그램의 의미가 바뀐다**. 변환의 전제는 항상 "분석이 불가능하다고 한 것은 정말 불가능"(건전성)이다.
(b) flat(ℤ)에서 구체 상수 n으로 답함 = "모든 실행에서 그 변수는 정확히 n" — 가장 정밀하면서 건전한 답(치환 가능). **⊤로 답함 = "상수가 아닐 수 있음/모름"** — 정보는 없지만 어떤 실행도 빠뜨리지 않으므로 역시 건전(치환은 포기). ⊥ = "이 지점 도달 불가/미정". 건전성은 세 답 모두 유지하며, 정밀도만 다르다 — "확신이 없으면 ⊤로 후퇴"가 건전한 분석의 기본 동작이다.
(c) **불가피한 건전성이다.** `input()`은 임의의 값이 될 수 있으므로 어떤 건전한 분석도 그 합을 단일 상수로 답할 수 없다 — ⊤는 정보 부족의 정직한 표현이지 분석의 결함이 아니다. (반면 `+ +̂ −  = ⊤` 같은 경우는 도메인의 표현력 한계로 인한 **정밀도 손실** — 더 풍부한 도메인(구간·관계형)이면 좁힐 수 있다. "원리적으로 알 수 없는 ⊤"와 "도메인이 거칠어 생기는 ⊤"를 구분하는 것이 도메인 설계의 감각이다.)

### 문제 X-12 [설계·응용] (X: 강의 8 ↔ 9·11)
세 알고리즘 — 강의 8의 PropagationWorkListAlgorithm, 강의 9의 PropagationWithWidening, 강의 11의 cubic Propagate — 은 모두 "워크리스트에서 꺼내 → 지역 계산 → 변했으면 갱신하고 의존 대상 추가"의 구조를 공유한다. (a) 세 알고리즘에서 (꺼내는 단위 / 지역 계산 / 갱신 연산 / 의존 대상)을 표로 대응시켜라. (b) 강의 9 버전이 강의 8 버전에서 바꾼 것은 단 하나다 — 무엇이며 왜 그 한 줄로 충분한가? (c) 이 공통 구조를 갖춘 새 분석을 설계할 때 설계자가 정해야 할 것들을 체크리스트로 정리하라.

**풀이.**
(a)
| | 강의 8 (전파 워크리스트) | 강의 9 (위드닝 전파) | 강의 11 (cubic Propagate) |
|---|---|---|---|
| 꺼내는 단위 | 노드 vᵢ | (노드, [문맥]) vᵢ | (토큰, 변수) 쌍 (t,x) |
| 지역 계산 | y ← t_{vᵢ}(xᵢ) (전이 함수) | Y ← t_v(xᵢ) (제어 민감: (상태, 다음 노드) 집합) | x.cond(t)의 잠든 제약 발동 + 후속으로 토큰 전파 |
| 갱신 연산 | z ← xⱼ **⊔** y | z ← xⱼ **∇** y | sol.add / succ.add (집합 추가, 가드로 중복 차단) |
| 의존 대상 | dep(vᵢ) (전방이면 succ) | 전이가 알려준 다음 노드 vⱼ | x.succ (포함 간선의 끝점들) |

(b) **join(⊔)을 위드닝(∇)으로 바꾼 것뿐이다** (`z ← xⱼ ⊔ y` → `z ← xⱼ ∇ y`). 충분한 이유: 알고리즘의 종료 논거가 "갱신될 때마다 값이 커지고, 커질 수 있는 횟수가 유한"인데, 무한 높이 격자에서 깨지는 것은 **"유한"** 쪽뿐이다. ∇는 (i) ⊔ 이상이므로 건전성·단조 증가는 그대로 유지되고, (ii) 수렴 조건(∇ 정의 ②)이 증가 횟수의 유한성을 연산자 수준에서 복구한다. 나머지 구조(워크리스트, 변화 감지, 전파)는 높이와 무관하므로 손댈 필요가 없다.
(c) 설계 체크리스트:
1. **도메인(격자)**: 추상값과 순서 ⊑ — 유한 높이인가? 아니면 ∇·△을 함께 설계.
2. **방향·합류**: 전방/후방(JOIN = pred/succ, dep은 그 반대), may/must(⊔ = ∪/∩) — 강의 8의 4분면에서 위치 결정.
3. **전이 함수 t_v**: 노드 종류별 효과(kill/gen 또는 eval·갱신) — 각 t_v가 **단조**이고 **건전**(실제 의미를 과근사)함을 확인.
4. **초기값**: 시작 노드 = 분석의 출발 정보(entry ⊤ 또는 ∅ 등), 나머지 = ⊥.
5. **(필요시) 문맥**: 절차간이면 문맥 종류(k-call-site / functional)와 push·return 규칙.
이 다섯을 채우면 워크리스트 엔진은 공용이다 — 단조 프레임워크(강의 7 슬4)가 "분석 제조 틀"이라는 말의 실천적 의미다.
